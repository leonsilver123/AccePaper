# @deepseek-ai/dsh-research-web

English | [中文](README.zh.md)

The dual-face plugin of the research workbench. The host half is deliberately inert (it performs no host registration), while the browser half mounts the `research` tab of the `conversation.view` slot as 9 panels: Summary / Pipeline / Figures / Tables / Roadmap / Gates / Adversarial / Approval / Recovery.

The panels are derived from a run summary by pure selectors in `panels.ts`, and `summary.ts` is a dependency-free view model, so both are unit-testable without Cordis. Copy goes through the `zh` / `en` dictionaries in `client/locales.ts`, following the client's locale-ownership convention.

## Known Limitations and Deferred Work

- **A retry is the same command** (2026-09-16): the approval panel mints a `commandId` per intent and REUSES it when the reader presses the same button again after a failure — a timeout must not become a second decision. Changing the decision mints a new one, because that is a different intent. The id is required on the wire: a command with no identity cannot be retried safely.
- **The page states what kind of run this is and whether anything is ready** (2026-09-16): the wire twin now declares the four readiness facts the host has carried since the readiness split — `evidenceProfile`, `profileEligible`, `submissionReady`, `readinessNote` — and the workbench states the mode and the readiness beside the source badge. **The twin had not declared them**, so the browser received all four and could name none: the same drift `packageExport` and `runPersistence` are annotated for, and the third time this face has silently dropped host fields. Readiness is stated where the badge is, NOT behind a tab, because it is true of the whole run. **An unstated readiness renders as unstated**, never as ready and never as failed: `null` and `false` are different answers, and only one of them was checked.
- **A run stopped at the human gate says it is waiting, not that it is finished** (2026-09-16): `runStatusOf` returns the new `awaiting-approval` when every automatable step has closed and a step is `gated`, instead of `completed`. A gated step is not an unfinished one — the pipeline has stopped exactly where it is supposed to — and a header reading "completed" at the moment it needs the reader is the promise that status exists to stop making. The intro copy was corrected in the same pass: surviving all sixteen steps produces a manuscript whose MATERIAL is complete, and "material is not submittability" now says what else it takes (the production evidence profile, every gate closed, no unclosed reviewer concern, a person's approval).
- **The page names the project revision it is showing** (2026-09-16): the Remote projection carries the run's `projectRevision` and the workbench states it beside the source badge, so a reader can tell whether what is on screen and an exported package — whose manifest carries the same number — describe one state of the study or two. **A host that names none shows none**: a missing revision is not rendered as zero, because zero is a revision a run genuinely starts at, and showing it would name a state nobody read. **Not yet per artifact**: the artifact list on the wire carries no revision of its own.
- **A decision the backend applied is shown as applied, whatever else failed** (2026-09-16): the approval receipt now carries `approvalEventId`, `decidedAt` and `persisted`, and the panel states three separate facts where it used to state one. A decision that did not reach disk says so — "the decision stands and was NOT saved, a restart loses it" — instead of reading exactly like one that did; and a run the client could not re-read says "the decision stands and the page could not be refreshed", instead of being reported as a MALFORMED RESPONSE that told the operator their approval failed while the run said it passed. **Before this the client dropped `persisted` and `persistenceError` on the floor**, and a summary that failed to build replaced a successful decision with `ok: false`. The three receipt fields are REQUIRED on the wire: a backend built before them is reported as a host/client build mismatch rather than defaulted, because defaulting them invents the two facts this channel exists to carry.
- **The real data path is connected**: the workbench starts a real run through `ctx.remote.research.run({})` and renders it, with the badge following the data source. **It never invents a run**: a session that has run nothing shows the orientation block and the run control alone, and a failed run states its cause and leaves no run on screen. The bundled demo run it used to fall back to is gone from `src/` — it lives under `tests/support/` now, where no production import can reach it.
- The component **has an injection seam**: `ResearchWorkbench` accepts three props — `summary`, `onRun`, `onApprove` (inject a summary, start a run, submit a human verdict). An absent `summary` means no run has happened, which the view reports rather than filling in.
- **Human approval is wired to the backend** (2026-09-14): `client/approval-source.ts` sends the verdict over `ctx.connection.rpc.call('/research-approval', 'decide', ...)` to the channel `dsh-research-team` registers and the host browser-authenticates, and the panel renders only the status, attempt, and operator the backend returns; a rejection, an invalidation, or a transport failure **reports itself truthfully** and leaves the step awaiting review. When `onApprove` is absent (a deployment with no browser-authentication channel) the two buttons are **disabled** with the reason stated, rather than displaying a decision nobody made.
- The recovery panel is **read-only, and says why**: this deployment exposes no restore entry point, so the panel reports the run on screen and offers no action. It used to offer a "restore from snapshot" button whose handler reloaded the demo run, which looked like a recovery and replaced the reader's run with invented data.
- **Test coverage has been completed** (B5): all 9 tabs are clicked, and every selector in `panels.ts` is imported; the host half of `src/index.ts` is a deliberately empty body (the view is mounted by the client half), so no test references it.

No invariant companion is published because the package publishes no runtime invariant entry: its host half is intentionally inert, leaving no companion to publish.

- **The run wiring is Runtime-verified** (2026-09-15). The research tab starts a real run — `ctx.remote.research.run({})` → mapping in `run-source.ts` → rendering by `ResearchWorkbench` — and has been driven by an independent browser probe against a running Host on port 1120, asserting against the backend's own records (`.workbuddy/tmp/verify-browser-b.mjs`, 30/30). The earlier note here said no browser had ever driven it; that was true when written and is no longer.
- **The approval panel is likewise only Integration-verified**: its submitter is covered by jsdom specs against a stubbed Connection service, and `dsh-research-team/tests/approval.spec.ts` covers the backend checks and each invariant in §8.1; what was verified on a real socket is **the channel itself** (no cookie → 401 and the handler is not called; token exchanged for a cookie → 200 and a backend record written; forged cookie → 401), not this click in a browser.
- **The `summary` payload shape is a structural twin declared by this package.** The service compiles on the Host face and this package on the Client face, and a client bundle takes no cross-plugin value dependency, so `WireRunSnapshot` in `run-source.ts` is a **restatement** rather than an import. A field name that differs between the two sides makes the view silently empty. The host-side integration spec asserts exactly the same set of field names.
- **The MOCK badge follows the data source** (`summary.isMock`), and no production path produces a fixture-sourced summary any more: `run-source.ts` labels every run it maps `live`. The badge is therefore reachable only for a host that injects a fixture-labelled summary, which today means the specs.
