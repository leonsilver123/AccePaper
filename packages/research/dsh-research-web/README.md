# @deepseek-ai/dsh-research-web

English | [中文](README.zh.md)

The dual-face plugin of the research workbench. The host half is deliberately inert (it performs no host registration), while the browser half mounts the `research` tab of the `conversation.view` slot as 9 panels: Summary / Pipeline / Figures / Tables / Roadmap / Gates / Adversarial / Approval / Recovery.

The panels are derived from a run summary by pure selectors in `panels.ts`, and `summary.ts` is a dependency-free view model, so both are unit-testable without Cordis. Copy goes through the `zh` / `en` dictionaries in `client/locales.ts`, following the client's locale-ownership convention.

## Known Limitations and Deferred Work

- **The page follows a run's stream instead of polling it** (2026-09-16): `client/follow-source.ts` opens `followRun`, renders every `snapshot` frame (the service's own projection), and uses the `event` frames as its POSITION: a frame that does not continue the sequence it holds is refused, and the page re-opens rather than applying a state it cannot account for. A `resync` frame re-opens without the refused cursor; the position survives across re-opens, so a re-open can tell whether it missed anything. Re-opening is bounded (`MAX_FOLLOW_ATTEMPTS`), because a host that answered every open with a refusal would otherwise spin a tab. **The events are not replayed into a projection here** — the service owns that, and a second one in the client could disagree with it while looking entirely plausible.
- **A step that did not pass says why, on the step** (2026-09-16): the overview's step list showed only `blocked`, and the reason lived behind another tab in a gate record the reader had to know to look for. Each step now carries its failing gate's rationale — the aggregate's own sentence, so a step held because a required check never ran says exactly that. **What it still does not do**: it does not say what to DO about it. The reason names the check; the remedy is still the reader's.
- **A retry is the same command** (2026-09-16): the approval panel mints a `commandId` per intent and REUSES it when the reader presses the same button again after a failure — a timeout must not become a second decision. Changing the decision mints a new one, because that is a different intent. The id is required on the wire: a command with no identity cannot be retried safely.
- **The page states what kind of run this is and whether anything is ready** (2026-09-16): the wire twin now declares the four readiness facts the host has carried since the readiness split — `evidenceProfile`, `profileEligible`, `submissionReady`, `readinessNote` — and the workbench states the mode and the readiness beside the source badge. **The twin had not declared them**, so the browser received all four and could name none: the same drift `packageExport` and `runPersistence` are annotated for, and the third time this face has silently dropped host fields. Readiness is stated where the badge is, NOT behind a tab, because it is true of the whole run. **An unstated readiness renders as unstated**, never as ready and never as failed: `null` and `false` are different answers, and only one of them was checked.
- **A run stopped at the human gate says it is waiting, not that it is finished** (2026-09-16): `runStatusOf` returns the new `awaiting-approval` when every automatable step has closed and a step is `gated`, instead of `completed`. A gated step is not an unfinished one — the pipeline has stopped exactly where it is supposed to — and a header reading "completed" at the moment it needs the reader is the promise that status exists to stop making. The intro copy was corrected in the same pass: surviving all sixteen steps produces a manuscript whose MATERIAL is complete, and "material is not submittability" now says what else it takes (the production evidence profile, every gate closed, no unclosed reviewer concern, a person's approval).
- **The page names the project revision it is showing** (2026-09-16): the Remote projection carries the run's `projectRevision` and the workbench states it beside the source badge, so a reader can tell whether what is on screen and an exported package — whose manifest carries the same number — describe one state of the study or two. **A host that names none shows none**: a missing revision is not rendered as zero, because zero is a revision a run genuinely starts at, and showing it would name a state nobody read. **Not yet per artifact**: the artifact list on the wire carries no revision of its own.
- **A decision the backend applied is shown as applied, whatever else failed** (2026-09-16): the approval receipt now carries `approvalEventId`, `decidedAt` and `persisted`, and the panel states three separate facts where it used to state one. A decision that did not reach disk says so — "the decision stands and was NOT saved, a restart loses it" — instead of reading exactly like one that did; and a run the client could not re-read says "the decision stands and the page could not be refreshed", instead of being reported as a MALFORMED RESPONSE that told the operator their approval failed while the run said it passed. **Before this the client dropped `persisted` and `persistenceError` on the floor**, and a summary that failed to build replaced a successful decision with `ok: false`. The three receipt fields are REQUIRED on the wire: a backend built before them is reported as a host/client build mismatch rather than defaulted, because defaulting them invents the two facts this channel exists to carry.
- **The page starts a run and follows it, instead of waiting for one** (2026-09-16): `client/index.ts` now calls `startRun` for a run id, then reads `runSnapshot` and hands every snapshot to the workbench as it arrives — so the page shows the run while the study is still working, and shows the run's id and its execution state (`running` / `stopped` / `failed`, with the driver's own error when it threw) beside the readiness badges. Before this it awaited `remote.research.run(...)`, which resolves only when the whole study is over: minutes of blank page, and a reload that lost the run's identity. **The command id is minted per press and reused on a retry**, so a response the page never read does not become a second study. **A reload restores the run this tab was following**, from a session-scoped handle: the driver is the host's, so what a reload may lose is the page's handle on the run, and a page that came back saying "nothing has been run" over a study still going would be reporting its own amnesia as the run's state. **A run the service holds no record of is reported as exactly that**, rather than polling a run that does not exist. **What this is not**: an event stream. The page polls on a fixed client interval, so a step's progress appears within an interval rather than when it lands, and there is no cursor, dedup or gap recovery — those arrive with the channel that needs them. **`summary.execution` is null when the host names none**, and the page then states nothing rather than defaulting to stopped.
- **The real data path is connected**: the workbench starts a real run through the Host's `research` namespace and renders it, with the badge following the data source. **It never invents a run**: a session that has run nothing shows the orientation block and the run control alone, and a failed run states its cause and leaves no run on screen. The bundled demo run it used to fall back to is gone from `src/` — it lives under `tests/support/` now, where no production import can reach it.
- The component **has an injection seam**: `ResearchWorkbench` accepts `summary`, `onRun`, `onPropose`, `onApprove` (inject a summary, start and follow a run, ask the host for directions, submit a human verdict). `onRun` takes the confirmed plan and a callback it reports every snapshot through, so a run in progress is rendered as it goes. An absent `summary` means no run has happened, which the view reports rather than filling in.
- **Human approval is wired to the backend** (2026-09-14): `client/approval-source.ts` sends the verdict over `ctx.connection.rpc.call('/research-approval', 'decide', ...)` to the channel `dsh-research-team` registers and the host browser-authenticates, and the panel renders only the status, attempt, and operator the backend returns; a rejection, an invalidation, or a transport failure **reports itself truthfully** and leaves the step awaiting review. When `onApprove` is absent (a deployment with no browser-authentication channel) the two buttons are **disabled** with the reason stated, rather than displaying a decision nobody made.
- The recovery panel is **read-only, and says why**: this deployment exposes no restore entry point, so the panel reports the run on screen and offers no action. It used to offer a "restore from snapshot" button whose handler reloaded the demo run, which looked like a recovery and replaced the reader's run with invented data.
- **Test coverage has been completed** (B5): all 9 tabs are clicked, and every selector in `panels.ts` is imported; the host half of `src/index.ts` is a deliberately empty body (the view is mounted by the client half), so no test references it.

No invariant companion is published because the package publishes no runtime invariant entry: its host half is intentionally inert, leaving no companion to publish.

- **The page can say what its link is doing** (2026-09-17): `connection-state.ts` names the seven phases a subscription passes through (`idle`, `connecting`, `live`, `reconnecting`, `resyncing`, `offline`, `disposed`), the follow loop reports every transition it makes, and the workbench states the phase for a run on screen. **`live` requires a frame** — an open that was requested is not a connection — and a disposed link ignores everything, so a frame already in flight cannot move a page that has let go of a run back into `live`. The "may not be current" note is attached only in `offline`, when the page has STOPPED repairing itself; while reconnecting the state is stale too, but the page is fixing it. **A revision-bound write is closed only in the disconnected phases**: a run followed to its rest leaves the link `disposed`, and the human gate is reached exactly there, so a rule that demanded `live` would make a finished study undecidable. The approval and revision panels disable their controls with the reason stated.
- **The revision loop has a tab, and it does not pretend to close** (2026-09-17): `RevisionPanel` reads the run's revision requests, their candidates and their reviews from the host and renders the request, the sections it targets, **both sides of every changed section** (before and after, both from the host — a page that showed only the new text would ask the reader to remember the old one), and each check's verdict with the detail behind it. Two controls move the loop: write a candidate, and review one. **No accept is offered, and the panel says why**: turning a candidate into the official manuscript needs an accepting transaction that does not exist, so the tab states the gap where a person would look for the control rather than rendering a candidate as accepted. A loop that could not be read is reported as a failure, not as "no revisions".
- **The gate offers the third thing a reviewer means** (2026-09-17): the approval panel sends `request_changes` with the instruction the person typed, and the button stays disabled until there is text, because the backend refuses a request that names nothing. **The receipt states the decision the BACKEND recorded**, not one derived from the step's status: a change request leaves the step `gated`, so a derived value reported a rejection the operator did not make and hid the instruction they wrote. The panel states all three decisions, and a step whose snapshot carries a recorded decision shows it — who decided, when, and what was asked for — so a page that reloaded, or was never open, reads the request off the run rather than off a chat.
- **The workbench is organized by the researcher's task, not by pipeline vocabulary** (2026-09-17): six stages (`stages.ts`) group the run's own steps — task and material, literature and positioning, method and experiment setup, results and figures, organization and writing, review and delivery — and every state a stage shows is derived from its steps' statuses, so collapsing a stage or visiting one cannot change whether a study advances. The intake group reports no step: what a person supplies before a study exists is not a seventeenth executed step. **`awaiting-human` is its own bucket and never progress**; a status this build cannot name is `unknown` and blocks its stage rather than being defaulted to `not-started`. The progress line reports counts — passed of catalogued, decisions waiting on a person, failures, unknown states — and carries **no percentage and no completion time**. A later stage names the EARLIEST incomplete stage it waits on. **"You supply this" and "this build cannot place these steps" are different facts**: the intake group is `declared === 0`, and a stage whose declared steps the projection did not carry says so and names them. **A study opened second is not overwritten by the first**: each read takes a generation and a snapshot from an older one is dropped. The grouping is checked against the engine's own catalogue by `tests/stages.spec.ts`, which imports `STEPS` from the core package's source and fails when a step is added. **Not done**: the connection state machine and the single project cache M05 calls for.
- **The studies a deployment holds are offered as a list, so a page that remembers nothing can still open one** (2026-09-17): the workbench renders `[data-research-projects]` rows — one per study, each carrying how many steps passed of how many the pipeline catalogues, the execution state, the host's own `saveFailure` and interruption facts, the run id it opens by, and an "Open this study" button. The list is read from the deployment on mount, and the picker appears only when the host provides BOTH `onListRuns` and `onOpenRun`; a host that cannot list studies shows no picker rather than an empty one. **A list that could not be read is reported as a failure, not rendered as "no studies"** — "this deployment holds no study" and "the question could not be asked" have different remedies — and `runListFrom` maps an execution state this build cannot name to `null` rather than folding it into `stopped`. Opening a study performs the same follow the run control performs and remembers the id, so a reload lands on the study the reader picked.
- **The run wiring is Runtime-verified** (2026-09-15). The research tab starts a real run — `ctx.remote.research.run({})` → mapping in `run-source.ts` → rendering by `ResearchWorkbench` — and has been driven by an independent browser probe against a running Host on port 1120, asserting against the backend's own records (`.workbuddy/tmp/verify-browser-b.mjs`, 30/30). The earlier note here said no browser had ever driven it; that was true when written and is no longer.
- **The approval panel is likewise only Integration-verified**: its submitter is covered by jsdom specs against a stubbed Connection service, and `dsh-research-team/tests/approval.spec.ts` covers the backend checks and each invariant in §8.1; what was verified on a real socket is **the channel itself** (no cookie → 401 and the handler is not called; token exchanged for a cookie → 200 and a backend record written; forged cookie → 401), not this click in a browser.
- **The `summary` payload shape is a structural twin declared by this package.** The service compiles on the Host face and this package on the Client face, and a client bundle takes no cross-plugin value dependency, so `WireRunSnapshot` in `run-source.ts` is a **restatement** rather than an import. A field name that differs between the two sides makes the view silently empty. The host-side integration spec asserts exactly the same set of field names.
- **The MOCK badge follows the data source** (`summary.isMock`), and no production path produces a fixture-sourced summary any more: `run-source.ts` labels every run it maps `live`. The badge is therefore reachable only for a host that injects a fixture-labelled summary, which today means the specs.
