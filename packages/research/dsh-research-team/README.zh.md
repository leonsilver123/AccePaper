# @deepseek-ai/dsh-research-team

[English](README.md) | 中文

`ctx.agentTeams` 服务与 T19-B 运行器:红队舰队、带 CAS 修订的任务板、写入范围守卫、会话投影,以及把 16 步驱动起来的执行器注册表(`runner/`)。

分层是显式的:纯逻辑层(`types` / `revision` / `projection` / `scope-guard` / `roster` / `redteam` / `anchor` / `experiment`)→ 薄适配层(`journal` / `task-board` / `session-events` / `research-projection` / `research-guard`)→ `index.ts` 这一个接线点(服务声明、`SessionEventMap` 注入、`ctx.effect` 生命周期)。

`runner/registry.ts` 是 16 步执行器的审计真源:每个条目声明 `stepId` / `executor` / `producer` / `truthfulness` / `timeoutMs` / `gateRequirement` / `recoveryPolicy`,且输入输出 schema 与闸门要求都从 core 的冻结定义派生,以防与 16 步定义漂移。

## 已知限制与延期工作

- **拒绝再导出的检查,必须在移动被复核过之后放行再导出**(2026-09-17,R06):只要上一份包读取时依据的产物移动过,`artifacts-current` 就会失败,而它自己的 detail 写明了该怎么办 —— `re-export to describe the run as it stands`。**这个补救办法做不到**:交给再导出的版本来自**磁盘上那份包**,而一份产物已经移动过的包按构造描述的就是更旧的状态,于是 `moved` 永远不为空,「与上一次导出不同」成了永久违法 —— 一个移动过、又被重新检查并重新批准的运行依然产不出最终包。现在:当包所携带的批准仍覆盖运行当前状态时(`approval !== undefined && staleApproval === undefined`)该检查通过,因为批准会点名它被作出时所依据的产物版本,正是「这次移动被重新看过」的证据;通过的那一侧会把发生过什么说出来,而不是报一句一切正常。**两个该拒绝的方向依然成立** —— 没有批准、或批准已不覆盖当前运行,`approval-recorded` / `approval-current` 失败,这条检查随之失败。**这里没有覆盖的**:调用者无法要求导出**更早版本**的包,所以「旧版本的迟到导出」只能以「移动了却没有对应批准」的形式到达。

- **交付格式是 DOCX 与 LaTeX;PDF 是部署的额外项**(2026-09-17):`CompileFormat` 增加 `docx`,`PandocCompiler` 在 pandoc 可用时提供 `html` / `latex` / `docx` —— **DOCX 不需要自己的引擎**,pandoc 直接写出整个 OOXML 包,图内嵌、公式为 OMML。PDF 仍只在探测到 LaTeX 引擎时提供。E1 **总是**请求这三种交付格式(所以没有配置编译器的部署,工件上仍会带 `compile-compiler-missing`,读者能分清「没编译」与「编译得糟」),只在该部署自己探测得到时才额外请求 PDF。验收:`tests/pdf-acceptance.spec.ts` 用真实 pandoc 写出 DOCX 并把它的部件读回来(ZIP 签名、`word/document.xml`、`word/media/` 里的一项、正文文字真的在包里),并检查 LaTeX 带着 `\documentclass` 与正文。**曾在此报告过一条缺陷,现已撤回**:「正文点名了图的 LaTeX 文档没有正文」看起来像真的,原因却是测试自己的夹具 —— `documentOf` 把 float 挂到**名为 results 的小节**,而夹具把图放在了永远不会带 float 的小节里,于是图根本没进文档。把 float 放到装配器真正放置它的地方重测:LaTeX 带着 `\includegraphics`、caption 与正文,`assets.embedded` 里有那张图,`assets/figure-1.png` 也在包里。探针真正证伪的是 `file://` 形式 —— 它更糟,pandoc 拉不到本地图片 —— 所以保持朴素的绝对路径。

- **PDF 被逐页读出来,而且是在真实引擎上**(2026-09-17,R01):本机装了真实的 TeX Live(来自 CTAN,`scheme-minimal` + `pdftex` + pandoc 模板所需宏包),位于 `.workbuddy/tmp/texlive/tex` —— 这是跟踪树之外的部署工具链,**没有任何指向它的路径被提交**。E1 现在**在部署能产出 PDF 时**编译 `pdf`,依据编译器自己探测出的 `formats`,所以没有引擎的机器永远不会被要求一个它会拒绝的 PDF;三种格式渲染自**同一份**文档模型。`tests/pdf-acceptance.spec.ts` 通过这道缝自己的入口编译,然后**用真实解析器把页面读出来**:文件头、页数大于一、第 1 页带着第一节的标题与正文、第 1 页**没有**第二节的正文而后面某一页有 —— 这一对正是「真实文档」与「页面全空或每页重复」之间的区别。实测:pandoc 2.12 → pdfTeX 3.141592653-2.6-1.40.29(TeX Live 2026)→ 多页 PDF。该用例 `describe.skipIf` 在是否装了引擎上,所以报的是 skipped 而不是静默通过。**这里没有的**:出货 profile 构建的包还没有被编译成 PDF(profile 没点名引擎),「图在第 3 页」也没有被断言。

- **绘图是部署填的一道缝,而图是一张画**(2026-09-17,R05②/R02):`runner/figure-provider.ts` 陈述 `FigureProvider` —— 一个 id、库版本、`renderFigure(spec)` 与 `renderDiagram(graph)`,两者都从一次渲染里返回 SVG **和** base64 PNG —— 而 `dsh-research-cordis/src/matplotlib-provider.ts` 是部署侧的:它通过部署点名的解释器运行一段内置脚本,检查答案真的是 SVG、真的以 PNG 签名开头,并在构造时**被探测**,所以没有这个库的机器不提供 provider,而不是在 D1 才失败。配置方式与编译器一致(`Config.figures` → 引擎探测 → `hostFigureProvider()` → `DriveOptions.figureProvider`)。D1 通过它画图**和**路线图,每张 float 记下 `drawnBy` / `drawnByVersion`;没有 provider 时由内置渲染器画,路线图 float 记 `diagramDrawn: false` —— 这是诚实的状态,而不是一个没人点名的被丢弃 float。对着 venv 里的 matplotlib 3.11.2 验证过(真库用例用 `describe.skipIf` 挂在本机是否有的解释器上)。**E1 把这张画带进文档**:provider 画出的路线图是一张带两种渲染的图,而不是 Mermaid 源码,所以每种编译格式都能内联它;`compilation.documents` 单独携带二进制的交付件(`.docx`、`.pdf`),与它们内联的图(`compilation.assets`)分开 —— 找期刊收到的那份稿件的人,不该在"文档携带的东西"里找它。**这里没有的**:出货 profile 不点名解释器(`Config.figures` 在那里写成可选追加项,因为哪台机器有这个库属于部署事实);而 `pdf` 仍被拒绝,因为本机没有装任何 LaTeX 引擎。

- **一条引用的判断是关于某个版本的句子,不是关于一个槽位**(2026-09-17,R05):`CitationUse.statementId` 的注释陈述了本层需要的性质 —— 重写那句话的修订应当让引用失效 —— 而赋给它的值是常量 `introduction:prior-work`,每次运行的每份草稿共用。**错的有两件事,常量只是其中一件**:绑定还是在**正文存在之前**铸造的(`citationUsesOf({claimRef, statementId})` 在 D3 开头),于是一条绑定唯一能点名的就是槽位。现在四件事分开记录 —— **节点**身份(`Statement.statementId`,由小节与「该句在被引句子中的序号」铸出,所以重写保留节点、插入一句未被引用的句子不会让后面移位)、**内容版本**(`Statement.textSha256`)、**证据版本**(`CitationUse.quoteSha256`)、以及**判断**(它记下自己针对的那个内容版本)。顺序也随之改变:`judgementsFor(claimRef)` 返回已复核语料所确立的内容(**未挂载**),D3 写各小节,`locateStatements` 找出每条被引句子在**哪里**(定位,不是识别),`bindJudgements` 把每条判断挂到引用其来源的那条 statement 上。`checkStatementBindings` 拒绝 `citation-statement-missing` / `citation-statement-changed` / `citation-evidence-changed`,而**重新绑定对任何一种都不是补救** —— 判断是一个人做出的阅读,只有另一次阅读才能替代它。没有任何一句话引用的已复核来源在 D3 就被拒绝(`citation-source-uncited`),而不是从列表里悄悄去掉。**R05③ 的日志**:草稿记录 `proseRequests`(指令原文、要求与收到的证据、带每段文本版本的引用名册),于是一条因「文本变了」被拒的判断可以追溯到那个被回答了一句依赖旧文本的话的请求。 **稿件必须有过部署要求的那些审阅**(2026-09-18,复核的两轮 P0):`revisionRounds` 限的是**能问作者几次**,而循环一旦某轮关闭了自己的意见就停 —— 于是一次碰巧关光的一轮就结束了审阅。`runner/review-policy.ts` 陈述下限(`minimumRounds`,默认两轮)与什么算数:作者照旧答复的一轮不是第二次阅读,而仅仅 `pending-verification` 的意见是欠账不是答复。D4 在下限未达时再要一轮,rebuttal 工件记录策略与它自己的评估。`checkFinalPackage` 新增 `review-complete`:审阅没走完的包可以按它本来的样子作为草稿导出,**不能**作为期刊收到的那份论文。 **意见由读者关闭,不由「改了」这个动作关闭**(2026-09-18,复核的 issue 生命周期 P0):补丁应用成功就处置掉了它的意见(`patched`),非空解释也一样(`accepted_explanation`)—— 于是两个**都不能证明问题被回答**的动作成了结束问题的那两个。补丁可以落在它所针对的那句话旁边;解释是作者对自己作品的陈述。现在 `applyRevision` 把凡是产出了东西的意见一律留在 `pending-verification`,并由 `runner/resolution-verifier.ts` 陈述**谁来判**:部署的 `ResolutionVerifier` 逐条读(拿到关切、答复、改动与当前小节正文),给出 `verified` 或 `rejected`;**核验者署名等于作者时直接拒绝** —— 答复不能给自己发证书。循环的停止原因也说明是哪一种:`closed`,或者在答复已摆在桌上而无人读过时的 `awaiting-verification`。没有核验者的部署,它的意见是**等待**,不是关闭。 **引用是一句话,不是一条来源**(2026-09-18,复核的 P0):`bindJudgements` 用一个 citeKey 集合去重,任何已经绑过的键都被跳过 —— 于是同一来源出现在引言又在讨论里时,只为先出现的那一句生成绑定,其余句子上任何读绑定的检查都没有东西可读。现在**每一句引用它的句子各得一条绑定**,各自携带那句话自己的内容版本,并在同键内按正文顺序排列。反方向也检查了:`checkStatementBindings` 对「这一句引用了来源,却没有任何绑定覆盖它」拒绝(`citation-statement-unbound`)—— 一组绑定可以条条成立,而某一句一个都没有。`checkCitationKeys` 随之改变:一个键命名**一条来源**(这仍然拒绝),而不是命名一次引用(同一来源被两句引用正是论文会做的事)。 **一条引用的支持是关于句子,不是关于它来自的那句主张**(2026-09-18,复核的第二个引用缺口):`evidence-corpus.ts` 记的是复核者对**主张**的结论,而绑定层把那个裁决挂到了引用该来源的那句话上 —— 于是一句没人读过的句子继承了一个它没挣到的 `supported`。`runner/statement-support.ts` 是终结这件事的缝:`StatementAssessment` 记下句子自己的身份与内容版本、来源、**针对那句话**的裁决、裁决所依据的东西、以及谁做的;`StatementSupportAssessor` 是部署读一句话的能力 —— 与 prose writer、figure provider 同形。D3 在部署有 assessor 时逐句评估,并拒绝 `statement-unassessed` / `statement-contradicted` / `statement-unrelated` / `statement-beyond-scope`;D4 把读数**带过去**、把补丁改过的句子**重读**;E1 对**修订后的**稿件再查一次,而**是否要求读数由运行的能力决定,不由工件上恰好有没有那个字段决定** —— 一次把读数弄丢的修订会被拒绝,而不是被当成「这个部署读不了句子」。评估身份同时绑定句子版本、段落版本与 assessor 版本:三者任一变化都使问题变成另一个,于是被更正的 excerpt 会被重读,而不是从缓存里作答。**这里没有的**:assessor 本身属于部署;出货 bundle 不点名任何 assessor,所以出货运行的绑定仍带着主张的裁决,并说明没有句子被读过。**这里没有的**:判断本身仍是被记录下来的裁决而不是重新推导,谁来重读是个人或部署自己的复核者,而模型可见的那半日志住在运行的工件上 —— 没有新增会话事件。

- **质量结果说明「读到了什么」,不只说明「发现了什么」**(2026-09-17,R04):`runner/paper-quality.ts` 新增 `reportPaperQuality(input)`,包清单以它的 `quality` 取代裸的 `qualityFindings` 列表。**空发现列表只是「能读到这份稿件的五条精确规则」的输出,而它读起来像对论文的判定** —— 复核正是逐字拒绝了这种读法。报告把空列表压平的四种事实分开:每条规则一个 `QualityCheck`,带 `no-defect-found` / `defect-found` / `not-applicable` / `not-executed`,以及答不出来时的理由(没有参考文献表、没有一句话陈述测量变化、没有 float 名册、没有草稿);`needsDomainReview` 点名这里任何规则都回答不了的问题(主张是否值得检验、每条被引来源是否真说了引用它的那句话、图是否易读、正文是否声称了测量支撑不了的东西);以及一句说明这份报告**是**什么的 `summary` —— `no defect found by the 3 check(s) that could read this manuscript; 2 check(s) could not run, and 5 question(s) need a domain reviewer` —— 永远不会说论文好。`reviewPaperQuality` 作为「只要 findings」的视图保留,逐条规则的用例仍在驱动它。**这里没有覆盖的**:覆盖清单说的是**这五条**规则里哪些读到了稿件,而不是一篇论文还需要哪些检查;领域问题被点名而没有作答 —— 把评审人的回答记在某条 item id 上还没有做。

- **研究自己呈现自己,报告它的四个步骤不再点名它**(2026-09-17):`runner/study-adapter.ts` 持有 `StudyAdapter` —— 可执行的方法、两条臂的名字与身份、`B3` 与 `C1` 盖的生产者品牌、数字的来源、测量结果(记录、门禁输入、规则版本、序列,都来自**同一次**执行)、每个实验工件附带的来源块、呈现(图计划、渲染器 spec、表、图)、`C3` 所消融的边界、陈述「测量对主张做了什么」的那句话,以及每个章节的兜底正文 —— 运行上下文携带它:第一步之前由计划解析而来,Case Pack 提供研究自己的场景时由 `A2-claim`(通过 `setRunStudy`)重建。**第二个研究现在跑得完**:`LATENCY_PLAN`(单服务器、`p95-latency-ms`、毫秒、**越小越好**、一条声明的到达 trace)走完 16 步并停在人工闸门 —— `tests/second-study-run.spec.ts` —— 而此前它停在 `D1-figure-map`,因为四个执行器各自把编队研究当作名字来认识。**序列是一等的形状**:`StudySeries` 随结果记录同行,`sequencePresentationPlan` 把它画在 `sequence` 轴上、点按位置寻址(`series.arms.baseline.3`),记录的内容哈希覆盖它 —— 两条臂相同而观测不同的两份记录,是两次测量。**同一处改动带出两个门禁缺陷**:A 通道的措辞检查把每条主张都对着编队的短语表读,于是关于任何其他量的主张都没有短语、每条检查都 abstain、一条表述良好的主张被挂起;C 通道则无论运行在跑哪个研究,都用 `measureStudy(ctx.runCtx.study)` 给主张评分。**通用化还暴露了另外四个**:兜底正文里一个负载率是运行从未声明的数字,被数字检查拒绝;`D4` 的一条修订补丁与 `E1` 的一处表注会把编队句子带进任何研究的稿件;判决的 `evaluator` 一行对每次运行都点名编队模块。**这里没有覆盖的**:`SCENARIO.venueName`/`venueId` 仍是 `A1`/`A4`/`E1` 读的部署常量,`A3-agenda` 的主张与证据文本仍是编队味道的兜底正文,图渲染器仍是本仓库自己的工具。

- **编译产物会说明自己装了哪些 float,而编译产物丢了图的包不能是最终包**(2026-09-17,R01/R02):编译按格式报出 `assets.embedded` 与 `assets.dropped`,稿件工件记录下来(`compilation.floatsEmbedded` / `floatsDropped`),内联进文档的图以**字节**进入包(`PackageFile.encoding: 'base64'`,于是 PNG 写成 PNG,摘要也是对着真正落盘的字节算的);`checkFinalPackage` 新增 `compiled-document-complete`:只要编译产物没有带上稿件拥有的某个 float,这份包就不能是 final —— 图缺失的投稿件不是那篇论文。不编译任何东西的部署不受这条约束 —— 它的稿件作为 Markdown 是完整的,工件也写明它没有被编译。包还携带 `figure-plan.json`,于是一张图可以按它被画出来时依据的计划复现,而不只是"在包里能找到"。**这里没有覆盖的**:不点名绘图 provider 的部署,其路线图仍然只有 Mermaid 一种形态,所以它的编译产物装不下 `Figure 2`、包停在 draft —— 对那样的部署这就是诚实的状态,而不是一条该放松的检查。

- **包会写明自己是「哪一版产物」的读数,而对着已移动的运行再次导出会说出来**(2026-09-17):manifest 携带 `artifactRefs`(导出读取的每件产物,以及运行当时持有的版本),`checkFinalPackage` 新增 `artifacts-current`:当后一次导出拿到磁盘上那份包所依据的版本(`previousArtifactRefsOf(directory)`,已接进 `@Remote('exportRunPackage')`)时,检查会点名运行已经走过哪些产物,而这份包无论其他条件如何都只能是 DRAFT。**一次导出是一个状态的读数** —— 后续的步骤、一次修订、一次重跑或一次手工编辑都会替换产物,而仍然自称 final 的包等于在为一份运行已不再持有的文档作证。这条检查也从另一侧覆盖「迟到渲染」:在运行移动之后落地的编译或导出,描述的是它读到的那个状态,会被拒绝成为 final,而不是覆盖读者心中的图景。**这里没有覆盖的**:这条检查比较的是**前一份** manifest 写下的版本,所以只导出过一次、从未被比较过的包没有可比对象 —— 它的 `artifacts-current` 条目陈述的是自己读到什么,而不是它无法支持的判定;而产物级的依赖图(哪一步的产物会让谁失效)属于 core,在那里测试,不在这里复述。

- **稿件是一份文档,而编译是部署填的那道缝**(2026-09-17):`runner/document-compile.ts` 把稿件陈述为若干部件 —— 带类型块的章节(prose、自带 SVG 的 figure、作为 markdown 的 table、作为 mermaid 的 diagram、作为 LaTeX 的 equation)、按正文引用方式命名的 references 且只编号一次 —— 于是 HTML、LaTeX 与之后的任何后端渲染的是同一份文档,而不是对同一段装配字符串的三种读法。`checkCompileRequest` 拒绝:部署没有配置编译器(`compile-compiler-missing`)、编译器在该部署上产不出的格式(`compile-format-unavailable`,没有 LaTeX 引擎的机器对 `pdf` 的回答就是这个)、没有章节的文档、以及参考文献表不持有的引用(`compile-citation-unresolved`)—— 最后一条发生在编译器运行**之前**,因为编译器会把无法解析的引用渲染出来,只在一个没人看的日志里留一条警告。`compileManuscript` 什么都不写:内容返回给调用者去暂存与发布,于是一次失败的编译不可能毁掉上一次导出写下的东西。E1 通过注入的编译器编译 `html`、`latex` 与 `docx`(部署的引擎探测找到引擎时还有 `pdf`),并把 `compilation`(工具、可用格式、已编译文件、作为字节携带的 documents 与 assets、拒绝)记在工件上,于是包的读者能分清「没有编译」与「编译得很糟」。**这里没有的**:出货 bundle 接的编译器驱动的是 `pandoc`(见 `dsh-research-cordis`),目前任何地方都还不产出 PDF;文档模型刻意很薄 —— 段落携带文本,而语句级模型(M04 针对句子的契约)才是 M08 将来渲染的东西。

- **图先被计划,再被画出来,而且它的数值要与运行对账**(2026-09-17):`runner/presentation-plan.ts` 持有 `PlannedFigure` —— 这张图回答的**问题**、它数值来自哪份运行记录、以 `{key, value}` 命名记录字段的 series、坐标轴与单位、不确定性、它自己的画布尺寸与格式、caption,以及论文是否需要它 —— 和带版本的 `PresentationPlan`。**D1 此前只画一张固定 320×240 画布、固定标题、单 series 的柱状图,而没有任何东西说过它是**为了什么**:交付那篇论文带着六个没人引用的 float,而一个不回答任何问题的 float 就是这个样子。现在先建计划、再把它的 spec 交给渲染器,于是读者拿到的图与有人写下的那个问题是同一个对象。**数值对账是一项检查**:一张图绘制的每个值,都必须是运行在它点名的键、它点名的记录下记下的那个值,于是一张图无法图示一个没人做过的测量 —— 漂移过的记录会以 `figure-values-unsourced` 被拒绝,而不是照字面值画出来;单独驱动的步骤会把来源写成 `recomputed-measurement`,让读者能分清两种情况。其余拒绝是 `figure-no-question`(不回答任何问题的 float 是装饰)、`figure-sequence-missing`(横轴声明为序列、而点不是序列中的位置,画出的趋势没有任何测量支撑)、`figure-interval-missing`(没人算过的区间带是运行没有做出的不确定性主张)与 `figure-duplicate-id`。**这里没有的**:渲染器仍是本仓库自己的 SVG/PNG 工具,而不是计划推荐的 Matplotlib provider —— 本机是 Python 3.14 且未安装 Matplotlib,所以没有任何依赖它的 provider 被接进来,图的字体与样式是内置渲染器所拥有的那些;图的易读性与它与正文的一致性属于视觉复核(M09),这里不判定。

- **一节是按它「欠读者什么」来写的,而否证必须被当成否证来报**(2026-09-17):`runner/argument-plan.ts` 持有 `SectionContract` —— 该节的**职责**、没有就不能写的证据、以及它必须履行的义务 —— 和 `ArgumentPlan`,后者由运行派生:问题、主张,以及 `claimOutcomeOf(measuredPct, committedDirection, thresholdPct)`,它说出测量是**支持**了主张、**否证**了它、还是没达到阈值。**出货运行否证了它自己的主张**(−38.2% 对「至少 +20%」的预测),而它稿件的任何一节都没有这样说 —— 这正是本单元存在的理由:当结果是 `refuted` 时,报告结果的那些节必须写明测量到的变化、用词写出的方向、**以及**该测量与主张相矛盾这三件事,之所以是三条独立义务,是因为一节只带 `-38.20%` 时,skim 的读者从中得不到任何关于「主张怎么样了」的信息。E1 拒绝未履行义务的稿件(`argument-obligation-unmet`,点名是哪一节、哪条义务)、计划声明而稿件缺失的节、以及稿件带着而计划从未声明的节。计划随草稿一起携带 `ARGUMENT_PLAN_VERSION`,并由 D4 带过去,于是一次修订是**对它写作时所依据的那份计划**受检。**计划是派生的,不是配置的**:同一项确定性研究在第二个任务的承诺(预测下降)下,被同一个 −38.2% **支持**,它的各节欠的是方向而不是矛盾 —— 这是生产路径上的一条仓库自有测试。原先住在 `section-evidence.ts` 的证据要求现在住在契约上,于一节的「所需证据」与「义务」是一条记录,而不是两张会漂移的表。**这里没有的**:需要读者来判断的义务(Discussion 的替代解释、Conclusion 的局限)记录在契约上但不作判定,因为对散文立规则就成了关于散文的规则;一节所记录的版本也不包含「是哪个 skill 或提示词组装了写作请求」—— 请求不是会话事件,所以草稿记录的是计划与它写作所依据的证据,而不是指令本身。

- **一条引用绑定到一句话,以及有人真读过的那段文本**(2026-09-17):`runner/citation-bindings.ts` 持有 `CitationUse` —— 陈述、来源、稳定的 `citeKey`、读到该段文本的位置、那段文本及它的 SHA-256、支持关系、读到多少、以及谁判定的。**键来自标识符,绝不来自标题**:`citeKeyOf` 铸出 `cite-<id>`,因为用作者加年份拼出的键会撞车,用标题拼出的键会在标题被更正时移位。`checkCitationUse` 拒绝:没有引文的绑定、比「读到的范围」更强的支持判断(只读了摘要无法确立只有方法才能显示的东西)、已被撤稿的来源、检索到却不被持有的来源、以及对一个读不到的来源作出的支持判断。**参考文献表由引用派生,检索则留在它本来的位置 —— 候选库**:`buildReferences`(把 landscape 扫描返回的每一条命中都变成条目)已删除,D3 放进草稿的是 `bibliographyOf(citations)`,于是一篇文献出现在参考文献表里,是因为有一句话引用了它。**这是读交付那篇论文读出来的**:它参考文献表里 25 个真实 DOI,正文一句都没引 —— 没有任何测试能看见,因为两半各自都能工作。`checkManuscriptCitations` 现在在 E1 拒绝三件事,那里是正文与列表在稿件成为产物之前同时在手的地方 —— 正文引了而列表没有的键(`citation-target-missing`)、没有一句话引用的条目(`citation-entry-uncited`)、以及本次运行没有复核判断的被引来源(`citation-unreviewed-source`,引用检索命中的那条正是这种)。写作者会拿到 `citations`,并被要求用 `[@citeKey]` 点名每个来源;E1 把它们印成列表分配的编号;D4 把绑定带过去,于是一次修订不会把正确的引用变成未复核的引用。**引言陈述了文献位置却一句不引的运行,会在 E1 被拒绝,且不发布任何稿件** —— 这条拒绝是本仓库自己的测试,不是演示。**这里没有的**:只有部署已复核的语料可以被引用,所以这次运行的文献位置建立在三个人读过的来源上;引用所针对的陈述目前是一个固定槽位(`introduction:prior-work`),而不是稿件按句子铸出的 id;语料没有记录 locator(卷、页或文章号),于是 `missingSourceFields` 把它报成缺失,而不是补上。

- **指标只声明一次,与声明不一致的研究跑不起来**(2026-09-17):`runner/metrics.ts` 持有 `METRIC_REGISTRY` —— 每个量一条 `MetricDefinition`,写明它的 key、单位、哪个方向更好、一次变化**意味着什么**、以及它属于哪些研究类型 —— `checkMetricDeclaration` 对每处不一致返回一条拒绝(`metric-unknown`、`metric-unit-mismatch`、`metric-direction-mismatch`),并把两侧都写出来。**单位只比较、从不换算**:一个用毫秒报告 `min-ttc-seconds` 的研究,测的是一个与本部署里任何东西都无法比较的量。`requireMetricDeclaration(MEASURED_METRIC)` 在 `driveOptions` 里被调用 —— 那是 `startRun` 与 `runPipeline` 唯一共同解析配置的地方 —— 于是一个漂移过的研究**在运行存在之前**就被拒绝:把研究的单位改成 `ms`,`tests/start-run.spec.ts` 里二十四个测试就会带着那条拒绝失败,接线就是这么核对的。`metricsFor(type)` 把 REQUIRED 与 NOT-APPLICABLE 分开,而包清单的 `declaredMetrics` 逐条写明每个指标的 key、单位、方向、含义,以及运行自己的类型是否要求它 —— 从运行冻结的 spec 里读出,而不是在导出时现查。**这里没有的**:没有任何东西在写句子的时候读那条「含义」。质量基线的方向词检查只读测量的符号,读方向的是它的**褒贬**分支(「an improvement」)—— 一个不含褒贬词的稿件只按符号判定,所以出货运行自己的文字从没走到那一支。
- **一次运行在它自己冻结的研究画像下进行,重新配置也移不动它**(2026-09-17):`runner/research-profile.ts` 把此前混在一起的两件事分开 —— 研究**类型**(`simulation-study` | `literature-review`)决定一项研究到底有那些指标,期刊画像则陈述某家期刊对文档的要求。**没人读过的规则不算规则**:每条 `JournalRule` 都带着它来自哪里(`source`),没有 source 的会被 `resolveResearchProfile` 拒绝,因为没人读过的规则是猜测,而猜测不得被施加到每一份稿件上。因此 `TRC_PROFILE` **一条规则都不带** —— 作者指南从未取得,空列表说的就是这个事实,而填上内容就等于凭空发明(`../project-plan/architecture-review-2026-09-15/TRC-PROFILE-SPEC-CHECKLIST-2026-09-17.md` 逐条记录了未核验的规格)。解析发生在运行开始时 —— 未知的研究类型在那里就被拒绝,而不是在恰好读到它的那一步 —— 而 `runSpecOf` 把解析出的画像冻结进运行的 spec,于是在同一个快照目录上以**另一种**研究类型重启的部署,改不动一次运行已经记下的画像。**客户端说不上话**:类型与期刊都从部署自己的引擎上读取,与证据 profile 一样,因为一个浏览器可达、又接受类型参数的入口,会让调用者改变自己的稿件按哪套指标评判。

- **包会说明自己是最终包还是工作草稿,而最终包是可以被拒绝的**(2026-09-17):`planRunPackage` 从运行自己的记录里算出九个条件 —— production 证据 profile、稿件已产出、每一步都已收束、没有被拒绝书写的章节、没有悬而未决的意见、人工门上有一条批准、这条批准仍然覆盖运行当前持有的那些产物、稿件声明的每个文件都在包里、以及运行最后一次写入已落盘 —— manifest 带着由此得到的 `state`(全部成立才是 `final`)、这些检查本身、以及那条批准与它当时所依据的产物版本。**驱动结束时写出的那一份,按构造就是草稿**:到达人工门的运行就停在那里,于是当时写下的 manifest 记的是 `E2-submit: gated`,而随后作出的批准从未到达它 —— 页面若把那份文件当作最终包提供,提供的就是决定之前的那个状态。`@Remote('exportRunPackage')` 按需写出包,并**在操作里**拒绝最终包:点名第一条不成立的条件,而且什么都不写 —— 一个在退出路上清空目录的拒绝,会连读者手上的草稿一起拿走。草稿照写,并说明自己是什么(manifest 的 `state`、那些检查、以及它自己的 `run-summary.md`),因为想拿到当前材料的人应该拿到它、带着标注,而不是收到一个对谁都没帮助的拒绝。
- **上一次进程留下的研究,先被取回,才能被裁决**(2026-09-17):`@Remote('openStoredRun')` 把一份存量运行读进本进程,**什么都不驱动** —— 快照进内存、运行登记到审批通道、报成 `stopped`。**它存在的原因是:对本进程不持有的运行的审批会被拒绝**(决定必须写进运行的状态),于是"到达闸门并熬过重启"的研究成了找得到、读得到、却裁决不了的东西;`resumeRunPipeline` 也不是入口 —— 它从第一个非终态步骤驱动,而每一步都已尘埃落定的运行没有可恢复的。**取回两次会被拒绝**(第二次会用磁盘上的拷贝替换读者正在看的状态),部署不持有的运行会被拒绝而不是被凭空造出,而最后一次写入失败的运行**保留**那个事实 —— 打开一次运行不是一次写入,清不掉它。被取回的运行经与其他写入相同的串行写入器写入。
- **每一次写入都以「上一次真正落盘的写入」所推进的版本为基准**(2026-09-17):审批会写运行快照,而下一次写入的基准是 `active.savedRevision` —— `persistRun` 现在把自己的结果记进这个字段,检查点的回调把它的版本记进这个字段,取回存量运行时也用读到的那份快照为它赋初值。**这是从浏览器里发现、也只有从浏览器里能发现的**:跟在修改请求之后的那次接受被拒绝 —— "the persisted snapshot is at revision 25 but this write is based on revision 24" —— 因为审批的那次写入把文件推进了,而没有任何东西告诉进程。接受记录写下了、它的 `persisted` 带着这条原因报成 false,而它发布的稿件从未进到文件里:页面显示着一份稿件,而重启之后会显示 E1 那一份。**把基准改读「上一次写入的记录」会从另一侧重新引入同一个裂缝** —— 检查点推进文件时不经过 `persistRun`,所以那条记录描述的是其中一条路径的写入,对另一条一无所知。
- **候选稿写在部署自己铸造的 id 之下**(2026-09-17):`generateCandidate` **不读**调用者送来的 `candidateId` —— 页面此时还没有可命名的候选稿,送的是空字符串 —— 而 `buildCandidate` 在没有拿到 id 时自己铸一个。**此后每一次读取都走这个 id**:记录文件以它命名、复核按它查找、接受要命名它、页面的每个控件都钉在它上面。若照抄调用者的值,每个请求的每份候选稿都共用 id `''`:每个请求一个 `candidate-.json`、第二份候选稿覆盖第一份、`review-.json` 指的是最后被复核的那一份,而页面上接受与复核按钮全都指着同一个候选稿。**这是浏览器探针发现的,不是单元测试发现的**:探针用候选稿 id 钉住自己的点击,空 id 让它点到了另一个请求的控件,而读数看起来是通过。
- **被复核过的候选稿可以被发布为稿件,而这是它自己的操作**(2026-09-17):`@Remote('acceptCandidate')` 把候选稿的章节组装到这次运行持有的稿件之上,交给核心的 `acceptManuscriptCandidate`:它经登记表写入一个新的稿件版本、推进项目版本,并记录被它替换掉的那一版。**这不是一次步骤提交**:E1-format 在任何人读到论文之前就提交了,所以它带着自己的守卫 —— 调用者所述之外的运行版本、当前版本不是候选稿依据的稿件、没有复核、复核的是另一版、复核未通过、无法规范编码的值 —— 以及一个写着**人**(`human-acceptance`)而不是执行器的生产者。**调用者命名请求与候选稿,从不递文档**:值在这里组装,并保留 E1 工件的其余每个字段。检查只有一处,所以页面在提供控件之前做的那次读取,不可能与拒绝它的操作发生漂移。
- **修改请求由候选稿回答,而候选稿先被检查再被相信**(2026-09-17):审批端点接受一个 `onDecided` hook,服务用它 —— 一条已生效的 `request_changes` 决定会在 `<snapshotDirectory>/revisions/<requestId>/` 下记录一条 `RevisionRequestRecord`,列出稿件的每个章节及其当时的正文哈希,以及这条要求针对哪些章节。**候选稿是**对着请求读到的那个版本**写的**:基准在写入时重新读出,移动过的稿件会被拒绝;请求指向已消失的章节、写作者什么都没写,同样被拒绝。**写作者是部署自己的 prose 通道**(D3/D4 写作时用的那道缝),写出候选稿的通道会被记在候选稿上。**检查读的是这次运行,不是被测文本**:被改动章节的数字必须是这次运行声明过或测量到的,引用标号必须在参考文献表里,候选稿的章节必须与稿件完全一致;复核绑定在候选稿自己的哈希上。`@Remote('listRevisions' | 'requestRevision' | 'generateCandidate' | 'reviewCandidate')` 暴露这个闭环。**这里没有的**:接受。把候选稿变成正式稿件需要模块设计里描述的那次接受事务(版本比对、引用校验、对登记表的原子写入、下游失效),在它存在之前,一份被复核过的候选稿无法成为稿件。
- **修改请求是一个决定,而且它把闸门留在原处**(2026-09-17):`submitApproval` 在 `approved` 与 `rejected` 之外接受 `request_changes`,带上调用者写明的要求,并用**后端记录的那个决定**加上重新投影的运行作答。核心把它记进运行自己的审批记录与 `human-approval` 事件,冻结在当时呈现在人面前的那些产物引用上,而该步骤**保持** `gated` —— 人要的是不一样的工作,不是让研究停下。**什么都没写的请求会在两道边界上被拒绝**(通道的读取器与核心),而拒绝把闸门留在原处。回执陈述的是后端记录的决定,而不是从步骤状态推导出来的值,因为 `gated` 既是"已被要求修改"的步骤的状态,也是"没人看过"的步骤的状态。
- **研究靠一次部署读取被找到,而不是靠页面记住了什么** (2026-09-17):`@Remote('listRuns')` 回答这个部署持有哪些研究,最新的在前 —— 这就是让一项研究在启动它的标签页消失之后仍能被够到的读取,因为 run id 留在那个标签页的存储里,而快照一直在盘上。**本进程持有的运行从它的活状态报告;本进程不持有的运行从它的文件读出**并报 `stopped`,同时带着快照被取走时正在飞行中的步骤,所以中断的研究与跑完的研究分得开。同一项研究即使在两处都存在也只出现一次,因为活状态就是它自己的读者看到的那个状态。**顺序是 id 的顺序,不是版本的顺序**:版本数的是**一项**研究提交了什么,无法把两项研究相互排序,而 id 是 UUID,在多次调用、多个进程之间排序稳定。每条记录带着执行状态、项目版本、编目的 `stepsTotal` 里过了几步 `stepsPassed`、`submissionReady`,以及读者据以行动的两条失败事实(`saveFailure`、`executionError`)。**读不到的列表是拒绝**,不是空列表:"这个部署没有任何研究"与"我问不出来"有不同的补救办法,而其中一个不是"你的工作没了"。**浏览器只有在 Remote assembly bundle 带着这个方法时才够得到它** —— `dsh-api-remotes/lib/client.js` 把各包生成的描述符内联进来,所以新增一个 `@Remote` 方法要在生成器重写描述符之后重建 client face;先打包的构建会让页面去调用一个在别处都存在的方法,而页面把它报成 `listRuns is not a function`。
- **没落盘的保存可以重试,而且重试不是重跑** (2026-09-16):`@Remote('retryRunSave')` 把**本进程持有的**一次运行的当前状态再写一遍到它的快照。这是部署的写入路径失败又恢复之后,人真正需要的那条补救:没有它,想让一次运行回到盘上就只能把研究再做一遍 —— 那要花掉两倍的模型调用,还会在同一名字下产出不同的数字。它与磁盘**对账**而不是相信记住的数字(基准版本从磁盘当下的状态读出),并且只推进**快照的写入计数**,绝不推进运行的 `projectRevision`(把同一份状态再写一遍没有提交任何东西),所以重试之前做出的决定仍然命名着一个当前版本。**本进程不持有的运行会被拒绝**:从文件读回来的运行已经处于它文件记录的状态,再写一遍没有磁盘上还没有的内容。客户端在**后端自己报出** `saveFailure` 时提供这个重试,并渲染重试回答的那份运行 —— 于是决定所需的版本正是页面重新读到的那个。
- **没落盘的保存会成为运行的状态,并同时拒绝就绪与裁决** (2026-09-16):这次失败此前只活在 `RunResult.checkpointErrors` 里,而一次**正在运行**的运行还没产出它 —— 于是页面显示一项研究在推进,却对"这些成果没有落到盘上"一字不提。现在它是 `ActiveRun.checkpointError`,作为该运行持久化记录的 `error` 报出(就在**不再前进的 `revision`** 旁边),并由下一次落盘的写入**清除**。`submissionReady` 与就绪说明读的是**同一条记录**,经由投影渲染它的那一个访问器(`livePersistence`)—— 读两次可能对同一个问题给出不同答案,让页面在一个谁都存不下去的运行上说"就绪"。**审批也被它拒绝,且是在做出任何决定之前**(`research/approval-save-failed`):`submitApproval` 与其他前置条件 —— 运行、步骤、`humanGate`、当前状态、当前 attempt、期望版本 —— 并列地读这次运行最后一次落盘的写入,因为事后报 `persisted: false` 已经太晚:闸门在内存里已经走到 `passed`,而快照仍说 `gated`,于是重启后系统请人批准一件他已经批准过的事,而调用者只被告知自己的决定不持久,却无从补救。拒绝里带着部署自己的原因,并且 `RememberedRun` 新增了 `saveState`(与 `persist` 一同变为必填),让一个能写决定的调用者无法忘记说明"这次运行是否在盘上"。**补救与它的边界**:拒绝不会被记住,所以运行的下一次写入落地后,同一条命令就能被裁决 —— 那是运行仍在被驱动期间的一个检查点。**驱动一旦停止,本进程内就没有任何东西再写这次运行**,所以**最后一次**写入失败的运行会一直被拒,直到它被重新驱动;拒绝里说明了这一点,而那个重新驱动的操作属于断线恢复那一项工作,不在这里。

- **启动命令要么可被找回,要么就谈不上幂等** (2026-09-16):`StartCommandRecord` 以"写临时文件再改名"的方式写进 `<snapshotDirectory>/commands/<commandId>.json`,而"进行中"的答案在任何 `await` 之前同步登记 —— 所以同时到达的两次调用只产生**一次**运行(映射此前是在保存之后才写的,两边都可能错过它),重启后的重试由记录回答,而不是再起一项研究。**记录先于它所命名的运行落盘**,这正是关掉两者之间那个窗口的顺序:反过来写时,进程死在"运行的首次保存"与"记录那一次写入"之间,会留下一项没有任何东西命名的研究,而重试因为找不到记录,会再起**第二项**。先写记录,重试就总有东西可查,窗口能造成的代价只剩"这个命令 id 要换一个":记录在而运行不在时会被如实报出(`persisted: false` 并指出缺失的运行),而不是重跑 —— 已经开始的 研究可能已经产出了东西,再起一项不是查明的方式。这个顺序的代价在失败路径上偿付:一次没有发生的启动会把它写的记录**从它写的位置**删掉,于是该 id 仍可重试;若这次删除本身失败,记录会留下,那是安全的方向 —— 重试被拒绝,而不是重复。携带**不同**研究的命令 id 会被摘要比较拒绝,无法命名文件的 id 被**拒绝而不是净化**(净化后的 id 是另一个 id,下一次重试找不到它)。**记录写不出来的启动会失败** —— 一条谁也查不到的命令比没跑过更糟。**尚未做的**:`startCommands` 没有淘汰,启动很多运行的部署会让这个映射在进程存活期间持续增长。

- **cursor 命名的是一个**历史**里的位置,而不只是一个运行里的位置** (2026-09-16):从检查点恢复的运行保留那次检查点保存的事件,并在丢失的尾巴原本占用的下标上追加**新**事件 —— 于是读者已经消费过的位置在这里可能放着不同的事件,而从这个位置继续,等于让一个从未见过"替代物"的读者接着往下走。cursor 现在是 `<runId>#<已消费数>#<digest>`,digest 是该位置以下事件的一条链(每个事件的指纹折进前一个 digest,并且按**固定字段顺序**折,好让一次重启不会看起来像另一个历史)。digest 与所呈现日志不符的 cursor 会被带原因的 `resync` 帧拒绝,读者重新读取。**位置是"已消费的数量",不是"最后看到的下标"**:事件信封现在同时携带 `cursor`(该事件**之后**的位置)与 `eventId`,于是中途重连的页面不会再收到它已经应用过的事件(旧写法把页面持有的位置设成事件自己的下标,等于又点了一次它)。**控制更新也是帧**:运行的保存健康与执行归属会在**没有任何事件被追加**的情况下变化 —— 检查点失败、驱动停止 —— 现在任一变化都会发出一帧快照;它在开场帧处就被读取(生成器是在第一次 `yield` **之后**才执行初始化语句的,所以一个只听说过追加事件的读者,在运行停在人工门期间保存坏掉时会一无所知)。慢读者不会被缓冲:async generator 只在消费者索取下一帧时才产出,订阅由它自己的 `AbortSignal` 取消。
- **运行改为通过一条流、按 cursor 跟随,而不是轮询** (2026-09-16):`@Remote({ mode: 'stream' }) followRun({ runId, cursor? })` 产出开场的一帧 `snapshot`、每个新追加事件一帧 `event`,以及在没有东西再驱动这次运行时的一帧收尾 `snapshot`。**cursor 是事件的下标**,以 `<runId>#<sequence>` 的形式限定到它所属的运行:运行的审计事件没有序号字段,而 `ts` 是两条事件可能共用的毫秒值,所以下标是它唯一严格单调的键 —— 而日志只会被 push,所以一个下标终生命名同一个事件。**开场的 cursor 与它的快照是同一次读取**,这正是"快照与订阅之间没有缺口"由构造成立的原因:那份快照已包含位于它及之前的每一个事件的效果,重连的读者拿到的是已经包含所错过内容的状态。来自别的运行的 cursor、或日志从未到达过的位置,会被带原因的 `resync` 帧拒绝,而不是被读成别的历史里的位置。**这条流只读** —— 版本敏感的命令留在经过认证的 unary 通道上 —— 且**信封不携带 `detail`**,因为 typert 生成器拒绝线上边界上的裸 `unknown`(第一次构建就被它拦下)。
- **研究可以在运行中被启动和读取,重启后还能找到它** (2026-09-16):`@Remote('startRun')` 创建一次运行、把它写到磁盘、返回它的 id,并在本服务的后台驱动它;`@Remote('runSnapshot')` 读取这次运行的当前状态。在此之前唯一的入口是 `@Remote('run')`,它要等整项研究结束才返回 —— 于是按下按钮的人几分钟内什么都看不到,刷新页面就丢掉了手里唯一的把手,而视图是由 `RunResult` 构建的,那个值在运行结束前根本不存在。**`RunResult` 仍然是驱动调用的结果**;改变的是:回答"这次运行在做什么"不再需要它。`runner/project-view.ts` 读取这次运行**自己的记录** —— 步骤状态、工件登记表、`step-executed` 记录 —— 并投影出目录里的每一个步骤,所以尚未执行的步骤报 `pending` 且 attempt 为 0,既不会缺席,也不会被默认成一个成功。**快照带有 `execution`**,它是关于**本进程**的事实:`running` 表示此刻这里有执行器在驱动它,而且这个值绝不会从一个已经消失的进程写下的记录里读回来。因此重启后的查询会从检查点恢复这次运行并报 `stopped`,同时列出当时在飞行中的步骤 —— 对读者会失去什么保持诚实,而不是给出一个陈旧的 `running`。**抛异常的执行器在运行层报告**(`execution: 'failed'` 加 `executionError`),因为按步骤的记录只能说明研究走到了哪里,说不出"本来要继续它的东西已经不在了"。**重试的命令读到第一次发送产生的答案**:`commandId` 命名的是命令,所以没读到响应的客户端重发同一个 id 时,拿到的是它已经启动的那次运行,而不是再花掉一项研究。**无法把运行记录下来的启动会被拒绝** —— id 在驱动开始之前写入磁盘,所以快照目录不可用的部署拿到的是错误,而不是一个它守不住的"成功"。`runPipeline` 也补上了 `checkpointAfterStep`,这本该在检查点落地时就有的:异步启动的运行此前只在结束时才保存。
- **研究报告它进行得怎么样,而不只是结果如何** (2026-09-16):客户端的运行控件启动运行、读取它、跟随它,每读到一份快照就渲染一次;工作台在就绪徽章旁标出运行 id 与执行状态。**这个跟随循环是页面对于研究的兴趣,不是研究本身**:执行器由本服务持有,所以关掉页面不会取消运行,回来的客户端读到的是同一次运行。**传输原本是客户端固定间隔的轮询,现在改为运行自己的事件流**(`followToRest` 走 `@Remote({ mode: 'stream' }) followRun`,带 cursor、去重,并在 cursor 被拒时重开 —— 见下面那一条,那一半记录在那里)。**尚不存在的部分**:客户端读取失败会抛错退出跟随循环,所以"页面不再跟随"与"运行已停止"是读者必须自行从消息里分辨的两件事;另外 `runSnapshot` 每次调用都读这次运行的记录,所以很长的运行其轮询会重新投影整次运行,而不是读增量。
- **批准绑的是读者看过的那个版本,而它过去绑的是当下的版本**(2026-09-16):`ApprovalSubmission.expectedProjectRevision` 是必填的,而 `submitApproval` 会拒绝任何不是运行当前版本的决定 —— 于是一个在读者眼皮底下移动过的页面(第二个标签页、落了地的步骤、一次恢复)无法把决定记在一份没人读过的文档上。拒绝里同时点名两个版本,并说明要重新读。**客户端那一半**:一个说不出自己版本的页面**根本不提供**裁决按钮。与 `approvalStalenessOf` 合起来 —— 后者在决定**之后**抓同一个错配 —— 版本在决定那一刻的两侧都被绑住。
- **导出 manifest 说出它读的是哪个项目版本**(2026-09-16):`RunPackageManifest.projectRevision` 从运行读出,不由文件推导,于是比较两个包的读者 —— 或者拿一个包去对照某个屏幕的人 —— 能分辨它们是不是这份研究的同一个状态。`generatedAt` 说的是有人什么时候读的,那不是同一件事:相隔一分钟的两次导出可以装着不同的手稿。
- **修订留下的未关闭意见现在会挡住就绪**(2026-09-16):`openIssuesOf` 读 `rebuttal` 工件里逐条 issue 的结局,`submissionReadinessOf` 对仍然带着一条的运行拒绝就绪,并点名那条 issue、它所在的节、以及应用器给出的原因。一轮修订会记下它提出的每一条意见变成了什么;被留成 `open` 的那些,是因为补丁是针对另一个版本写的、什么都没改、或与同一节的另一份补丁冲突 —— 每一条都是评审者提过、而论文没有回答的东西,所以一次门禁全关、也有人批准过的运行**仍然不就绪**。**在这之前,这份清单被写进产物,却没有人读**:它不阻止 `D4-rebuttal` 步进,也完全没有进入就绪判定。**仍然缺的**:没有轮次计数、没有预算,所以「两轮同样的失败转人决」没有东西可数 —— `D4` 只跑一轮,一次拒绝是被报告,而不是被重试。
- **目标期刊的要求是一条记录,而 TRC 的指南已在 2026-09-18 被读过**(2026-09-18):此前每一条发布条件问的都是**论文**是否完成,没有一条问它是不是**期刊**会收的那份文档。官方正文由用户于 2026-09-18 取得 —— 本机抓取器三次都拿到 HTTP 403 —— 连同来源、日期与 SHA-256 保存在 `plan/venue/trc-guide-for-authors.md`;从中记录九条要求,每条引用官方页面、日期、文章类型与指南里的标题。主要发现:**摘要不得超过 250 词**、**highlights 是必需的,3 到 5 条、每条至多 85 字符**、**引文风格由期刊在 proof 阶段套用**而不是要求作者套用、**必须提供 Word(.docx)或 LaTeX 源文件,PDF 不合格**、以及**审稿是单盲 —— 作者留在标题页上,所以把稿件匿名化才是错误而不是要求**。指南被读过而确实没有规定的事项记为 `not_specified`,那是发现而不是缺口;只有 `unknown` 才阻断。`JournalRule` 携带一条要求必须写明的东西 —— 它写在哪个官方页面、那个页面何时被读过、适用于哪种文章类型、是否已核实,以及条件或这次尝试得到的结果 —— 由 `runner/venue-rules.ts` 判定:`checkVenueRules` 在画像里有任一未读规则时拒绝投稿,也把没有规则的画像按「未读的指南」拒绝。`unreadRulesFor` 仍产出那个状态 —— 那是没人查过的期刊的样子:`abstract-length`、`highlights`、`graphical-abstract`、`reference-style`、`figures-and-tables`、`manuscript-file`、`declarations`、`anonymity`。**实测,2026-09-18**:TRC 的三个官方页面 —— ScienceDirect 的 `…/publish/guide-for-authors` 与 `…/about/author-information`,以及 Elsevier 的 `…/journals/…/guide-for-authors` —— 都返回 HTTP 403 与一个 JavaScript 挑战页(1.2 MB),而不是指南本身;这就是出货规则是 `unknown` 而不是被填上的原因。画像经由 `resolveResearchProfile({ journal })` 冻结进运行的 spec;导出从那里读,而不是自己重述它想据以发布的规则。`checkFinalPackage` 新增 `journal-rules-verified`;E1 的 `venueStyle` 不再写 `<name> template` —— 那是在点名一份没有任何运行读过的模板,而编译器应用的是 pandoc 默认。

- **就绪只有一个含义,而且只在一个地方评估**(2026-09-18):`submission-readiness.ts` 与 `final-package.ts` 各自决定一次运行的产出是否可发布,各用一份自己的条件表 —— 其中六条被写了两遍,而 2026-09-18 的复核找到了二者矛盾的例子:一次运行的修订被答复了却没人读过,它在清单里满足就绪(`submissionReady: true`),而导出以 `review-complete` 拒绝了它。现在 `checkManuscript` 就是稿件的就绪、也是它唯一的定义 —— 关于论文的那七条(profile 合格、稿件存在、每一步都关闭、没有小节因缺证据被拒、没有意见仍未关、批准未过期、编译出的文档带着每一个 float、审阅已完成)—— 而 `submissionReadinessOf` 原样报出第一条未满足条件自己的话。`checkFinalPackage` 在其上追加关于**交付**的六条(批准已有记录、包带着稿件声明的文件、包带着编译产出的那些**文档** —— `.docx` 是字节,不在任何声明的文本文件里,而 `manuscript.md` 无论编译成功与否都在包里 —— 包描述的是运行当前所处的状态、该状态已落盘),并通过一张显式声明的顺序表拼起两组,所以先被点名的条件与原来完全一致。`manuscriptFactsOf` 为两者只采集一次事实,顺带修掉一个字段名:在工件写 `floatsDropped` 的地方去读 `dropped`,会让这个列表永远是空的。

- **就绪判定会拒绝一次批准已过期的运行**(2026-09-16):`readinessOfRun` 对每一步向 core 的 `approvalStalenessOf` 提问,把第一个答案交给 `submissionReadinessOf`,后者把它变成一条点名「哪个版本移动了」的拒绝。批准覆盖的是摆在本人面前的那份文档;一份离开了那个版本的手稿 —— 后面的步骤、从另一份快照恢复、或者一只手 —— 没有被批准过,而这个状态下的运行不就绪。**这不覆盖的东西**:导出的包**文件**。导出之后在磁盘上编辑 `manuscript.md` 在运行的 registry 之外,这里看不到;manifest 里逐文件的 `sha256` 才是读者拿来核对它的东西。
- **浏览器那条循环闭合了**(2026-09-16):端到端探针在 `cdf9e69f` 上报 **41/41**。一次经由出货应用驱动的运行把十六步带到 `E2-submit`,操作者通过页面批准、后端记下了这次批准(`{"a2":"passed","e2":"gated","steps":16}` 然后是 `{"e2":"passed"}`),而导出的包引用了 25 条来自实时目录的真实 DOI —— 没有一条是合成锚。它的手稿由部署配置的模型路由写出,并通过了四条检查的对抗性阅读。**它试了五次** —— 四次停在进程内套件从未看见的缺陷上,一次停在目录故障上 —— 那些缺陷记在 `../.agents/notes/implemented/testing/2026-09-16-what-the-browser-found.md`。**探针按交付跑,不按提交跑**:一次循环 = 两个面的完整构建 + 一次 profile 安装刷新 + 一个启动的应用 + 一个 Chrome 实例 + 最多二十分钟的实时模型。
- **闭环在 production profile 上跑通**(2026-09-16):`tests/e2e/closed-loop.spec.ts` 一次断言整条链,因为"每一部分各自通过"正是**断掉的循环**从内部看起来的样子。一次 production 运行凭复核过的文献跑完十五步到 `E2-submit`,写出一份各节都记录了"它从哪条证据写出"的手稿,在读到一个人为注入的、运行从未测过的数字的那道门**停下**,用审过 draft 的同一套检查复审修订稿,并在有人批准之前一直报 `profileEligible: true` / `submissionReady: false`。被证伪的预测会让运行正常完成 —— `mvp-results.outcome` 是 `refuted` 且 `decisive: true`,这是两件不同的事实 —— 因为一条只在正面结果上完成的流水线,是在制造正面结果。**这不是什么**:不是一次批准。`readinessOfRun` 说的是材料存在、门禁关闭;包由人在 E2 批准,而 `evaluation` 永远不就绪。
- **修订要么是一次 diff,要么什么都不是**(2026-09-16):`runner/issue-patch.ts` 装着 Issue → Patch → Verify 这条循环。一条 issue 具名一个节、以及它是针对哪一个版本写的(`basisHash`,由作者被展示的那份正文算出);一份 patch 是一段替换正文。只有当基准仍是当前的、且结果与它不同时才会被应用 —— 于是 `revised` 是"正文**变过**的那些节"的性质,由正文派生,绝不由调用方断言。针对过期版本写的 patch 会被拒而不是被应用(应用它会静默丢掉中间发生的一切);同一节的两份 patch 是冲突而不是合并。不改变正文的回答是 `accepted_explanation`,与 patch 分开记录。`D4-rebuttal` 读 `CONCERN`/`SECTION`/`RESPONSE`/`PATCH` 行,并把 `issues`、`changes`、`patchedSections`、`openIssues` 写进 rebuttal 与 revised draft。**在这之前**每一节都被映射成 `{ ...section, revised: record.hasRevisions }`,于是一条意见把整份手稿标成已修订而没有任何正文改变。**模型那条路已被驱动,而畸形的回复被拒绝**(2026-09-16):`tests/d4-model-revision.spec.ts` 让 D3 与 D4 穿过一个按各步自己的格式作答的写作者,于是解析器读到的是模型会产出的那种回复 —— 浏览器那次运行自己的三段交换就是那份 fixture。`runner/issue-parse.ts` 分清三种意图:一段替换正文、`PATCH: NONE`(作者把这条意见接受为解释)、以及**缺少** `PATCH` 行。第三种曾经与第二种是同一个值,于是一份只是没按格式作答的回复被记成 `accepted_explanation`,该步通过。省略标签的交换现在按编号与所缺标签被报告,`assertWellFormed` 把这份报告变成一次失败的步骤,而不是在空无之上关闭一条 issue。**解析器只认这一种带标签的格式**:用散文作答的回复被拒,不会被解释。
- **重复的批准命令被回答,而不是被重新裁决**(2026-09-16):`ApprovalSubmission` 带 `commandId`,而 `submitApproval` 对重复的 id 回答**第一次发送产生的结果**。一个从没读到第一个答案的调用方 —— 超时、刷新、再点一次那个看起来没反应的按钮 —— 过去会撞上 `not-pending`,一句它无法与「我的决定根本没落地」区分开的拒绝。**不同的 id 是不同的意图**,它撞上的是第一条命令产生的状态,所以这本台账回答重试,却不是绕过门的办法。**拒绝不被记住**:缓存一次拒绝,会让因为暂时性原因失败的命令在那个 id 下被永久拒绝。**台账在内存里**:跨重启之后,重试的命令会再次撞上 `not-pending` —— 这是安全的(它无法裁决两次),但不幂等,这条边界写在这里,而不是交给一个这一层并不拥有的持久表。
- **一次修订是一条有界的循环,不是单轮**(2026-09-16):`D4-rebuttal` 过去只跑一次,`roundId` 硬编码成 `t19s-rebuttal-1`,应用器拒绝一份补丁之后没有东西可以再试。现在它会再问 —— 最多 `revisionRounds` 轮(部署配置,默认 2)—— 每一轮都被告知上一轮留下的是**哪些节**,并拿到当前这份手稿。工件带上 `rounds`、`revisionRounds` 与 `stoppedBecause`。**「无进展」按节比较,不按 issue id**:每一轮都从 1 开始编号,比较 id 会把两轮在同样几节上失败叫作"有进展",然后把预算花在重复提问上。**它不做的事**:循环停下时仍未关闭的意见不会变成人工决定 —— 它挡住就绪、工件写明原因。
- **没有运行的必需检查会挡住 A 门**(2026-09-16):`checkDispositionOf` 把每条 review 映射成一条门禁检查,`verdictA` 按该轮声明的角色聚合它们,于是一个 `judgeRound` 单独会放过的步骤,在一条必需检查**从未报告**时被挡住。**跑过并判定材料不足的检查不属于这一类**:弃权是一条发现,`not_evaluated` 才是沉默,而聚合只挡第二种。可达的情形是「该检查的必需输入不存在」—— 运行里没有结果记录时,`red-stat` 与 `red-claim` 报 `evaluated: false`,因为它们什么都没核验。**在这之前这个区分根本不存在**:一条跑不成的检查报的是 `abstain`,与「读了材料、判定它不足以裁决」是同一个值,于是「什么都没核验」无从被拒绝。
- **A 门禁审的是手稿,不是 claim 材料**(2026-09-16):当这次运行已经产出稿子时,`verdictA` 读 `draft` / `revised-draft` 并审**它** —— `runner/manuscript-review.ts` 拿正文里的数字对照运行的测量记录、拿方法一节对照真正执行的那个实现、拿图表与文献引用对照 draft 自己的名册、拿结论的方向对照测量的符号。在这之前它调的是 `reviewClaim(runCtx.claimMaterial)`,无论那一步写了什么,于是一个离线探针可以改掉正文里的一个数字、删掉方法一节、跳过修订,而 A 的票不动。在还没有手稿时就由 A 把关的步骤(A2、A3、B1、D2)仍然审 claim 材料,而判定的 evidence 会写明读的是两者中的哪一个。**这些检查只找四件事,不多**:一个没有任何东西测量过的数字、一节没人写过的正文、一个指向空处的引用、以及一个被它自己的证据否掉的结论。一篇论文好不好,需要一个读者,而本仓库不会把规则的输出报告成读者的意见。
