# @deepseek-ai/dsh-research-team

[English](README.md) | 中文

`ctx.agentTeams` 服务与 T19-B 运行器:红队舰队、带 CAS 修订的任务板、写入范围守卫、会话投影,以及把 16 步驱动起来的执行器注册表(`runner/`)。

分层是显式的:纯逻辑层(`types` / `revision` / `projection` / `scope-guard` / `roster` / `redteam` / `anchor` / `experiment`)→ 薄适配层(`journal` / `task-board` / `session-events` / `research-projection` / `research-guard`)→ `index.ts` 这一个接线点(服务声明、`SessionEventMap` 注入、`ctx.effect` 生命周期)。

`runner/registry.ts` 是 16 步执行器的审计真源:每个条目声明 `stepId` / `executor` / `producer` / `truthfulness` / `timeoutMs` / `gateRequirement` / `recoveryPolicy`,且输入输出 schema 与闸门要求都从 core 的冻结定义派生,以防与 16 步定义漂移。

## 已知限制与延期工作

- **就绪判定会拒绝一次批准已过期的运行**(2026-09-16):`readinessOfRun` 对每一步向 core 的 `approvalStalenessOf` 提问,把第一个答案交给 `submissionReadinessOf`,后者把它变成一条点名「哪个版本移动了」的拒绝。批准覆盖的是摆在本人面前的那份文档;一份离开了那个版本的手稿 —— 后面的步骤、从另一份快照恢复、或者一只手 —— 没有被批准过,而这个状态下的运行不就绪。**这不覆盖的东西**:导出的包**文件**。导出之后在磁盘上编辑 `manuscript.md` 在运行的 registry 之外,这里看不到;manifest 里逐文件的 `sha256` 才是读者拿来核对它的东西。
- **浏览器那条循环闭合了**(2026-09-16):端到端探针在 `cdf9e69f` 上报 **41/41**。一次经由出货应用驱动的运行把十六步带到 `E2-submit`,操作者通过页面批准、后端记下了这次批准(`{"a2":"passed","e2":"gated","steps":16}` 然后是 `{"e2":"passed"}`),而导出的包引用了 25 条来自实时目录的真实 DOI —— 没有一条是合成锚。它的手稿由部署配置的模型路由写出,并通过了四条检查的对抗性阅读。**它试了五次** —— 四次停在进程内套件从未看见的缺陷上,一次停在目录故障上 —— 那些缺陷记在 `../.agents/notes/implemented/testing/2026-09-16-what-the-browser-found.md`。**探针按交付跑,不按提交跑**:一次循环 = 两个面的完整构建 + 一次 profile 安装刷新 + 一个启动的应用 + 一个 Chrome 实例 + 最多二十分钟的实时模型。
- **闭环在 production profile 上跑通**(2026-09-16):`tests/e2e/closed-loop.spec.ts` 一次断言整条链,因为"每一部分各自通过"正是**断掉的循环**从内部看起来的样子。一次 production 运行凭复核过的文献跑完十五步到 `E2-submit`,写出一份各节都记录了"它从哪条证据写出"的手稿,在读到一个人为注入的、运行从未测过的数字的那道门**停下**,用审过 draft 的同一套检查复审修订稿,并在有人批准之前一直报 `profileEligible: true` / `submissionReady: false`。被证伪的预测会让运行正常完成 —— `mvp-results.outcome` 是 `refuted` 且 `decisive: true`,这是两件不同的事实 —— 因为一条只在正面结果上完成的流水线,是在制造正面结果。**这不是什么**:不是一次批准。`readinessOfRun` 说的是材料存在、门禁关闭;包由人在 E2 批准,而 `evaluation` 永远不就绪。
- **修订要么是一次 diff,要么什么都不是**(2026-09-16):`runner/issue-patch.ts` 装着 Issue → Patch → Verify 这条循环。一条 issue 具名一个节、以及它是针对哪一个版本写的(`basisHash`,由作者被展示的那份正文算出);一份 patch 是一段替换正文。只有当基准仍是当前的、且结果与它不同时才会被应用 —— 于是 `revised` 是"正文**变过**的那些节"的性质,由正文派生,绝不由调用方断言。针对过期版本写的 patch 会被拒而不是被应用(应用它会静默丢掉中间发生的一切);同一节的两份 patch 是冲突而不是合并。不改变正文的回答是 `accepted_explanation`,与 patch 分开记录。`D4-rebuttal` 读 `CONCERN`/`SECTION`/`RESPONSE`/`PATCH` 行,并把 `issues`、`changes`、`patchedSections`、`openIssues` 写进 rebuttal 与 revised draft。**在这之前**每一节都被映射成 `{ ...section, revised: record.hasRevisions }`,于是一条意见把整份手稿标成已修订而没有任何正文改变。**模型那条路已被驱动,而畸形的回复被拒绝**(2026-09-16):`tests/d4-model-revision.spec.ts` 让 D3 与 D4 穿过一个按各步自己的格式作答的写作者,于是解析器读到的是模型会产出的那种回复 —— 浏览器那次运行自己的三段交换就是那份 fixture。`runner/issue-parse.ts` 分清三种意图:一段替换正文、`PATCH: NONE`(作者把这条意见接受为解释)、以及**缺少** `PATCH` 行。第三种曾经与第二种是同一个值,于是一份只是没按格式作答的回复被记成 `accepted_explanation`,该步通过。省略标签的交换现在按编号与所缺标签被报告,`assertWellFormed` 把这份报告变成一次失败的步骤,而不是在空无之上关闭一条 issue。**解析器只认这一种带标签的格式**:用散文作答的回复被拒,不会被解释。
- **A 门禁审的是手稿,不是 claim 材料**(2026-09-16):当这次运行已经产出稿子时,`verdictA` 读 `draft` / `revised-draft` 并审**它** —— `runner/manuscript-review.ts` 拿正文里的数字对照运行的测量记录、拿方法一节对照真正执行的那个实现、拿图表与文献引用对照 draft 自己的名册、拿结论的方向对照测量的符号。在这之前它调的是 `reviewClaim(runCtx.claimMaterial)`,无论那一步写了什么,于是一个离线探针可以改掉正文里的一个数字、删掉方法一节、跳过修订,而 A 的票不动。在还没有手稿时就由 A 把关的步骤(A2、A3、B1、D2)仍然审 claim 材料,而判定的 evidence 会写明读的是两者中的哪一个。**这些检查只找四件事,不多**:一个没有任何东西测量过的数字、一节没人写过的正文、一个指向空处的引用、以及一个被它自己的证据否掉的结论。一篇论文好不好,需要一个读者,而本仓库不会把规则的输出报告成读者的意见。
- **线上到达的方案会被解析到那个测量它所指之量的实现**(2026-09-16):`requirePlan`(`runner/study-plan.ts`)返回的方案**总是**带着 `implementationId`,取自 `metric.key` 与方案一致的那个唯一的受支持实现。具名 id 的方案,该 id 会与指标校对;没有任何实现能测的量在边界上被拒。线上方案 —— 模型提一个研究、人确认它 —— 不带 id,而在这次改动之前 `requirePlan` 会接受它,`B1-method` 则在运行到第四步之后抛出,把该步留在 `in_progress` 且看不到任何错误。每一次浏览器运行都停在那里。`runT19B` 现在在第一步之前调用 `requirePlan`,于是一个它无法执行的方案会被拒,而调用方还来得及被告知原因。**目前只有一个实现**,所以测量别的东西的研究会被拒,而不是被跑。
- **每一节都从证据写出,没有证据的那一节被拒绝**(2026-09-16):`runner/section-evidence.ts` 把 section id 映射到它写作所依据的运行数据 —— Results 拿到数字、单位、以及产出它们的规则版本;Method 拿到实现,外加一条 `execution`,比对方法声明的版本与结果的版本;Experiments 拿到运行口径;Discussion 拿到复核过的来源,包括评审者判定**不**支持主张的那些。`D3-writing` 把它放在写作者请求的 `evidence` 下,而必需证据缺失的那一节**根本不写** —— 模型不写,内置句子也不补。draft 记下 `sectionEvidence` 与 `refusedSections`,`readinessOfRun` 拒绝把这样一次运行叫作就绪。**运行真正撞上的是 E1**:`assembleManuscript` 本来就拒绝空正文的节(`DSH_MANUSCRIPT_EMPTY_SECTION`),所以被拒绝的节是让运行停下,而不是送到读者面前。**写作者此前拿到的是标签,不是证据** —— `{field, direction, sectionId, claimRef, figureCount, citable}`,而 `citable` 只是一张图表编号清单。
- **B 通道锚在真正取回、真正读过的文献上**(2026-09-16):`runner/evidence-corpus.ts` 存着一小组已入库的真实来源 —— 每一条带着它的标识符、评审者读过的**原文段落**、覆盖该段落的哈希,以及一条"它是否支持这句主张"的记录判定 —— `runner/evidence-anchors.ts` 在它上面跑与合成路径同一条 core `verifyCitation` 身份链,发布 `sourceClass: 'literature'`。一次 production 运行现在能凭一个真实锚跑完十五步到人工门;在这之前唯一的锚是 `MockCitationResolverAdapter` 套 `10.0000/synthetic.t19b-anchor`,所以任何 production 运行都到不了真实的 B 通过。运行**不会**重新抓取这些来源,每一条的 provenance 注记都这么写。**语料库里没有的 claim 版本回落到合成锚**,而 production 仍然拒它 —— 那条回落路径正是 `tests/production-evidence-policy.spec.ts` 钉住的。**来源是以代码形式入库的,不是运行时抓的**,所以一条来源被撤稿或被取代,运行不会知道:`retracted` 是评审者设的字段,不是运行去查的东西。**评审者的保留意见是散文,不是字段**:判定的 `scope` 记下这条来源**没有**确立什么,而下游没有任何东西依据它行动。
- **一次运行报告一个结果,并说明是哪一个**(2026-09-16):`C1-mvp` 写 `result-version` —— 六个测量量、规则版本、主张的指标,以及覆盖它们的 SHA-256 —— 每一个陈述数字的步骤都把它声明为输入并读它(`C2`、`C3`、`D1`、`D3`、`D4`、`E1`)。这些数字原本在每一处各自重算;它们相互一致,只是因为仿真对同一份研究是确定性的,而那张图与那张结果表本可以和旁边的正文漂开。`D1-figure-map` 与 `E1-format` 现在用这条记录建展品,`draft` / `revised-draft` 带上 `resultSource` 与 `resultRef`。**没有产出者时被驱动的步骤会自己量这份研究并写 `recomputed`** —— 经驱动不可达,因为这条记录是驱动器要求的声明输入。`B3-baseline` 仍然自己量,而且必须如此:它跑在 C1 之前,确立基线是它的职责。
- **手稿说的方法,就是跑过的那段代码**(2026-09-16):`B1-method` 曾经把模型的回答写进 `method-spec`,方法一节渲染的正是那段回答 —— 一条记录在案的回答写着强化学习策略,而每一个数字都来自 `runner/platoon-sim.ts`。现在 `runner/implementations.ts` 声明这次运行执行的实现,它的算法、引用、参数、变化因素、方程与产出全部从仿真自己的常量里读出,由 `StudyPlan.implementationId` 具名;`requirePlan` 拒绝具名本运行没有的实现的方案。模型保留过程步骤与指标方向,它自己答的 FAMILY 记为 `modelDeclaredFamily` 供审计。默认方案的 `essentialDifference` 在同一次改动里更正:它原本写着 `adaptive (RL) rather than fixed-time`,两处都不真。**目前只有一个实现**,所以另一个领域的第二个研究仍然跑不了。
- **判定带着它所审查的东西,由门禁比对**(2026-09-16):`GateVerdict` 新增 `targetRefs` 与 `inputDigest`,由 `bindVerdict` 在**构建判定**的地方设置 —— 绝不在提交时 —— 而 `submitGateVerdict` 拒绝目标与该 attempt 提交 receipt 不完全一致的判定(`DSH_GATE_STALE_TARGET`、`DSH_GATE_STALE_INPUTS`、`DSH_GATE_UNBOUND_VERDICT`)。门禁还要求 receipt 本身(`DSH_GATE_WITHOUT_COMMIT`、`DSH_GATE_COMMIT_MISMATCH`),而 `recordArtifact` 在该 attempt 提交之后拒绝(`DSH_ARTIFACT_AFTER_COMMIT`)。这四条都由一次独立复核先行复现;逐 slug 的接缝仍为 `ctx.research.recordArtifact`、恢复用 fixture 与 E2 的空门路径保留。
- **资格不是就绪**(2026-09-16):manifest 与运行摘要同时带上 `profileEligible`(部署的证据 profile 是否**有可能**承载投稿)与 `submissionReady`(**这次运行**的材料是否齐备、门禁是否全部关闭),两者分开。**就绪不是批准,而这条检查也不读批准记录**:`submissionReadinessOf` 看的是运行里每一步的状态,从不看批准记录,所以一次运行报就绪是因为每一道门都关闭了,不是因为有谁签了字。`submittabilityOf` 因此改名 `evidenceEligibilityOf` —— 它旧的名字承诺了一个它从未计算过的、关于某次运行的事实,而一次在 A1 就停住的 production 运行导出了 `submittable: true`。**就绪不是投稿、也不是批准**:它说的是材料存在、门禁关闭,而最终包仍由人批准。
- **运行把它被解析时依据的配置记下来,重启读那条记录**(2026-09-16):`setRunSpec` 在第一步之前把研究方案、方案的来源、证据 profile 与每步预算存到运行上,受与运行输入相同的冻结约束。`resumeRunPipeline` 读那条记录,而不是从执行恢复的部署当下提供的东西里取标题、领域、方向、大纲与预算 —— 后者正是让"被恢复的运行"变成另一个研究的原因。主张那一半仍从工件覆盖,因为工件才是门禁裁断了什么的权威。**解析不出来的记录会静默回落到部署的方案**,除了快照自己的 spec 会与实际的驱动不一致 —— 格式现在要求这条记录,所以这只描述这次改动之前写下的记录。
- **运行每步之后做 checkpoint**(2026-09-16):`DriveOptions.checkpointAfterStep` 每完成一步就持久化一次快照,于是中途死掉的进程是恢复而不是从头再来。产物包仍然只在结束时导一次。失败的 checkpoint 收进 `RunResult.checkpointErrors`、运行继续 —— 那一步已经提交,失败是被**报告**而不是被抛出。
- **依赖图要对着步骤实际读的东西检查**(2026-09-16):`StepOutcome.readSlugs` 记下执行器运行时向 `getInput` 要过的每一个 slug,`tests/dependency-closure.spec.ts` 把它与声明的输入比对。两条未声明的读取是这样找出来的,现在已声明(`D2-framework` 读 `method-spec`,`E1-format` 读 `paper-outline`)。**`readSlugs` 只覆盖执行器直接调用的 `getInput`** —— 通过工具依赖去够工件的步骤不在其中,而目前没有这样的读取。
- **一次运行声明它的证据允许是什么,而出货 bundle 声明的是 `evaluation`**(2026-09-16):`DriveOptions.evidenceProfile` 由驱动器解析一次,交给每一条门通道;未声明的运行就是评估运行,它会执行、且全部输出被盖上不可投稿。B 通道现在**声明**它所构建锚的 provenance(`fixture`:一个针对合成语料的模拟解析器),而不再只在散文里描述;`verdictB` 在裁断之前调用 `admitAsEvidence`:在 `production` 下核验被扣下,由 core 自己的 `requireExternalAnchor` 产生弃权,于是锚是**扣住**门而不是通过它。`ResearchRunSnapshot` 带上 `evidenceProfile` / `profileEligible` / `submissionReady` / `readinessNote`,而 `run-summary.md` 与产物包 manifest 带上同样这三项,所以读包的人分得清演示与投稿。**`pending` 这一档还够不到端到端**:它是"真记录但全文没读"会产生的东西,而 B 通道目前还没有生产级来源。
- **一步的产物作为一个集合提交,门禁拒绝一个没有产出它们的步骤**(2026-09-16):`runStep` 不再逐 slug 写,而是调用 core 的 `commitStepOutputs` —— 它要求候选集合与该步声明的产物**恰好**相等,拒绝为"步骤已经走过去的那个 attempt"提交,并且在写任何东西**之前**就克隆并哈希每一个值。registry 条目带上 `ref`(工件 id、版本、规范化编码的 SHA-256),于是读者具名的是 revision 而不是 slug。当某个声明产物缺失、或属于另一个 attempt 时,`submitGateVerdict` 拒绝该判定。**提交 receipt 不持久化**,所以被恢复的 attempt 读不回自己的 receipt —— 重复执行仍被既有的 `DSH_STEP_ALREADY_EXECUTED` 守卫挡住,所以这个省略不会变成重复提交,但它属于 checkpoint 那项工作。
- **一次运行研究什么,由模型提出、由人确认**(2026-09-15):`@Remote('proposeDirections')` 收一个领域,答回若干候选 —— 标题、方向、主张,以及它承诺的判定标准 —— 每一个都已经过门自己那条主张级检查,所以 C 通道判不了的主张会带着理由被拒,而不是端上来再在半路弃审。客户端的运行控件打开一个对话框(`DirectionDialog.tsx`),判定标准是从方案自己声明的承诺里读出来渲染的,确认之后才按那个人确认的方案开始跑。`requirePlan`(`runner/study-plan.ts`)会拒掉从线上下来的方案 —— 缺字段、章节 id 跟骨架不一致、指标不是这项研究测的那个、或者主张门判不了 —— 而不是拿默认方案顶替:一次悄悄测了别的东西的运行,产出的工件讲的是一个没人要过的研究。
- **候选方向是写出来的,所以没有散文通道的部署提不了方向**(2026-09-15):`Config.prose` 没配写入器时 `proposeDirections` 直接拒绝,客户端的运行控件于是直接跑默认方案,而不是打开一个注定失败的对话框。对话框还会说明候选来自哪条通道,免得把确定性路由的输出当成模型的回答。**对话框自己搭了模态**:`@deepseek-ai/dsh-client-ui-primitives` 已经导出 `Modal`(portal、Escape 与遮罩关闭、设计令牌),而 `dsh-research-web` 还没依赖它,所以这个对话框没有 Escape 处理、颜色也是自己写的。换过去是机械的、只是推迟了,不是被挡住。**对话框展示候选的标题、方向、主张、预测与判定标准,但不展示它的章节标题。** 候选同样选定了章节标题 —— 它们是方案的一部分,也会进入手稿 —— 所以人确认的东西比对话框展示的多。把这一行渲染出来是小事,但还没做。
- **被测量的量仍然是研究的,不是方案的**(2026-09-15):候选的预测必须点出这次运行能测的那个量,因为能裁决"关于别的量"的主张的那个实验还不存在。指标不同的方案在边界上就被拒。把这件事解开的那一步 —— 生成并执行基准 —— 是下一个阶段。

- **研究是这次运行的数据,不是这个包源码里的常量**(2026-09-15):`runner/study-plan.ts` 装着 `StudyPlan` —— 手稿标题、领域、检索方向、章节骨架、主张(id、一句话引用、断言、本质差异、证伪实验、预测)以及被测量的量 —— 原先读 `CANONICAL_CLAIM_ID` / `CANONICAL_CLAIM_REF` / `CANONICAL_PREDICTION` / `CANONICAL_METRIC_KEY` / `DEFAULT_OUTLINE` / `DEFAULT_HEADING` 这些常量的地方,现在都读它。A1 的检索题目是 `plan.direction`,而同一个值也种进运行的 `domain-direction` 输入:这两者以前是两个值,而且题目是个没有任何输入喂给它的字面量,于是一次运行的文献可以是关于一个跟它的测量无关的题目。默认方案的方向因此就是这项研究自己的题目,而不再是 `adaptive traffic signal control`。`SCENARIO` 只留下没有任何方案会选择的东西 —— 两个编队、兜底 venue 和数据集文件。
- **方案还不是持久的,也没有面向部署的配置能声明它**(2026-09-15):一次运行从 `DriveOptions.studyPlan` 拿方案,拿不到就用默认方案、并让 `domainDirection` 替换该默认方案的方向;`dsh-research-cordis` 的 `Config` 里还没有方案字段。**恢复**会从运行已经记下的工件里重建方案的**主张**那一半(主张 id、引用、预测、指标键、承诺),但标题、领域、方向和大纲不在任何工件里,所以被恢复的运行从"执行恢复的那个部署"给的方案里拿这四项。默认方案下这是精确的;一个部署声明自己的方案、又去恢复另一个部署的运行时,就不精确。把方案持久化,属于"让人能给出方案"那次改动。
- **每个散文请求都带上这次运行的主题**(2026-09-15):每个 `proseWriter.write` 请求都往 `context` 里摊入 `planContextOf(plan)` —— 领域与方向;另外 D2 的章节名从 `plan.outline` 派生,而不是从一张 `DEFAULT_HEADING` 表。没有后者的话,方案改了一个章节的名字,输出里还会是旧名字。

- **判决门与具体研究是分开的,被测量的量是参数**(2026-09-15):`runner/prediction-gate.ts` 装着"一条主张到底能不能被判决"的那套纪律 —— 把主张绑到研究测的那个量上、把它写下的锚与方向词拿去和它自己声明的承诺对质、遇到否定就停手 —— 并把那个量当作参数(`MeasuredMetric`:主张声明的键、给人看的标签、值越大是否越好、以及主张必须真的用到的那些措辞)。在此之前它长在 `runner/platoon-sim.ts` 里、挨着一个跟车模型,别的领域的研究要够到它就得先 import 一个交通模块。现在研究通过 `PredictionGateInput.measure` 把自己的测量交进来,而那是一个回调:门只在每一道主张级检查都过了之后才调它 —— 正是这一点让一次跑坏的测量没法把措辞缺陷盖住。**这套参数化是由 `tests/prediction-gate.spec.ts` 里一个合成的延迟指标验证的,不是由第二份真的研究验证的**:这棵树里还没有第二份研究,所以"别的领域的研究够得到这套纪律"是在门自己的接口上被证明的,不是端到端被证明的。
- **只拿研究的符号去判方向词,是 `higher-is-better` 的假定**(2026-09-15):门直接从改进量的符号算出 `inClaimDirection`,于是在一个"越小越好"的量上,一条"shall lower the latency"的主张被判成要的是反方向,并被一个其实满足它的测量报成被反驳。现在读的是 `MeasuredMetric.direction`;车队那个场景行为不变,因为它的方向就是 `higher-is-better`,两种读法在那里一致。这个缺陷是上面那个合成指标的用例找出来的,不是出货的研究找出来的。

- **真值等级是 5 级**(2026-09-14 增补 `local_computation`)。16 步的划分:
  - `real_tool_fixture_input`(5 步,工具函数真的执行):A1 / A2 / C3 / D1 / E1;
  - `local_computation`(5 步,无工具、无外部系统,由本包代码算出真实测量):A4 / B2 / B3 / C1 / C2;

- **实验是车队跟驰仿真,不是查表**(2026-09-14 换):`runner/platoon-sim.ts` 用 IDM(Treiber/Hennecke/Helbing 2000)在声明的固定步长上积分两个车队 —— 全 HV 基线与 HV–AV–HV 变体 —— 反应延迟用环形缓冲取 leader 的延迟状态,报告最小 TTC、平均车头时距、平均 jerk 与字符串稳定性指数,全部从轨迹算出。**没有 fixture 表,也没有按 claim id 查表**。

- **两股机制是分开的,而且各自可消融**:反应延迟(leader 的过去状态)与预测(把观测到的状态向前外推一个 horizon)是两件事。第一版把 horizon 从延迟里**减掉**,于是两个"可分离机制"其实是同一根标量轴上的两点 —— 一个审计用 `{reaction:0.15,horizon:0.15}` 与 `{reaction:1.2,horizon:1.2}` 逐位相同的轨迹证明了这一点,Method 段里"AV 向前预测 0.15 s"那句话当时描述不了任何东西。
