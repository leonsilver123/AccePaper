# @deepseek-ai/dsh-research-team

[English](README.md) | 中文

`ctx.agentTeams` 服务与 T19-B 运行器:红队舰队、带 CAS 修订的任务板、写入范围守卫、会话投影,以及把 16 步驱动起来的执行器注册表(`runner/`)。

分层是显式的:纯逻辑层(`types` / `revision` / `projection` / `scope-guard` / `roster` / `redteam` / `anchor` / `experiment`)→ 薄适配层(`journal` / `task-board` / `session-events` / `research-projection` / `research-guard`)→ `index.ts` 这一个接线点(服务声明、`SessionEventMap` 注入、`ctx.effect` 生命周期)。

`runner/registry.ts` 是 16 步执行器的审计真源:每个条目声明 `stepId` / `executor` / `producer` / `truthfulness` / `timeoutMs` / `gateRequirement` / `recoveryPolicy`,且输入输出 schema 与闸门要求都从 core 的冻结定义派生,以防与 16 步定义漂移。

## 已知限制与延期工作

- **研究靠一次部署读取被找到,而不是靠页面记住了什么** (2026-09-17):`@Remote('listRuns')` 回答这个部署持有哪些研究,最新的在前 —— 这就是让一项研究在启动它的标签页消失之后仍能被够到的读取,因为 run id 留在那个标签页的存储里,而快照一直在盘上。**本进程持有的运行从它的活状态报告;本进程不持有的运行从它的文件读出**并报 `stopped`,同时带着快照被取走时正在飞行中的步骤,所以中断的研究与跑完的研究分得开。同一项研究即使在两处都存在也只出现一次,因为活状态就是它自己的读者看到的那个状态。**顺序是 id 的顺序,不是版本的顺序**:版本数的是**一项**研究提交了什么,无法把两项研究相互排序,而 id 是 UUID,在多次调用、多个进程之间排序稳定。每条记录带着执行状态、项目版本、编目的 `stepsTotal` 里过了几步 `stepsPassed`、`submissionReady`,以及读者据以行动的两条失败事实(`saveFailure`、`executionError`)。**读不到的列表是拒绝**,不是空列表:"这个部署没有任何研究"与"我问不出来"有不同的补救办法,而其中一个不是"你的工作没了"。**浏览器只有在 Remote assembly bundle 带着这个方法时才够得到它** —— `dsh-api-remotes/lib/client.js` 把各包生成的描述符内联进来,所以新增一个 `@Remote` 方法要在生成器重写描述符之后重建 client face;先打包的构建会让页面去调用一个在别处都存在的方法,而页面把它报成 `listRuns is not a function`。
- **没落盘的保存可以重试,而且重试不是重跑** (2026-09-16):`@Remote('retryRunSave')` 把**本进程持有的**一次运行的当前状态再写一遍到它的快照。这是部署的写入路径失败又恢复之后,人真正需要的那条补救:没有它,想让一次运行回到盘上就只能把研究再做一遍 —— 那要花掉两倍的模型调用,还会在同一名字下产出不同的数字。它与磁盘**对账**而不是相信记住的数字(基准版本从磁盘当下的状态读出),并且只推进**快照的写入计数**,绝不推进运行的 `projectRevision`(把同一份状态再写一遍没有提交任何东西),所以重试之前做出的决定仍然命名着一个当前版本。**本进程不持有的运行会被拒绝**:从文件读回来的运行已经处于它文件记录的状态,再写一遍没有磁盘上还没有的内容。客户端在**后端自己报出** `saveFailure` 时提供这个重试,并渲染重试回答的那份运行 —— 于是决定所需的版本正是页面重新读到的那个。
- **没落盘的保存会成为运行的状态,并同时拒绝就绪与裁决** (2026-09-16):这次失败此前只活在 `RunResult.checkpointErrors` 里,而一次**正在运行**的运行还没产出它 —— 于是页面显示一项研究在推进,却对"这些成果没有落到盘上"一字不提。现在它是 `ActiveRun.checkpointError`,作为该运行持久化记录的 `error` 报出(就在**不再前进的 `revision`** 旁边),并由下一次落盘的写入**清除**。`submissionReady` 与就绪说明读的是**同一条记录**,经由投影渲染它的那一个访问器(`livePersistence`)—— 读两次可能对同一个问题给出不同答案,让页面在一个谁都存不下去的运行上说"就绪"。**审批也被它拒绝,且是在做出任何决定之前**(`research/approval-save-failed`):`submitApproval` 与其他前置条件 —— 运行、步骤、`humanGate`、当前状态、当前 attempt、期望版本 —— 并列地读这次运行最后一次落盘的写入,因为事后报 `persisted: false` 已经太晚:闸门在内存里已经走到 `passed`,而快照仍说 `gated`,于是重启后系统请人批准一件他已经批准过的事,而调用者只被告知自己的决定不持久,却无从补救。拒绝里带着部署自己的原因,并且 `RememberedRun` 新增了 `saveState`(与 `persist` 一同变为必填),让一个能写决定的调用者无法忘记说明"这次运行是否在盘上"。**补救与它的边界**:拒绝不会被记住,所以运行的下一次写入落地后,同一条命令就能被裁决 —— 那是运行仍在被驱动期间的一个检查点。**驱动一旦停止,本进程内就没有任何东西再写这次运行**,所以**最后一次**写入失败的运行会一直被拒,直到它被重新驱动;拒绝里说明了这一点,而那个重新驱动的操作属于断线恢复那一项工作,不在这里。

- **启动命令要么可被找回,要么就谈不上幂等** (2026-09-16):`StartCommandRecord` 以"写临时文件再改名"的方式写进 `<snapshotDirectory>/commands/<commandId>.json`,而"进行中"的答案在任何 `await` 之前同步登记 —— 所以同时到达的两次调用只产生**一次**运行(映射此前是在保存之后才写的,两边都可能错过它),重启后的重试由记录回答,而不是再起一项研究。**记录先于它所命名的运行落盘**,这正是关掉两者之间那个窗口的顺序:反过来写时,进程死在"运行的首次保存"与"记录那一次写入"之间,会留下一项没有任何东西命名的研究,而重试因为找不到记录,会再起**第二项**。先写记录,重试就总有东西可查,窗口能造成的代价只剩"这个命令 id 要换一个":记录在而运行不在时会被如实报出(`persisted: false` 并指出缺失的运行),而不是重跑 —— 已经开始的 研究可能已经产出了东西,再起一项不是查明的方式。这个顺序的代价在失败路径上偿付:一次没有发生的启动会把它写的记录**从它写的位置**删掉,于是该 id 仍可重试;若这次删除本身失败,记录会留下,那是安全的方向 —— 重试被拒绝,而不是重复。携带**不同**研究的命令 id 会被摘要比较拒绝,无法命名文件的 id 被**拒绝而不是净化**(净化后的 id 是另一个 id,下一次重试找不到它)。**记录写不出来的启动会失败** —— 一条谁也查不到的命令比没跑过更糟。**尚未做的**:`startCommands` 没有淘汰,启动很多运行的部署会让这个映射在进程存活期间持续增长。

- **cursor 命名的是一个**历史**里的位置,而不只是一个运行里的位置** (2026-09-16):从检查点恢复的运行保留那次检查点保存的事件,并在丢失的尾巴原本占用的下标上追加**新**事件 —— 于是读者已经消费过的位置在这里可能放着不同的事件,而从这个位置继续,等于让一个从未见过"替代物"的读者接着往下走。cursor 现在是 `<runId>#<已消费数>#<digest>`,digest 是该位置以下事件的一条链(每个事件的指纹折进前一个 digest,并且按**固定字段顺序**折,好让一次重启不会看起来像另一个历史)。digest 与所呈现日志不符的 cursor 会被带原因的 `resync` 帧拒绝,读者重新读取。**位置是"已消费的数量",不是"最后看到的下标"**:事件信封现在同时携带 `cursor`(该事件**之后**的位置)与 `eventId`,于是中途重连的页面不会再收到它已经应用过的事件(旧写法把页面持有的位置设成事件自己的下标,等于又点了一次它)。**控制更新也是帧**:运行的保存健康与执行归属会在**没有任何事件被追加**的情况下变化 —— 检查点失败、驱动停止 —— 现在任一变化都会发出一帧快照;它在开场帧处就被读取(生成器是在第一次 `yield` **之后**才执行初始化语句的,所以一个只听说过追加事件的读者,在运行停在人工门期间保存坏掉时会一无所知)。慢读者不会被缓冲:async generator 只在消费者索取下一帧时才产出,订阅由它自己的 `AbortSignal` 取消。
- **运行改为通过一条流、按 cursor 跟随,而不是轮询** (2026-09-16):`@Remote({ mode: 'stream' }) followRun({ runId, cursor? })` 产出开场的一帧 `snapshot`、每个新追加事件一帧 `event`,以及在没有东西再驱动这次运行时的一帧收尾 `snapshot`。**cursor 是事件的下标**,以 `<runId>#<sequence>` 的形式限定到它所属的运行:运行的审计事件没有序号字段,而 `ts` 是两条事件可能共用的毫秒值,所以下标是它唯一严格单调的键 —— 而日志只会被 push,所以一个下标终生命名同一个事件。**开场的 cursor 与它的快照是同一次读取**,这正是"快照与订阅之间没有缺口"由构造成立的原因:那份快照已包含位于它及之前的每一个事件的效果,重连的读者拿到的是已经包含所错过内容的状态。来自别的运行的 cursor、或日志从未到达过的位置,会被带原因的 `resync` 帧拒绝,而不是被读成别的历史里的位置。**这条流只读** —— 版本敏感的命令留在经过认证的 unary 通道上 —— 且**信封不携带 `detail`**,因为 typert 生成器拒绝线上边界上的裸 `unknown`(第一次构建就被它拦下)。
- **研究可以在运行中被启动和读取,重启后还能找到它** (2026-09-16):`@Remote('startRun')` 创建一次运行、把它写到磁盘、返回它的 id,并在本服务的后台驱动它;`@Remote('runSnapshot')` 读取这次运行的当前状态。在此之前唯一的入口是 `@Remote('run')`,它要等整项研究结束才返回 —— 于是按下按钮的人几分钟内什么都看不到,刷新页面就丢掉了手里唯一的把手,而视图是由 `RunResult` 构建的,那个值在运行结束前根本不存在。**`RunResult` 仍然是驱动调用的结果**;改变的是:回答"这次运行在做什么"不再需要它。`runner/project-view.ts` 读取这次运行**自己的记录** —— 步骤状态、工件登记表、`step-executed` 记录 —— 并投影出目录里的每一个步骤,所以尚未执行的步骤报 `pending` 且 attempt 为 0,既不会缺席,也不会被默认成一个成功。**快照带有 `execution`**,它是关于**本进程**的事实:`running` 表示此刻这里有执行器在驱动它,而且这个值绝不会从一个已经消失的进程写下的记录里读回来。因此重启后的查询会从检查点恢复这次运行并报 `stopped`,同时列出当时在飞行中的步骤 —— 对读者会失去什么保持诚实,而不是给出一个陈旧的 `running`。**抛异常的执行器在运行层报告**(`execution: 'failed'` 加 `executionError`),因为按步骤的记录只能说明研究走到了哪里,说不出"本来要继续它的东西已经不在了"。**重试的命令读到第一次发送产生的答案**:`commandId` 命名的是命令,所以没读到响应的客户端重发同一个 id 时,拿到的是它已经启动的那次运行,而不是再花掉一项研究。**无法把运行记录下来的启动会被拒绝** —— id 在驱动开始之前写入磁盘,所以快照目录不可用的部署拿到的是错误,而不是一个它守不住的"成功"。`runPipeline` 也补上了 `checkpointAfterStep`,这本该在检查点落地时就有的:异步启动的运行此前只在结束时才保存。
- **研究报告它进行得怎么样,而不只是结果如何** (2026-09-16):客户端的运行控件启动运行、读取它、跟随它,每读到一份快照就渲染一次;工作台在就绪徽章旁标出运行 id 与执行状态。**这个跟随循环是页面对于研究的兴趣,不是研究本身**:执行器由本服务持有,所以关掉页面不会取消运行,回来的客户端读到的是同一次运行。**传输原本是客户端固定间隔的轮询,现在改为运行自己的事件流**(`followToRest` 走 `@Remote({ mode: 'stream' }) followRun`,带 cursor、去重,并在 cursor 被拒时重开 —— 见下面那一条,那一半记录在那里)。**尚不存在的部分**:客户端读取失败会抛错退出跟随循环,所以"页面不再跟随"与"运行已停止"是读者必须自行从消息里分辨的两件事;另外 `runSnapshot` 每次调用都读这次运行的记录,所以很长的运行其轮询会重新投影整次运行,而不是读增量。
- **批准绑的是读者看过的那个版本,而它过去绑的是当下的版本**(2026-09-16):`ApprovalSubmission.expectedProjectRevision` 是必填的,而 `submitApproval` 会拒绝任何不是运行当前版本的决定 —— 于是一个在读者眼皮底下移动过的页面(第二个标签页、落了地的步骤、一次恢复)无法把决定记在一份没人读过的文档上。拒绝里同时点名两个版本,并说明要重新读。**客户端那一半**:一个说不出自己版本的页面**根本不提供**裁决按钮。与 `approvalStalenessOf` 合起来 —— 后者在决定**之后**抓同一个错配 —— 版本在决定那一刻的两侧都被绑住。
- **导出 manifest 说出它读的是哪个项目版本**(2026-09-16):`RunPackageManifest.projectRevision` 从运行读出,不由文件推导,于是比较两个包的读者 —— 或者拿一个包去对照某个屏幕的人 —— 能分辨它们是不是这份研究的同一个状态。`generatedAt` 说的是有人什么时候读的,那不是同一件事:相隔一分钟的两次导出可以装着不同的手稿。
- **修订留下的未关闭意见现在会挡住就绪**(2026-09-16):`openIssuesOf` 读 `rebuttal` 工件里逐条 issue 的结局,`submissionReadinessOf` 对仍然带着一条的运行拒绝就绪,并点名那条 issue、它所在的节、以及应用器给出的原因。一轮修订会记下它提出的每一条意见变成了什么;被留成 `open` 的那些,是因为补丁是针对另一个版本写的、什么都没改、或与同一节的另一份补丁冲突 —— 每一条都是评审者提过、而论文没有回答的东西,所以一次门禁全关、也有人批准过的运行**仍然不就绪**。**在这之前,这份清单被写进产物,却没有人读**:它不阻止 `D4-rebuttal` 步进,也完全没有进入就绪判定。**仍然缺的**:没有轮次计数、没有预算,所以「两轮同样的失败转人决」没有东西可数 —— `D4` 只跑一轮,一次拒绝是被报告,而不是被重试。
- **就绪判定会拒绝一次批准已过期的运行**(2026-09-16):`readinessOfRun` 对每一步向 core 的 `approvalStalenessOf` 提问,把第一个答案交给 `submissionReadinessOf`,后者把它变成一条点名「哪个版本移动了」的拒绝。批准覆盖的是摆在本人面前的那份文档;一份离开了那个版本的手稿 —— 后面的步骤、从另一份快照恢复、或者一只手 —— 没有被批准过,而这个状态下的运行不就绪。**这不覆盖的东西**:导出的包**文件**。导出之后在磁盘上编辑 `manuscript.md` 在运行的 registry 之外,这里看不到;manifest 里逐文件的 `sha256` 才是读者拿来核对它的东西。
- **浏览器那条循环闭合了**(2026-09-16):端到端探针在 `cdf9e69f` 上报 **41/41**。一次经由出货应用驱动的运行把十六步带到 `E2-submit`,操作者通过页面批准、后端记下了这次批准(`{"a2":"passed","e2":"gated","steps":16}` 然后是 `{"e2":"passed"}`),而导出的包引用了 25 条来自实时目录的真实 DOI —— 没有一条是合成锚。它的手稿由部署配置的模型路由写出,并通过了四条检查的对抗性阅读。**它试了五次** —— 四次停在进程内套件从未看见的缺陷上,一次停在目录故障上 —— 那些缺陷记在 `../.agents/notes/implemented/testing/2026-09-16-what-the-browser-found.md`。**探针按交付跑,不按提交跑**:一次循环 = 两个面的完整构建 + 一次 profile 安装刷新 + 一个启动的应用 + 一个 Chrome 实例 + 最多二十分钟的实时模型。
- **闭环在 production profile 上跑通**(2026-09-16):`tests/e2e/closed-loop.spec.ts` 一次断言整条链,因为"每一部分各自通过"正是**断掉的循环**从内部看起来的样子。一次 production 运行凭复核过的文献跑完十五步到 `E2-submit`,写出一份各节都记录了"它从哪条证据写出"的手稿,在读到一个人为注入的、运行从未测过的数字的那道门**停下**,用审过 draft 的同一套检查复审修订稿,并在有人批准之前一直报 `profileEligible: true` / `submissionReady: false`。被证伪的预测会让运行正常完成 —— `mvp-results.outcome` 是 `refuted` 且 `decisive: true`,这是两件不同的事实 —— 因为一条只在正面结果上完成的流水线,是在制造正面结果。**这不是什么**:不是一次批准。`readinessOfRun` 说的是材料存在、门禁关闭;包由人在 E2 批准,而 `evaluation` 永远不就绪。
- **修订要么是一次 diff,要么什么都不是**(2026-09-16):`runner/issue-patch.ts` 装着 Issue → Patch → Verify 这条循环。一条 issue 具名一个节、以及它是针对哪一个版本写的(`basisHash`,由作者被展示的那份正文算出);一份 patch 是一段替换正文。只有当基准仍是当前的、且结果与它不同时才会被应用 —— 于是 `revised` 是"正文**变过**的那些节"的性质,由正文派生,绝不由调用方断言。针对过期版本写的 patch 会被拒而不是被应用(应用它会静默丢掉中间发生的一切);同一节的两份 patch 是冲突而不是合并。不改变正文的回答是 `accepted_explanation`,与 patch 分开记录。`D4-rebuttal` 读 `CONCERN`/`SECTION`/`RESPONSE`/`PATCH` 行,并把 `issues`、`changes`、`patchedSections`、`openIssues` 写进 rebuttal 与 revised draft。**在这之前**每一节都被映射成 `{ ...section, revised: record.hasRevisions }`,于是一条意见把整份手稿标成已修订而没有任何正文改变。**模型那条路已被驱动,而畸形的回复被拒绝**(2026-09-16):`tests/d4-model-revision.spec.ts` 让 D3 与 D4 穿过一个按各步自己的格式作答的写作者,于是解析器读到的是模型会产出的那种回复 —— 浏览器那次运行自己的三段交换就是那份 fixture。`runner/issue-parse.ts` 分清三种意图:一段替换正文、`PATCH: NONE`(作者把这条意见接受为解释)、以及**缺少** `PATCH` 行。第三种曾经与第二种是同一个值,于是一份只是没按格式作答的回复被记成 `accepted_explanation`,该步通过。省略标签的交换现在按编号与所缺标签被报告,`assertWellFormed` 把这份报告变成一次失败的步骤,而不是在空无之上关闭一条 issue。**解析器只认这一种带标签的格式**:用散文作答的回复被拒,不会被解释。
- **重复的批准命令被回答,而不是被重新裁决**(2026-09-16):`ApprovalSubmission` 带 `commandId`,而 `submitApproval` 对重复的 id 回答**第一次发送产生的结果**。一个从没读到第一个答案的调用方 —— 超时、刷新、再点一次那个看起来没反应的按钮 —— 过去会撞上 `not-pending`,一句它无法与「我的决定根本没落地」区分开的拒绝。**不同的 id 是不同的意图**,它撞上的是第一条命令产生的状态,所以这本台账回答重试,却不是绕过门的办法。**拒绝不被记住**:缓存一次拒绝,会让因为暂时性原因失败的命令在那个 id 下被永久拒绝。**台账在内存里**:跨重启之后,重试的命令会再次撞上 `not-pending` —— 这是安全的(它无法裁决两次),但不幂等,这条边界写在这里,而不是交给一个这一层并不拥有的持久表。
- **一次修订是一条有界的循环,不是单轮**(2026-09-16):`D4-rebuttal` 过去只跑一次,`roundId` 硬编码成 `t19s-rebuttal-1`,应用器拒绝一份补丁之后没有东西可以再试。现在它会再问 —— 最多 `revisionRounds` 轮(部署配置,默认 2)—— 每一轮都被告知上一轮留下的是**哪些节**,并拿到当前这份手稿。工件带上 `rounds`、`revisionRounds` 与 `stoppedBecause`。**「无进展」按节比较,不按 issue id**:每一轮都从 1 开始编号,比较 id 会把两轮在同样几节上失败叫作"有进展",然后把预算花在重复提问上。**它不做的事**:循环停下时仍未关闭的意见不会变成人工决定 —— 它挡住就绪、工件写明原因。

- **候选方向是写出来的,所以没有散文通道的部署提不了方向**(2026-09-15):`Config.prose` 没配写入器时 `proposeDirections` 直接拒绝,客户端的运行控件于是直接跑默认方案,而不是打开一个注定失败的对话框。对话框还会说明候选来自哪条通道,免得把确定性路由的输出当成模型的回答。**对话框自己搭了模态**:`@deepseek-ai/dsh-client-ui-primitives` 已经导出 `Modal`(portal、Escape 与遮罩关闭、设计令牌),而 `dsh-research-web` 还没依赖它,所以这个对话框没有 Escape 处理、颜色也是自己写的。换过去是机械的、只是推迟了,不是被挡住。**对话框展示候选的标题、方向、主张、预测与判定标准,但不展示它的章节标题。** 候选同样选定了章节标题 —— 它们是方案的一部分,也会进入手稿 —— 所以人确认的东西比对话框展示的多。把这一行渲染出来是小事,但还没做。
- **被测量的量仍然是研究的,不是方案的**(2026-09-15):候选的预测必须点出这次运行能测的那个量,因为能裁决"关于别的量"的主张的那个实验还不存在。指标不同的方案在边界上就被拒。把这件事解开的那一步 —— 生成并执行基准 —— 是下一个阶段。

- **研究是这次运行的数据,不是这个包源码里的常量**(2026-09-15):`runner/study-plan.ts` 装着 `StudyPlan` —— 手稿标题、领域、检索方向、章节骨架、主张(id、一句话引用、断言、本质差异、证伪实验、预测)以及被测量的量 —— 原先读 `CANONICAL_CLAIM_ID` / `CANONICAL_CLAIM_REF` / `CANONICAL_PREDICTION` / `CANONICAL_METRIC_KEY` / `DEFAULT_OUTLINE` / `DEFAULT_HEADING` 这些常量的地方,现在都读它。A1 的检索题目是 `plan.direction`,而同一个值也种进运行的 `domain-direction` 输入:这两者以前是两个值,而且题目是个没有任何输入喂给它的字面量,于是一次运行的文献可以是关于一个跟它的测量无关的题目。默认方案的方向因此就是这项研究自己的题目,而不再是 `adaptive traffic signal control`。`SCENARIO` 只留下没有任何方案会选择的东西 —— 两个编队、兜底 venue 和数据集文件。
- **方案还不是持久的,也没有面向部署的配置能声明它**(2026-09-15):一次运行从 `DriveOptions.studyPlan` 拿方案,拿不到就用默认方案、并让 `domainDirection` 替换该默认方案的方向;`dsh-research-cordis` 的 `Config` 里还没有方案字段。**恢复**会从运行已经记下的工件里重建方案的**主张**那一半(主张 id、引用、预测、指标键、承诺),但标题、领域、方向和大纲不在任何工件里,所以被恢复的运行从"执行恢复的那个部署"给的方案里拿这四项。默认方案下这是精确的;一个部署声明自己的方案、又去恢复另一个部署的运行时,就不精确。把方案持久化,属于"让人能给出方案"那次改动。
- **每个散文请求都带上这次运行的主题**(2026-09-15):每个 `proseWriter.write` 请求都往 `context` 里摊入 `planContextOf(plan)` —— 领域与方向;另外 D2 的章节名从 `plan.outline` 派生,而不是从一张 `DEFAULT_HEADING` 表。没有后者的话,方案改了一个章节的名字,输出里还会是旧名字。

- **判决门与具体研究是分开的,被测量的量是参数**(2026-09-15):`runner/prediction-gate.ts` 装着"一条主张到底能不能被判决"的那套纪律 —— 把主张绑到研究测的那个量上、把它写下的锚与方向词拿去和它自己声明的承诺对质、遇到否定就停手 —— 并把那个量当作参数(`MeasuredMetric`:主张声明的键、给人看的标签、值越大是否越好、以及主张必须真的用到的那些措辞)。在此之前它长在 `runner/platoon-sim.ts` 里、挨着一个跟车模型,别的领域的研究要够到它就得先 import 一个交通模块。现在研究通过 `PredictionGateInput.measure` 把自己的测量交进来,而那是一个回调:门只在每一道主张级检查都过了之后才调它 —— 正是这一点让一次跑坏的测量没法把措辞缺陷盖住。**这套参数化是由 `tests/prediction-gate.spec.ts` 里一个合成的延迟指标验证的,不是由第二份真的研究验证的**:这棵树里还没有第二份研究,所以"别的领域的研究够得到这套纪律"是在门自己的接口上被证明的,不是端到端被证明的。
- **只拿研究的符号去判方向词,是 `higher-is-better` 的假定**(2026-09-15):门直接从改进量的符号算出 `inClaimDirection`,于是在一个"越小越好"的量上,一条"shall lower the latency"的主张被判成要的是反方向,并被一个其实满足它的测量报成被反驳。现在读的是 `MeasuredMetric.direction`;车队那个场景行为不变,因为它的方向就是 `higher-is-better`,两种读法在那里一致。这个缺陷是上面那个合成指标的用例找出来的,不是出货的研究找出来的。

- **真值等级是 5 级**(2026-09-14 增补 `local_computation`)。16 步的划分:

  - `local_computation`(5 步,无工具、无外部系统,由本包代码算出真实测量):A4 / B2 / B3 / C1 / C2;
