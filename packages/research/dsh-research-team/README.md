# @deepseek-ai/dsh-research-team

English | [中文](README.zh.md)

The `ctx.agentTeams` service and the T19-B runner: the red-team fleet, the task board with CAS revisions, the write-scope guard, the session projection, and the executor registry (`runner/`) that drives the 16 steps.

The layering is explicit: a pure-logic layer (`types` / `revision` / `projection` / `scope-guard` / `roster` / `redteam` / `anchor` / `experiment`) → a thin adapter layer (`journal` / `task-board` / `session-events` / `research-projection` / `research-guard`) → `index.ts` as the single wiring point (service declaration, `SessionEventMap` injection, `ctx.effect` lifecycle).

`runner/registry.ts` is the audit source of truth for the 16-step executors: each entry declares `stepId` / `executor` / `producer` / `truthfulness` / `timeoutMs` / `gateRequirement` / `recoveryPolicy`, and both the input/output schemas and the gate requirements are derived from core's frozen definitions so they cannot drift from the 16-step definition.

## Known Limitations and Deferred Work

- **The manuscript's method is the code that ran** (2026-09-16): `B1-method` used to write the model's answer onto `method-spec`, and the Method section rendered that answer — one recorded response named a reinforcement-learning policy while every number came from `runner/platoon-sim.ts`. `runner/implementations.ts` now declares the implementation the run executes, with its algorithm, citation, parameters, varied factors, equations and outputs all read out of the simulation's own constants, and `StudyPlan.implementationId` names it; `requirePlan` refuses a plan naming an implementation this runner lacks. The model keeps the procedure steps and the metric direction, and its own FAMILY answer is recorded as `modelDeclaredFamily` for audit. The default plan's `essentialDifference` was corrected in the same change: it read `adaptive (RL) rather than fixed-time`, which was false twice over. **One implementation exists**, so a study from another field still cannot run.
- **A verdict carries what it judged, and the gate compares it** (2026-09-16): `GateVerdict` gained `targetRefs` and `inputDigest`, set by `bindVerdict` where the verdict is BUILT — never at submit time — and `submitGateVerdict` refuses a verdict whose targets are not exactly the attempt's commit receipt (`DSH_GATE_STALE_TARGET`, `DSH_GATE_STALE_INPUTS`, `DSH_GATE_UNBOUND_VERDICT`). The gate also requires the receipt itself (`DSH_GATE_WITHOUT_COMMIT`, `DSH_GATE_COMMIT_MISMATCH`), and `recordArtifact` refuses once the attempt has committed (`DSH_ARTIFACT_AFTER_COMMIT`). All four were reproduced by an independent review before they were fixed; the per-slug seam still exists for `ctx.research.recordArtifact`, the recovery fixtures and E2's empty-gate path.
- **Eligibility is not readiness** (2026-09-16): the manifest and the run summary carry `profileEligible` (what the deployment's evidence profile may ever carry) and `submissionReady` (whether THIS run produced an approved manuscript with every gate closed) as two separate facts. `submittabilityOf` was renamed `evidenceEligibilityOf` for the same reason — its old name promised a fact about a run that it never computed, and a production run blocked at A1 exported `submittable: true`. **Readiness is not a submission and not an approval**: it says the material exists and its gates closed, and a person still approves the final package.
- **A revision is still a flag, not a patch** (2026-09-16, measured): `D4-rebuttal` maps every section to `{ ...section, revised: record.hasRevisions }`, so one concern that says it requires a revision marks EVERY section revised while no body changes. An offline probe compared the D3 and D4 drafts and measured `unchangedBodies: true, revisedFlags: [true, true]`. What the review asks for is an Issue–Patch–Verify cycle in which `revised` is set only after a body has actually changed, and a concern requiring a text change cannot be closed without a diff. **This is the largest remaining P0 and it is not started** — the work is a per-section patch format on the D4 prose request, a pure apply-and-verify step, and a `disposition` per issue (`patched` / `accepted_explanation` / `open`).
- **The A gate reviews claim material, not the manuscript** (2026-09-16, measured): `verdictA` calls `reviewClaim(runCtx.claimMaterial)`, so the three offline rulebooks judge the claim's own fields whatever D3 or D4 wrote. An offline probe changed a number in the draft, deleted a method section, and skipped the revision; none of it moved the A vote. What the review asks for is a reviewer task bound to a `targetVersion` that actually reads the manuscript and its evidence. **Not started.**
- **The writer's context carries labels, not evidence** (2026-09-16, measured): the D3 request's context keys are `field, direction, sectionId, claimRef, figureCount, citable`, where the last is a label list. The method spec, the results table, the figure data and the literature records are all in the run and none of them reaches the writer, so a faithful model still cannot write a true Results section. **Not started**; it is the other half of the same gap as the A gate above.
- **A run records the configuration it was resolved against, and a restart reads it** (2026-09-16): `setRunSpec` stores the study plan, the plan's source, the evidence profile and the per-step budget on the run before the first step, under the same freeze as the run's inputs. `resumeRunPipeline` reads that record instead of taking the title, field, direction, outline and budget from whatever the resuming deployment currently supplies — which is what made a resumed run a different study from the one whose artifacts it was holding. The claim half is still overlaid from the artifacts, because the artifacts are the authority for what the gates graded. **A record that does not parse falls back to the deployment's plan silently apart from the snapshot's own spec, which then disagrees with what was driven** — the format requires the record now, so this describes only records written before the change.
- **A run checkpoints after every step** (2026-09-16): `DriveOptions.checkpointAfterStep` persists the snapshot once per finished step, so a process that dies mid-run resumes rather than starting over. The package is still exported once, at the end. A failing checkpoint is collected into `RunResult.checkpointErrors` and the run continues — the step has already committed, and the failure is reported rather than thrown.
- **The dependency graph is checked against what the steps read** (2026-09-16): `StepOutcome.readSlugs` records every slug an executor asked for while it ran, and `tests/dependency-closure.spec.ts` compares that with the declared inputs. Two undeclared reads were found this way and are declared now (`D2-framework` reads `method-spec`, `E1-format` reads `paper-outline`). **`readSlugs` is the executors' direct `getInput` calls only** — a step that reaches an artifact through a tool dependency is not covered, and no such read exists today.
- **A run declares what its evidence is allowed to be, and the shipped bundle declares `evaluation`** (2026-09-16): `DriveOptions.evidenceProfile` is resolved once by the driver and handed to every gate channel; an undeclared run is the evaluation run, which executes and whose entire output is stamped unsubmittable. The B channel now DECLARES the provenance of the anchor it builds (`fixture`: a simulated resolver over a synthetic corpus) instead of only describing it in prose, and `verdictB` calls `admitAsEvidence` before adjudicating: under `production` the verifications are withheld and core's own `requireExternalAnchor` produces the abstention, so the anchor holds the gate rather than passing it. `ResearchRunSnapshot` carries `evidenceProfile` / `submittable` / `submittabilityNote`, and `run-summary.md` plus the package manifest carry the same three, so a reader of a package can tell a demonstration from a submission. **The `pending` disposition is not yet reachable end to end**: it is what a real record with an unread full text produces, and the B channel has no production-grade source yet.
- **A step's outputs are committed as one set, and the gate refuses a step that has not produced them** (2026-09-16): `runStep` no longer writes slug by slug; it calls core's `commitStepOutputs`, which requires the candidate set to be exactly the step's declared outputs, refuses a commit for an attempt the step has moved past, and clones and hashes every value BEFORE writing any. The registry entry carries a `ref` (artifact id, version, SHA-256 of the canonical encoding), so a reader names a revision rather than a slug. `submitGateVerdict` refuses a verdict when a declared output is missing or belongs to another attempt. **The commit receipt is not persisted**, so a restored attempt cannot read its own receipt back — re-execution is still refused by the pre-existing `DSH_STEP_ALREADY_EXECUTED` guard, so the omission cannot become a double commit, but it belongs with the checkpoint work.
- **A run's research is proposed by a model and confirmed by a person** (2026-09-15): `@Remote('proposeDirections')` takes a field and answers with proposals — a title, a direction, a claim and the criterion it commits to — each already through the gate's own claim-level check, so a claim the C channel could not grade is refused with its reason rather than offered and then abandoned. The client's run control opens a dialog (`DirectionDialog.tsx`), shows the criterion read out of the plan's declared commitment, and starts the run under the plan the person confirmed. `requirePlan` (`runner/study-plan.ts`) refuses a plan that arrives off the wire — a missing field, an outline whose section ids differ from the skeleton, a metric this study does not measure, or a claim the gate cannot grade — instead of replacing it with the default, because a run that silently measured something else would produce artifacts describing a study nobody asked for.
- **The proposal is written, so a deployment with no prose channel cannot propose** (2026-09-15): `proposeDirections` refuses when `Config.prose` configures no writer, and the client's run control then starts the default plan directly rather than opening a dialog that could only fail. The dialog also states which channel produced the proposals, so a deterministic route is not mistaken for a model's answer. **The dialog hand-rolls its modal**: `@deepseek-ai/dsh-client-ui-primitives` already exports `Modal` (portal, Escape and mask close, design tokens) and `dsh-research-web` does not depend on it yet, so this dialog has no Escape handling and its own colours. Adopting it is mechanical and deferred, not blocked. **The dialog shows the proposal's title, direction, claim, prediction and criterion, but not its section headings.** A proposal chooses those too — they are part of the plan and they reach the manuscript — so a person confirms more than the dialog displays. Showing them is one rendered line and is not done yet.
- **The measured quantity is still the study's, not the plan's** (2026-09-15): a proposal's prediction must name the quantity this run can measure, because the experiment that would settle a claim about some other quantity does not exist yet. A plan whose metric differs is refused at the boundary. Generating and running the benchmark that would free the metric is the next stage.

- **The study is the run's data, not this package's source** (2026-09-15): `runner/study-plan.ts` holds `StudyPlan` — the manuscript title, the field, the retrieval direction, the section skeleton, the claim (id, reference sentence, assertion, essential difference, falsifying experiment, prediction) and the measured quantity — and every reader of the old `CANONICAL_CLAIM_ID` / `CANONICAL_CLAIM_REF` / `CANONICAL_PREDICTION` / `CANONICAL_METRIC_KEY` / `DEFAULT_OUTLINE` / `DEFAULT_HEADING` constants reads it there instead. A1's retrieval topic is `plan.direction`, which is also the value seeded into the run's `domain-direction` input: those were two values before, and the topic was a literal no input fed, so a run's literature could be about a subject its measurement was not. The default plan's direction is therefore the study's own subject rather than `adaptive traffic signal control`. `SCENARIO` keeps only what no plan chooses — the two compositions, the fallback venue and the dataset file.
- **A plan is not yet durable, and no deployment-facing config states one** (2026-09-15): a run takes its plan from `DriveOptions.studyPlan`, or from the default with `domainDirection` replacing that default's direction; `dsh-research-cordis`'s `Config` carries no plan field yet. A **resume** rebuilds the plan's CLAIM half from the artifacts the run already records (claim id, reference, prediction, metric key, commitment), but the title, the field, the direction and the outline are in no artifact, so a resumed run takes those four from the plan the resuming deployment supplies. For the default plan that is exact; for a deployment that states its own and resumes another's, it is not. Persisting the plan belongs with the change that lets a person supply one.
- **Every prose request carries the run's subject** (2026-09-15): each `proseWriter.write` request spreads `planContextOf(plan)` — the field and the direction — into its `context`, and D2 derives its section headings from `plan.outline` rather than from a `DEFAULT_HEADING` table. Without the second, a plan that renamed a section would have kept the old name.

- **The prediction gate is separate from the study, and the measured quantity is a parameter** (2026-09-15): `runner/prediction-gate.ts` holds the discipline that decides whether a claim can be graded at all — binding the claim to a quantity the study measures, checking the anchor and the direction word it wrote against the commitment it declared, and holding on a negation — and takes that quantity as a parameter (`MeasuredMetric`: the declared key, the display label, whether a larger value is better, and the phrasings a claim must actually use). It lived in `runner/platoon-sim.ts` until then, beside a car-following model, so a study from any other field would have had to import a traffic module to reach it. The study now hands its measurement in through `PredictionGateInput.measure`, a callback the gate calls only after every claim-level check has passed, which is the property that keeps a broken measurement from masking a wording defect. **The parameterization is exercised by a synthetic latency metric in `tests/prediction-gate.spec.ts`, not by a second shipped study**: no other study exists in this tree yet, so "a study from another field reaches this discipline" is proven at the gate's own interface rather than end to end.
- **Grading the direction word against the study's sign alone was a `higher-is-better` assumption** (2026-09-15): the gate computed `inClaimDirection` from the improvement's sign directly, so a "shall lower the latency" claim on a lower-is-better quantity was graded as asking for the opposite and reported refuted by a measurement that met it. It reads `MeasuredMetric.direction` now; the platoon case is unchanged, because its direction is `higher-is-better` and the two readings agree there. The defect was found by the synthetic-metric case above, not by the shipped study.

- **There are 5 truthfulness tiers** (`local_computation` added 2026-09-14). The 16 steps divide as follows:
  - `real_tool_fixture_input` (5 steps, the tool functions really execute): A1 / A2 / C3 / D1 / E1;
  - `local_computation` (5 steps, no tools and no external systems, a real measurement computed by this package's own code): A4 / B2 / B3 / C1 / C2;
  - `fixture_executor` (5 steps, the default path): A3 / B1 / D2 / D3 / D4 — with a `proseWriter` present these five go through that writer's channel: `channel: 'llm'` is recorded as `live_external`, and the deterministic channel of the shipped assembly is recorded as `mock_external`, with the label decided by one rule in `proseLabelling`;
  - `humanGate` (1 step): E2. That boundary is locked by assertions in `tests/t34-single-step.spec.ts` and `tests/runner-registry.spec.ts`. **Why this tier was added**: the report printed `real_tool_fixture_input` as "Real tool functions executed", while B3/C1/C2 execute no tool function at all — hanging them on that tier amounts to making the report state a falsehood.
- The tier an artifact declares for itself (the artifact's `__kind`) is the source of `StepOutcome.kind` when every artifact of that step agrees; a static registry entry cannot know deployment facts (A1 reaches a live catalogue only when a real channel is configured).
- **A4-venue now derives its venue choice from the retrieval corpus** (2026-09-14): `landscape-map` joins A4's declared inputs (`dsh-research-core/src/engine/steps.ts`), and the executor takes the `venue` occurring most often in the retrieval records as the target journal, with the count and the selection method written onto the artifact. **The criterion for scope matching is still declaration**, because this study does read the journal's submission guidelines — the artifact states this with `scopeSource: 'declared'`. With that, **every one of the 16 steps has an artifact derived from its inputs**.
- **The experiment is a platoon car-following simulation, not a table lookup** (swapped 2026-09-14): `runner/platoon-sim.ts` integrates two platoons with IDM (Treiber/Hennecke/Helbing 2000) at the declared fixed time step — an all-HV baseline and an HV–AV–HV variant — takes the leader's delayed state from a ring buffer for the reaction delay, and reports minimum TTC, mean headway, mean jerk, and a string-stability index, all computed from the trajectories. **There is no fixture table, and no lookup by claim id.**
- **Before this round it measured a different study**: the C channel used to measure a signalised intersection with Webster's delay formula, while the shipped Case Pack is about a platoon — C1's artifact says so itself: `doesNotMeasure: 'platoon car-following risk …'`. That line (`traffic-sim.ts`, `study-demand.ts`, `demand-profile.ts`, the SUMOP verification script with its generator and spec) has been retired, and intersection demand derivation no longer has a consumer.
- **The two mechanisms are separate, and each can be ablated independently**: reaction delay (the leader's past state) and prediction (extrapolating the observed state forward by a horizon) are two different things. The first version **subtracted** the horizon from the delay, so the two "separable mechanisms" were really two points on the same scalar axis — an audit proved it with bit-identical trajectories for `{reaction:0.15,horizon:0.15}` and `{reaction:1.2,horizon:1.2}`, and the sentence "the AV predicts 0.15 s ahead" in the Method section described nothing at the time.
- **The baseline is a homogeneous platoon, not a fixed-time signal plan**: the baseline is HV–HV–HV and the variant is HV–AV–HV. The numbers are model output rather than measurement; the two platoons are compared inside one model, so the "comparison" is a measurement while the "absolute values" are not.
- **The production assembly point for `proseWriter` already exists** (corrected 2026-09-14): `Config.prose` in `dsh-research-cordis` constructs an `LlmProseWriter`, `ResearchTeamService.hostProseWriter()` reads `ctx.research.proseWriter` and hands it to `DriveOptions`, and the shipped bundle's `research-cordis` row configures it too (`deepseek-official` / `deepseek-v4-pro`). The earlier note that there was "no assembly point yet" was already inaccurate at the time. **What remains unverified is that this chain runs against a real model** — that path needs credentials for the route, and this checkout has not done a live re-verification.
- `runner/registry.ts` is a single file of roughly 2250 lines carrying four kinds of responsibility at once — the type vocabulary, fixed data, 15 executors, and the audit projection — and splitting it is recognized debt.
- **This package's tests are now covered by the host aggregate** (fixed 2026-09-14): the four host-face research test globs have been moved out of `tsconfig.host.json`'s `exclude`, and `tsc -b tsconfig.host.json` reads them. Moving them out exposed **159 type errors**, all now fixed — and not all of them were mechanical (a type-only import pointing at a module that does not exist, a helper importing a member that was never exported, and an `isComplete` call with the wrong argument count). `dsh-research-web/tests/**` **must stay in `exclude`** — it is the client face, and including it would drag browser sources into the host program. See `.agents/notes/implemented/testing/2026-09-14-research-tests-join-the-typecheck-aggregate.md`.
- **`pnpm run lint` is still red for the research packages (it was red before the change)**: 299 errors measured before the change, 155 once the tests joined the aggregate, of which the 62 in research `src/` are untouched by that change and are pre-existing; the remaining 90 test-side errors are genuine rule violations (unsafe assignments caused by `any` from dynamic imports, and the like) and are left to a separate change.

No invariant companion is published: the team fold and authorization relations are asserted by this package's own revision, projection and scope specs, and independent observers cannot diverge here, so no `./invariant` entry is published alongside it.

- **`runPipeline` is the Remote exit** (2026-09-14): `ResearchTeamService` extends `TypertRemoteService`, and `@Remote('run')` is declared under the wire namespace `research` (the service key remains `agentTeams`). What it returns is a **snapshot** — the run itself plus the 16-step catalogue, every gate verdict (with evidence/rationale), artifact metadata, and each step's attempt and holdReason — rather than a `RunResult`, because neither the catalogue nor the evidence lives in `RunResult`, and a client could only rebuild them by inventing them. The package `exports` therefore gains the three subpaths `./types`, `./typert`, and `./remote`.
- **The human-approval wiring is in `src/approval.ts`** (2026-09-14): `E2-submit` is the only `humanGate` step, core exposes the channel that can turn `gated` into `passed` only through `@deepseek-ai/dsh-research-core/host`, and this file is its caller. After `runPipeline` finishes it hands the run's store and re-projection function to `rememberRun`; the `decide` endpoint of the `/research-approval` approval channel then checks run / step / `humanGate` / current `gated` status / **current attempt** item by item, and only then lets core write the `ApprovalRecord` and the `human-approval` audit event through `HostApprovalChannel.submit`. **Identity is not taken from the request body**: registration goes through `ctx.connection.rpc.handle`, and the host performs browser authentication on its own route first (an HMAC-signed session cookie whose origin is the process token `dsh web` prints); only the four fields `runId` / `stepId` / `attempt` / `decision` are read from the request body, and `actor` / `status` / `principalId` are never read. As with core's `./host`, **this is not process-level isolation**: code in the same process that already holds a `Context` can still call it directly; real isolation would need IPC identity, which a JavaScript API cannot provide.
- **The approval surface is not exported from the package entry** (2026-09-14): `src/approval.ts` deliberately does not join `index.ts`'s re-export list, and `ResearchTeamService` carries no corresponding Remote method. An ordinary tool call therefore has no name to point at, and the decision can arrive only through that authenticated route.
- **The build order is order-sensitive**: `clean` in `tsdown.config.ts` must list **only the files this package genuinely produces**. The Client pass runs with the same config after the Host pass, and a `lib/*.js` wildcard would delete the `typert.host.js` / `typert.remote-client.js` that the Host pass generated, which the Client pass will not regenerate.
