# @deepseek-ai/dsh-research-team

English | [中文](README.zh.md)

The `ctx.agentTeams` service and the T19-B runner: the red-team fleet, the task board with CAS revisions, the write-scope guard, the session projection, and the executor registry (`runner/`) that drives the 16 steps.

The layering is explicit: a pure-logic layer (`types` / `revision` / `projection` / `scope-guard` / `roster` / `redteam` / `anchor` / `experiment`) → a thin adapter layer (`journal` / `task-board` / `session-events` / `research-projection` / `research-guard`) → `index.ts` as the single wiring point (service declaration, `SessionEventMap` injection, `ctx.effect` lifecycle).

`runner/registry.ts` is the audit source of truth for the 16-step executors: each entry declares `stepId` / `executor` / `producer` / `truthfulness` / `timeoutMs` / `gateRequirement` / `recoveryPolicy`, and both the input/output schemas and the gate requirements are derived from core's frozen definitions so they cannot drift from the 16-step definition.

## Known Limitations and Deferred Work

- **The prediction gate is separate from the study, and the measured quantity is a parameter** (2026-09-15): `runner/prediction-gate.ts` holds the discipline that decides whether a claim can be graded at all — binding the claim to a quantity the study measures, checking the anchor and the direction word it wrote against the commitment it declared, and holding on a negation — and takes that quantity as a parameter (`MeasuredMetric`: the declared key, the display label, whether a larger value is better, and the phrasings a claim must actually use). It lived in `runner/platoon-sim.ts` until then, beside a car-following model, so a study from any other field would have had to import a traffic module to reach it. The study now hands its measurement in through `PredictionGateInput.measure`, a callback the gate calls only after every claim-level check has passed, which is the property that keeps a broken measurement from masking a wording defect. **The parameterization is exercised by a synthetic latency metric in `tests/prediction-gate.spec.ts`, not by a second shipped study**: no other study exists in this tree yet, so "a study from another field reaches this discipline" is proven at the gate's own interface rather than end to end.
- **Grading the direction word against the study's sign alone was a `higher-is-better` assumption** (2026-09-15): the gate computed `inClaimDirection` from the improvement's sign directly, so a "shall lower the latency" claim on a lower-is-better quantity was graded as asking for the opposite and reported refuted by a measurement that met it. It reads `MeasuredMetric.direction` now; the platoon case is unchanged, because its direction is `higher-is-better` and the two readings agree there. The defect was found by the synthetic-metric case above, not by the shipped study.

- **There are 5 truthfulness tiers** (`local_computation` added 2026-09-14). The 16 steps divide as follows:
  - `real_tool_fixture_input` (5 steps, the tool functions really execute): A1 / A2 / C3 / D1 / E1;
  - `local_computation` (5 steps, no tools and no external systems, a real measurement computed by this package's own code): A4 / B2 / B3 / C1 / C2;
  - `fixture_executor` (5 steps, the default path): A3 / B1 / D2 / D3 / D4 — with a `proseWriter` present these five go through that writer's channel: `channel: 'llm'` is recorded as `live_external`, and the deterministic channel of the shipped assembly is recorded as `mock_external`, with the label decided by one rule in `proseLabelling`;
  - `humanGate` (1 step): E2. That boundary is locked by assertions in `tests/t34-single-step.spec.ts` and `tests/runner-registry.spec.ts`. **Why this tier was added**: the report printed `real_tool_fixture_input` as "Real tool functions executed", while B3/C1/C2 execute no tool function at all — hanging them on that tier amounts to making the report state a falsehood.
- The tier an artifact declares for itself (the artifact's `__kind`) is the source of `StepOutcome.kind` when every artifact of that step agrees; a static registry entry cannot know deployment facts (A1 reaches a live catalogue only when a real channel is configured).
- **A4-venue now derives its venue choice from the retrieval corpus** (2026-09-14): `landscape-map` joins A4's declared inputs (`dsh-research-core/src/engine/steps.ts`), and the executor takes the `venue` occurring most often in the retrieval records as the target journal, with the count and the selection method written onto the artifact. **The criterion for scope matching is still declaration**, because this study does read the journal's submission guidelines — the artifact states this with `scopeSource: 'declared'`. With that, **every one of the 16 steps has an artifact derived from its inputs**.
- **The experiment is a platoon car-following simulation, not a table lookup** (swapped 2026-09-14): `runner/platoon-sim.ts` integrates two platoons with IDM (Treiber/Hennecke/Helbing 2000) at the declared fixed time step — an all-HV baseline and an HV–AV–HV variant — takes the leader's delayed state from a ring buffer for the reaction delay, and reports minimum TTC, mean headway, mean jerk, and a string-stability index, all computed from the trajectories. **There is no fixture table, and no lookup by claim id.**
- **Before this round it measured a different study**: the C channel used to measure a signalised intersection with Webster's delay formula, while the shipped Case Pack is about a platoon — C1's artifact says so itself: `doesNotMeasure: 'platoon car-following risk …'`. That line (`traffic-sim.ts`, `study-demand.ts`, `demand-profile.ts`, the SUMOP verification script with its generator and spec) has been retired, and intersection demand derivation no longer has a consumer.
- **The two mechanisms are separate, and each can be ablated independently**: reaction delay (the leader's past state) and prediction (extrapolating the observed state forward by a horizon) are two different things. The first version **subtracted** the horizon from the delay, so the two "separable mechanisms" were really two points on the same scalar axis — an audit proved it with bit-identical trajectories for `{reaction:0.15,horizon:0.15}` and `{reaction:1.2,horizon:1.2}`, and the sentence "the AV predicts 0.15 s ahead" in the Method section described nothing at the time.
- **The baseline is a homogeneous platoon, not a fixed-time signal plan**: the baseline is HV–HV–HV and the variant is HV–AV–HV. The numbers are model output rather than measurement; the two platoons are compared inside one model, so the "comparison" is a measurement while the "absolute values" are not.
- **The production assembly point for `proseWriter` already exists** (corrected 2026-09-14): `Config.prose` in `dsh-research-cordis` constructs an `LlmProseWriter`, `ResearchTeamService.hostProseWriter()` reads `ctx.research.proseWriter` and hands it to `DriveOptions`, and the shipped bundle's `research-cordis` row configures it too (`deepseek-official` / `deepseek-v4-pro`). The earlier note that there was "no assembly point yet" was already inaccurate at the time. **What remains unverified is that this chain runs against a real model** — that path needs credentials for the route, and this checkout has not done a live re-verification.
- `runner/registry.ts` is a single file of roughly 2250 lines carrying four kinds of responsibility at once — the type vocabulary, fixed data, 15 executors, and the audit projection — and splitting it is recognized debt.
- **This package's tests are now covered by the host aggregate** (fixed 2026-09-14): the four host-face research test globs have been moved out of `tsconfig.host.json`'s `exclude`, and `tsc -b tsconfig.host.json` reads them. Moving them out exposed **159 type errors**, all now fixed — and not all of them were mechanical (a type-only import pointing at a module that does not exist, a helper importing a member that was never exported, and an `isComplete` call with the wrong argument count). `dsh-research-web/tests/**` **must stay in `exclude`** — it is the client face, and including it would drag browser sources into the host program. See `.agents/notes/implemented/testing/2026-09-14-research-tests-join-the-typecheck-aggregate.md`.
- **`pnpm run lint` is still red for the research packages (it was red before the change)**: 299 errors measured before the change, 155 once the tests joined the aggregate, of which the 62 in research `src/` are untouched by that change and are pre-existing; the remaining 90 test-side errors are genuine rule violations (unsafe assignments caused by `any` from dynamic imports, and the like) and are left to a separate change.

No invariant companion is published: the team fold and authorization relations are asserted by this package's own revision, projection and scope specs, and independent observers cannot diverge here, so no `./invariant` entry is published alongside it.

- **`runPipeline` is the Remote exit** (2026-09-14): `ResearchTeamService` extends `TypertRemoteService`, and `@Remote('run')` is declared under the wire namespace `research` (the service key remains `agentTeams`). What it returns is a **snapshot** — the run itself plus the 16-step catalogue, every gate verdict (with evidence/rationale), artifact metadata, and each step's attempt and holdReason — rather than a `RunResult`, because neither the catalogue nor the evidence lives in `RunResult`, and a client could only rebuild them by inventing them. The package `exports` therefore gains the three subpaths `./types`, `./typert`, and `./remote`.
- **The human-approval wiring is in `src/approval.ts`** (2026-09-14): `E2-submit` is the only `humanGate` step, core exposes the channel that can turn `gated` into `passed` only through `@deepseek-ai/dsh-research-core/host`, and this file is its caller. After `runPipeline` finishes it hands the run's store and re-projection function to `rememberRun`; the `decide` endpoint of the `/research-approval` approval channel then checks run / step / `humanGate` / current `gated` status / **current attempt** item by item, and only then lets core write the `ApprovalRecord` and the `human-approval` audit event through `HostApprovalChannel.submit`. **Identity is not taken from the request body**: registration goes through `ctx.connection.rpc.handle`, and the host performs browser authentication on its own route first (an HMAC-signed session cookie whose origin is the process token `dsh web` prints); only the four fields `runId` / `stepId` / `attempt` / `decision` are read from the request body, and `actor` / `status` / `principalId` are never read. As with core's `./host`, **this is not process-level isolation**: code in the same process that already holds a `Context` can still call it directly; real isolation would need IPC identity, which a JavaScript API cannot provide.
- **The approval surface is not exported from the package entry** (2026-09-14): `src/approval.ts` deliberately does not join `index.ts`'s re-export list, and `ResearchTeamService` carries no corresponding Remote method. An ordinary tool call therefore has no name to point at, and the decision can arrive only through that authenticated route.
- **The build order is order-sensitive**: `clean` in `tsdown.config.ts` must list **only the files this package genuinely produces**. The Client pass runs with the same config after the Host pass, and a `lib/*.js` wildcard would delete the `typert.host.js` / `typert.remote-client.js` that the Host pass generated, which the Client pass will not regenerate.
