# @deepseek-ai/dsh-research-team

English | [中文](README.zh.md)

The `ctx.agentTeams` service and the T19-B runner: the red-team fleet, the task board with CAS revisions, the write-scope guard, the session projection, and the executor registry (`runner/`) that drives the 16 steps.

The layering is explicit: a pure-logic layer (`types` / `revision` / `projection` / `scope-guard` / `roster` / `redteam` / `anchor` / `experiment`) → a thin adapter layer (`journal` / `task-board` / `session-events` / `research-projection` / `research-guard`) → `index.ts` as the single wiring point (service declaration, `SessionEventMap` injection, `ctx.effect` lifecycle).

`runner/registry.ts` is the audit source of truth for the 16-step executors: each entry declares `stepId` / `executor` / `producer` / `truthfulness` / `timeoutMs` / `gateRequirement` / `recoveryPolicy`, and both the input/output schemas and the gate requirements are derived from core's frozen definitions so they cannot drift from the 16-step definition.

## Known Limitations and Deferred Work

- **A check that refuses a re-export must let the re-export through once the move was reviewed** (2026-09-17, R06): `artifacts-current` failed whenever the artifacts a previous package was read from had moved, and its own detail said what to do about it — `re-export to describe the run as it stands`. **The remedy could not be taken**: the versions handed to a re-export come from the package ON DISK, and a package whose artifacts have moved describes an older state by construction, so `moved` was never empty and 'differs from the previous export' was permanently illegal — a run that moved, was re-checked and was re-approved still could not produce a final package. The check now passes when the approval the package carries still covers the run as it stands (`approval !== undefined && staleApproval === undefined`), because an approval names the artifact versions it was taken on and is therefore exactly the evidence that the move was re-examined; the passing case says so instead of reporting a clean bill. **The refusal still holds both ways that matter** — no approval, or an approval that no longer covers the run, fails `approval-recorded` / `approval-current` and this check with them. **What is not here**: a caller cannot ask for a package of an EARLIER revision, so 'a late export of an old version' is reachable only as a move without a matching approval.

- **The deliverables are DOCX and LaTeX; PDF is a deployment extra** (2026-09-17): `CompileFormat` gained `docx`, and `PandocCompiler` offers `html` / `latex` / `docx` whenever pandoc answers — **DOCX needs no engine of its own**, since pandoc writes the whole OOXML package with the figures embedded and the equations as OMML. PDF is still offered only when a LaTeX engine was probed. E1 **always** requests the three deliverables (so a deployment with no compiler still reaches its artifact with `compile-compiler-missing`, and a reader can tell 'not compiled' from 'compiled badly') and asks for PDF only when the deployment's own probe says it can produce one. Acceptance: `tests/pdf-acceptance.spec.ts` writes a DOCX with the real pandoc and reads its parts back (ZIP signature, `word/document.xml`, a `word/media/` entry, the section text really in the package), and checks the LaTeX carries `\documentclass` and its body. **A defect was reported here and WITHDRAWN**: a LaTeX document whose prose named its figure looked like it came back without a body, and the cause was the test's own fixture — `documentOf` attaches floats to the SECTION CALLED `results`, and the fixture had put the figure in a section that never carries one, so the figure was simply not in the document. Re-measured with the float where the assembler puts it: the LaTeX carries `\includegraphics`, the caption and the body, `assets.embedded` names the figure and `assets/figure-1.png` is in the package. What the probe DID refute is the `file://` form, which is worse — pandoc cannot fetch it for a local image — so the plain absolute path stays.

- **The PDF is read page by page, on a real engine** (2026-09-17, R01): a real TeX Live is installed on this host (CTAN, `scheme-minimal` + `pdftex` + pandoc's template packages) at `.workbuddy/tmp/texlive/tex` — a deployment toolchain outside the tracked tree, with **no path to it committed**. E1 now compiles `pdf` **when the deployment can produce one**, from the compiler's own probed `formats`, so a machine with no engine is never asked for a PDF it would refuse; the three formats render from the SAME document model. `tests/pdf-acceptance.spec.ts` compiles through the seam's own entry point and then **reads the pages with a real parser**: header, more than one page, page 1 carrying the first section's heading and text, page 1 NOT carrying the second section's text while a later page does — the pair that separates a real document from a file whose pages are empty or repeated. Measured: pandoc 2.12 → pdfTeX 3.141592653-2.6-1.40.29 (TeX Live 2026) → a multi-page PDF. The case is `describe.skipIf` on an installed engine, so it says skipped rather than passing silently. **What is not here**: no package built by the shipped profile has been compiled to PDF (the profile names no engine), and 'the figure is on page 3' is not asserted.

- **The drawing is a seam the deployment fills, and a diagram is a picture** (2026-09-17, R05②/R02): `runner/figure-provider.ts` states `FigureProvider` — an id, the library version, `renderFigure(spec)` and `renderDiagram(graph)`, both returning SVG **and** base64 PNG from one render — and `dsh-research-cordis/src/matplotlib-provider.ts` is the deployment's: it runs a bundled script through the interpreter the deployment names, checks that the answer really is an SVG and really begins with the PNG signature, and is **probed** at construction so a machine without the library offers no provider instead of failing at D1. Configured like the compiler (`Config.figures` → engine probe → `hostFigureProvider()` → `DriveOptions.figureProvider`). D1 draws the chart AND the roadmap through it, and every float records `drawnBy` / `drawnByVersion`; with no provider the built-in renderer draws and the diagram float records `diagramDrawn: false` — the honest state, not a dropped float nobody names. Verified against matplotlib 3.11.2 in a venv (the real cases are `describe.skipIf` on an interpreter this host has). E1 CARRIES THE DRAWING INTO THE DOCUMENT: a roadmap the provider drew is a figure with both renderings, not Mermaid source, so every compiled format embeds it and `compilation.documents` carries the binary deliverables (`.docx`, `.pdf`) apart from the figures they embed. **What is not here**: the shipped profile names no interpreter (`Config.figures` is documented there as an opt-in, because which machine has the library is a deployment fact), and `pdf` is still refused because no LaTeX engine is installed.

- **A citation's judgement is about a version of a sentence, not about a slot** (2026-09-17, R05): `CitationUse.statementId` documented the property this layer needed — a revision that rewrites the sentence should invalidate the citation — and the value it was given was the constant `introduction:prior-work`, which every draft of every run shared. **Two things were wrong and only one was the constant**: the bindings were also made BEFORE the prose existed (`citationUsesOf({claimRef, statementId})` at the top of D3), so the only thing a binding could name was a slot. Now four things are recorded separately — the NODE's identity (`Statement.statementId`, minted from the section and the sentence's ordinal among CITED sentences, so a rewrite keeps the node and an inserted uncited sentence shifts nothing), the CONTENT VERSION (`Statement.textSha256`), the EVIDENCE VERSION (`CitationUse.quoteSha256`) and the JUDGEMENT, which records the content version it was made about. The order changed with them: `judgementsFor(claimRef)` returns what the reviewed corpus establishes UNATTACHED, D3 writes the sections, `locateStatements` finds where each cited sentence is (locating, not identifying), and `bindJudgements` attaches each judgement to the statement that cites its source. `checkStatementBindings` refuses `citation-statement-missing` / `citation-statement-changed` / `citation-evidence-changed`, and **re-binding is not the remedy for any of them** — a judgement is a reading somebody made, and only another reading can replace it. A reviewed source no sentence cites is refused at D3 (`citation-source-uncited`) rather than dropped from the list. **R05③'s log**: the draft records `proseRequests` (the instruction verbatim, the evidence required and supplied, the citation roster with each passage's version), so a judgement refused for a changed passage is traceable to the request that was answered with a sentence resting on it. **A CITATION IS A SENTENCE, NOT A SOURCE** (2026-09-18, the pipeline review's P0): `bindJudgements` kept a set of cite keys and skipped any it had already bound, so a source cited in the introduction and again in the discussion produced a binding for the first and NONE for the second — every check that reads bindings then had nothing to read for the rest of the manuscript. It now emits one binding per citing sentence, each carrying that sentence's own content version, sorted into document order within a key. The other direction is checked too: `checkStatementBindings` refuses `citation-statement-unbound` for a sentence that cites a source no binding covers, because a set of bindings can be entirely sound while a sentence has none. `checkCitationKeys` changed with them — a key names ONE SOURCE (that is still refused), not one citation (two sentences citing one source is what a paper does). **A citation's support is about the SENTENCE, not the claim it came from** (2026-09-18, the pipeline review's second citation gap): `evidence-corpus.ts` records what a reviewer concluded about a CLAIM, and the binding layer attached that verdict to whichever sentence cited the source — so a sentence nobody had read inherited a `supported` it had not earned. `runner/statement-support.ts` is the seam that ends it: `StatementAssessment` records the sentence's own identity and content version, the source, the verdict about THAT sentence, what the verdict rests on and who made it, and `StatementSupportAssessor` is the deployment's ability to read one — the same shape as the prose writer and the figure provider. D3 assesses every citing sentence when the deployment has an assessor and REFUSES `statement-unassessed` / `statement-contradicted` / `statement-unrelated` / `statement-beyond-scope`; E1 re-checks the REVISED manuscript, so a revision that rewrote a sentence without re-reading it is refused where the manuscript is published. A deployment with no assessor records nothing rather than inheriting: the draft carries NO `statementAssessments` field, and its absence is the fact — `[]` would say the readings were made and found nothing, which is the reading this removes. **What is not here**: the assessor itself is the deployment's; the shipped bundle names none, so the shipped runs still carry the claim's verdict on their bindings and say no sentence was read. **What is not here**: the judgement itself is still a recorded verdict rather than a re-derivation, who re-reads is a person or the deployment's reviewer, and the model-visible log lives on the run's artifacts — a session event is not added.

- **A quality result says what could be read, not only what was found** (2026-09-17, R04): `runner/paper-quality.ts` gained `reportPaperQuality(input)`, and the package manifest carries its `quality` in place of the bare `qualityFindings` list. **An empty finding list is the output of the five exact rules that could read the manuscript, and it reads as a verdict on the paper** — the review rejected that reading in as many words. The report separates the four facts the empty list collapsed: one `QualityCheck` per rule with `no-defect-found` / `defect-found` / `not-applicable` / `not-executed` and the reason when a rule could not answer (no bibliography, no sentence stating the measured change, no float roster, no draft), `needsDomainReview` naming the questions no rule here answers (is the claim worth testing, does each cited source say what the sentence claims, are the figures legible, does the prose claim more than the measurement supports), and a `summary` that states what the report IS — `no defect found by the 3 check(s) that could read this manuscript; 2 check(s) could not run, and 5 question(s) need a domain reviewer` — never that the paper is good. `reviewPaperQuality` stays as the findings-only view the rule-by-rule specs drive. **What is not here**: the coverage list says which of THESE five rules could read the manuscript, not what other checks a paper needs, and the domain questions are named and not answered — recording a reviewer's answer against an item id is not built.

- **A study presents itself, and the four steps that report one stop naming it** (2026-09-17): `runner/study-adapter.ts` holds `StudyAdapter` — the executable method, the two arms by name and identity, the producers `B3` and `C1` stamp, the source the numbers came from, the measurement (record, gate input, rule version and sequence, from ONE execution), the provenance block every experiment artifact attaches, the presentation (figure plan, renderer spec, table, diagram), the boundary `C3` ablates, the sentence stating what the measurement did to the claim, and the fallback prose for each section — and the run context carries it, resolved from the plan before the first step and rebuilt by `A2-claim` (through `setRunStudy`) when the Case Pack supplies the study's own scenarios. **The second study now runs**: `LATENCY_PLAN` (a single server, `p95-latency-ms` in milliseconds, LOWER is better, over a declared arrival trace) drives all sixteen steps to the human gate and stops there — `tests/second-study-run.spec.ts` — where before it stopped at `D1-figure-map`, because four executors each knew the platoon study by name. **A sequence is a first-class shape**: `StudySeries` travels inside the result record, `sequencePresentationPlan` plots it over a `sequence` axis with points addressed by position (`series.arms.baseline.3`), and the record's content hash covers it, because two records whose arms agree and whose observations differ are two measurements. **Two gate defects fell out of the same change**: the A channel's wording checks read every claim against the platoon's phrasings, so a claim about any other quantity had none, every check abstained, and a well-stated claim was held; and the C channel graded every claim with `measureStudy(ctx.runCtx.study)` whatever study the run was conducting. **Generalizing exposed four more**: a load factor in the fallback prose is a number the run never declared, and the number check refuses it; a `D4` revision patch and an `E1` table note carried platoon sentences into any study's manuscript; the verdict's `evaluator` line named the platoon module for every run. **What is not here**: `SCENARIO.venueName`/`venueId` are still deployment constants read by `A1`/`A4`/`E1`, `A3-agenda`'s claim-and-evidence text is still platoon-flavoured fixture prose, and the figure renderer is still this repository's own tool.

- **A compiled document says which floats it carries, and a package whose compiled document lost one is not final** (2026-09-17, R01/R02): the compile reports `assets.embedded` and `assets.dropped` per format, the manuscript artifact records them (`compilation.floatsEmbedded` / `floatsDropped`), the embedded figures travel into the package as BYTES (`PackageFile.encoding: 'base64'`, so a PNG is written as a PNG and its digest is over the bytes that landed), and `checkFinalPackage` gained `compiled-document-complete`: a package cannot be final while the compiled document does not carry a float the manuscript has, because a submission whose figures are missing is not the paper. A deployment that compiles nothing is not held to it — its manuscript is complete as Markdown and its artifact says it was not compiled. The package also carries `figure-plan.json`, so a figure can be reproduced from the plan it was drawn from rather than merely found in the package. `compilation.documents` carries the binary deliverables themselves (`.docx`, `.pdf`) separately from `compilation.assets`, which carries the figures they embed — a reader looking for the manuscript a journal receives must not find it under the things the document carries. **What this does not cover**: a deployment that names no drawing provider still has a roadmap whose only form is Mermaid, so its compiled document does not carry `Figure 2` and the package stays a draft — which is the honest state for that deployment, not a check to relax.

- **A package names the artifact versions it is a reading of, and a re-export over a moved run says so** (2026-09-17): the manifest carries `artifactRefs` (one entry per artifact the export read, with the version the run held), and `checkFinalPackage` gained `artifacts-current`: when a later export is handed the versions the package on disk was read from (`previousArtifactRefsOf(directory)`, wired into `@Remote('exportRunPackage')`), the checks name which artifacts the run has moved past, and the package is a DRAFT whatever else holds. **An export is a reading of one state** — a later step, a revision, a re-run or a hand edit replaces an artifact, and a package still calling itself final would be attesting to a document the run no longer holds. The check also covers the late-render case from the other side: a compile or an export that lands after the run moved describes the state it read and is refused as final rather than overwriting the reader's picture of it. **What this does not cover**: the check compares the versions the PREVIOUS manifest named, so a package exported once and never compared has nothing to compare against — its `artifacts-current` entry reports what it was read from rather than a verdict it cannot support; and the artifact-level dependency graph (which step's artifact invalidates which) is core's, tested there, not restated here.

- **A float nothing refers to, and a title that claims the finding the study refuted, are refused at the gate** (2026-09-17): `red-citation` now refuses a draft that CARRIES a float its prose never names — the delivered paper carries six (Figure 1, Figure 2, Table 1 and three equations) with no sentence referring to any, which is what a float nobody needed looks like — and `red-claim` refuses a title that asserts a direction the measurement contradicts. The delivered paper's title is `Raising Minimum Time-to-Collision in Three-Vehicle Platoons …` above a manuscript reporting that the quantity FELL by 38.2%: the headline asserts the finding the study refuted, and a reader who stops at the title has read the opposite of the result. Both rules name what they found (`floats no sentence refers to: …`, `the headline asserts the finding the study refuted`). **The pipeline's own output now passes both**: the sections name the floats they carry (the Results section points at the figure and the table, the Method section at the equations), so the package's `qualityFindings` is EMPTY for the shipped run and for the second task — where the same baseline used to report six unreferenced objects and no literature position. **The baseline reads both citation syntaxes**: a draft carries `[@citeKey]` and the assembled manuscript carries the numbers E1 assigned, so a rule that knew only `[1]` reported this run's Introduction as citing nothing — two findings against a paper that cites three sources. **What is not here**: the title rule reads direction words, not meaning — a title asserting a finding in words outside the declared vocabulary passes, and whether a title is *good* takes a reader.

- **The manuscript is a document, and compiling it is a seam the deployment fills** (2026-09-17): `runner/document-compile.ts` states the manuscript as parts — sections with typed blocks (prose, figure with its own SVG, table as markdown, diagram as mermaid, equation as LaTeX), references keyed the way the prose cites them and numbered once — so the HTML, the LaTeX and any later backend render the same document rather than three readings of one assembled string. `checkCompileRequest` refuses a deployment that configured no compiler (`compile-compiler-missing`), a format the compiler cannot produce on that deployment (`compile-format-unavailable`, which is what a machine with no LaTeX engine answers for `pdf`), a document with no sections, and a citation the bibliography does not carry (`compile-citation-unresolved`) — the last one BEFORE the compiler runs, because a compiler renders an unresolved citation with a warning in a log nobody reads. `compileManuscript` writes nothing: the content comes back for the caller to stage and publish, so a compile that fails cannot have destroyed what a previous export wrote. E1 compiles `html`, `latex` and `docx` through the injected compiler (`pdf` too when the deployment's engine probe found one) and records `compilation` (tool, formats, compiled files, documents and assets as bytes, refusals) on the artifact, so a reader of a package can tell "not compiled" from "compiled badly". **What is not here**: the compiler the shipped bundle wires drives `pandoc` (see `dsh-research-cordis`), and no PDF is produced anywhere yet; the document model is deliberately thin — paragraphs carry text, and a statement-level model (M04's contracts over sentences) is what M08 will render from.

- **A figure is planned before it is drawn, and its values are reconciled with the run** (2026-09-17): `runner/presentation-plan.ts` holds `PlannedFigure` — the QUESTION the figure answers, the run record its values come from, its series as `{key, value}` pairs naming the record's fields, its axes and units, any uncertainty, its own canvas size and format, its caption, and whether the paper needs it — and `PresentationPlan`, which carries a version. **D1 used to render one bar chart with a fixed 320×240 canvas, a fixed title and one series, and nothing said what it was FOR**: the delivered paper carries six floats no sentence refers to, which is what a float that answers no question looks like. The plan is now built first and the renderer is handed its spec, so the chart a reader gets and the question somebody wrote down are one object. **Source-data reconciliation is a check**: every value a figure plots must be the value the run recorded under the key it names, in the record it names, so a figure cannot illustrate a measurement nobody made — a drifted record is refused with `figure-values-unsourced` rather than drawn from a literal, and a step driven alone names `recomputed-measurement` as its source so a reader can tell which of the two happened. The other refusals are `figure-no-question` (a float that answers nothing is decoration), `figure-sequence-missing` (a chart over a sequence axis whose points are not positions in one draws a trend no measurement established), `figure-interval-missing` (a band nobody computed is an uncertainty claim the run did not make), and `figure-duplicate-id`. **What is not here**: the renderer is still this repository's own SVG/PNG tool, not the Matplotlib provider the plan recommends — Python 3.14 is on this host and Matplotlib is not installed, so no provider that needs it is wired, and the figure's typography and styling are the ones the built-in renderer has; a figure's legibility and its agreement with the prose are the visual review's work (M09), not judged here.

- **A section is written against what it owes, and a refutation has to be reported as one** (2026-09-17): `runner/argument-plan.ts` holds `SectionContract` — the section's JOB, the evidence without which it cannot be written, and the obligations it must discharge — and `ArgumentPlan`, which is derived from the run: the question, the claim, and `claimOutcomeOf(measuredPct, committedDirection, thresholdPct)`, which says whether the measurement SUPPORTED the claim, REFUTED it, or fell short of the threshold. **The shipped run refuted its own claim** (−38.2% against a prediction of at least +20%) and no section of its manuscript said so, which is what this unit is for: when the outcome is `refuted`, the sections that report it are obliged to state the measured change, the direction in words, AND that the measurement contradicts the claim — three separate obligations, because a section carrying `-38.20%` and nothing else has told a skimming reader nothing about what happened to the claim. E1 refuses a manuscript whose section did not discharge an obligation (`argument-obligation-unmet`, naming the section and the obligation), a section the plan declares that the manuscript omits, and a section the manuscript carries that the plan never declared. The plan travels on the draft with `ARGUMENT_PLAN_VERSION` and is carried through D4, so a revision is judged against the plan it was written under. **The plan is derived, not configured**: the same deterministic study under the second task's claim — which committed to a decrease — is `supported` by the same −38.2%, and its sections owe a direction rather than a contradiction, which is a repo-owned test on the production path. The evidence requirements that used to live in `section-evidence.ts` now live on the contract, so a section's requirements and its obligations are one entry rather than two tables that can drift. **What is not here**: the obligations that take a reader (the Discussion's alternative explanation, the Conclusion's limitation) are recorded on the contract and not judged, because a rule over prose would be a rule about prose; and the version a section records does not include which SKILL or prompt assembled the writer's request — the request is not a logged session event, so a draft records the plan and the evidence it was written from and not the instructions themselves.

- **A citation is bound to a sentence and to the passage somebody read** (2026-09-17): `runner/citation-bindings.ts` holds `CitationUse` — the statement, the source, a stable `citeKey`, the location the passage was read at, the passage and a SHA-256 over it, the support relationship, how much was read, and who judged it. **The key comes from the identifier, never from the title**: `citeKeyOf` mints `cite-<id>`, because a key assembled from an author and a year collides and one assembled from a title moves when the title is corrected. `checkCitationUse` refuses a binding with no passage, one whose support is stronger than what was read (`abstract-only` cannot establish what only the method shows), a retracted source, a source that was retrieved but not held, and a support judgement about a source that could not be read. **The reference list is derived from citations, and the retrieval is left as the library it is**: `buildReferences` — which turned every hit the landscape scan returned into an entry — is deleted, and `bibliographyOf(citations)` is what D3 puts in the draft, so a work appears in the reference list because a sentence cites it. **Found by reading the delivered paper**: twenty-five real DOIs in its reference list and a body that cites none of them, which no test could see because both halves worked. `checkManuscriptCitations` now refuses three things at E1, where the body and the list are both in hand before the manuscript becomes an artifact — a key the body cites that the list does not carry (`citation-target-missing`), an entry no sentence cites (`citation-entry-uncited`), and a cited source the run holds no reviewed judgement about (`citation-unreviewed-source`, which is what citing one of the retrieval hits is). The writer is handed `citations` and told to name each source as `[@citeKey]`; E1 prints them as the numbers the list assigns; D4 carries the bindings forward, so a revision does not turn correct citations into unreviewed ones. A run whose Introduction states a literature position without citing is REFUSED at E1 and publishes no manuscript — that refusal is a repo-owned test, not a demonstration. **What is not here**: only the deployment's reviewed corpus may be cited, so this run's literature position rests on three sources a person read; the statement a citation is made for is a fixed slot (`introduction:prior-work`) rather than an id the manuscript mints per sentence; and the corpus records no locator (volume, page or article number), so `missingSourceFields` reports it as absent rather than filling it in.

- **A metric is declared once, and a study that disagrees with the declaration does not run** (2026-09-17): `runner/metrics.ts` holds `METRIC_REGISTRY` — one `MetricDefinition` per quantity, stating its key, its unit, which way is better, what a movement MEANS, and the research types it belongs to — and `checkMetricDeclaration` returns one refusal per disagreement (`metric-unknown`, `metric-unit-mismatch`, `metric-direction-mismatch`), naming both sides. **The unit is compared and never converted**: a study reporting `min-ttc-seconds` in milliseconds measured a quantity nothing else in this deployment can be compared against. `requireMetricDeclaration(MEASURED_METRIC)` is called in `driveOptions`, the one place both `startRun` and `runPipeline` resolve their configuration, so a drifted study is refused **before the run exists** — making the study's unit `ms` makes twenty-four tests in `tests/start-run.spec.ts` fail with that refusal, which is how the wiring was checked. `metricsFor(type)` keeps REQUIRED and NOT-APPLICABLE apart, and the package manifest's `declaredMetrics` states per metric its key, unit, direction, interpretation and whether the run's own type required it, read out of the run's frozen spec rather than looked up at export time. **What is not here**: nothing reads the interpretation where a sentence is written. The quality baseline's direction-word check reads only the sign of the measurement, and its valence branch ("an improvement") is the one that reads the direction — a manuscript that states no valence word is judged on the sign alone, so the shipped run's own prose never exercises it.
- **A run is conducted under a research profile it freezes, and reconfiguring does not move it** (2026-09-17): `runner/research-profile.ts` separates the two configurations that were previously one — the research TYPE (`simulation-study` | `literature-review`) decides which metrics a study has at all, and the JOURNAL profile states what a particular venue requires of the document. **A journal rule is only a rule if somebody read it**: every `JournalRule` carries the `source` it came from and `resolveResearchProfile` refuses one without it, because a rule nobody read is a guess and a guess must not be enforced on every manuscript. `TRC_PROFILE` therefore carries **no rules at all** — the author guide was never obtained, and an empty list says so where a filled one would invent it (`../project-plan/architecture-review-2026-09-15/TRC-PROFILE-SPEC-CHECKLIST-2026-09-17.md` records each unverified specification). Resolution happens at the start of the run — an unknown research type is refused there rather than at the step that happens to read it — and `runSpecOf` freezes the resolved profile into the run's spec, so a deployment re-booted on the same snapshot directory under a DIFFERENT research type does not change the profile a run already recorded. **The client cannot state any of this**: the type and the journal are read off the deployment's own engine, the way the evidence profile is, because a browser-reachable entry that accepted a type would let a caller change which metrics its manuscript is judged against.

- **A package verifies as what its manifest says, and says when it was read** (2026-09-17): `checkPackagedFiles(directory, manifest)` answers "is this directory the package its manifest describes" in one pass — present, the stated bytes, the stated digest — and reports an edit that kept the length as a DIGEST difference rather than as ok. `scripts/verify-package-directory.mjs` is the hand-invoked runner for directories outside the test tree. **`generatedAt` is the moment of the export**: it was `new Date(0)`, so every manifest claimed its package was generated in 1970 — and that is the one field that tells the package written after an approval from the one the drive wrote. Both were found by verifying the delivered paper's package by hand: three of its ten files had never been copied into the delivery, one had been trimmed of trailing whitespace, and neither manifest could be checked against the directory it sat in. The delivery now keeps the reading copy, the original package and a complete re-export apart, each with its own manifest, and says in writing which entries do not reconcile.
- **A package says whether it is the final one or a working draft, and the final one can be refused** (2026-09-17): `planRunPackage` computes nine conditions from the run's own records — the production evidence profile, a manuscript, every step closed, no refused section, no open concern, an approval on the human gate, that approval still covering the artifacts the run holds, every file the manuscript declares present, and the run's last write landed — and the manifest carries the resulting `state` (`final` only when all of them hold), the checks themselves, and the approval with the artifact versions it was taken on. **The export at the end of a drive is a draft by construction**: a run that reaches the human gate stops there, so the manifest written then records `E2-submit: gated`, and the approval that followed never reached it — a page offering that file as the final package offered the state from before the decision. `@Remote('exportRunPackage')` writes the package on demand and REFUSES a final one **in the operation**, naming the first condition that failed and writing nothing: a refusal that emptied the directory on its way out would take away the draft a reader still has. The draft is written anyway and says which it is — in its manifest's `state`, in its checks, and in its own `run-summary.md` — because a reader who wants the current material should get it, labelled, rather than a refusal that helps nobody.
- **A study a previous process left is taken back before it is decided** (2026-09-17): `@Remote('openStoredRun')` loads a stored run into this process WITHOUT driving it — the snapshot goes into memory, the run is registered with the approval channel, and it is reported `stopped`. **It exists because an approval is refused for a run this process does not hold** (a decision has to be written into the run's state), which left a study that reached the gate and survived a restart findable, readable and undecidable; `resumeRunPipeline` is not the way in either — it drives from the first non-terminal step, and a run whose every step is settled has nothing to resume. **Adopting twice is refused** (the second call would replace the state a reader is watching with a copy of what was on disk), a run the deployment does not hold is refused rather than invented, and a run whose last write failed keeps that fact — opening a run is not a write and cannot clear it. The adopted run is written through the same serialized writer every other write uses.
- **Every write is based on the revision the last landed write updated** (2026-09-17): an approval writes the run snapshot, and the base for the NEXT write is `active.savedRevision` — the field `persistRun` now notes its own result into, that a checkpoint's callback stores its revision into, and that adopting a stored run seeds from the snapshot it read. **Found from the browser, and nowhere else**: the acceptance after a change request was refused — "the persisted snapshot is at revision 25 but this write is based on revision 24" — because the approval's write moved the file and nothing told the process. The acceptance record was written and its `persisted` said false with that reason, while the manuscript it published never reached the file: the page showed one manuscript and a restart would have shown E1's. **Reading the last write's RECORD instead of the field reintroduces the same split from the other side** — a checkpoint moves the file without going through `persistRun`, so that record describes one path's write and says nothing about the other's.
- **A candidate is written under an id the deployment minted** (2026-09-17): `generateCandidate` ignores the `candidateId` the caller sends — the page has none to name yet, so it sends the empty string — and `buildCandidate` mints one when it is given none. **Every later read goes through that id**: the record file is named for it, a review is looked up by it, an acceptance names it, and the page pins each control to it. Written from the caller's value, every candidate of every request shared the id `''`: one `candidate-.json` per request, a second candidate overwriting the first, `review-.json` meaning whichever candidate was judged last, and a page whose accept and review buttons all named the same candidate. **Found by the browser probe, not by a unit test**: the probe pinned its clicks by candidate id, and the empty id made it click another request's control while reading as a pass.
- **A reviewed candidate can be published as the manuscript, and that is its own operation** (2026-09-17): `@Remote('acceptCandidate')` assembles the candidate's sections over the manuscript the run holds and hands it to core's `acceptManuscriptCandidate`, which writes a new manuscript version through the registry, moves the project revision, and records the version it replaced. **It is not a step commit**: E1-format committed long before anyone read the paper, so this carries its own guards — a run revision other than the one the caller stated, a manuscript whose current version is not the candidate's basis, no review, a review of another version, a review that failed, an unencodable value — and a producer that names a person (`human-acceptance`) rather than an executor. **The caller names a request and a candidate, never a document**: the value is assembled here, keeping every other field of the E1 artifact. The checks live in one place, so the read a page makes before offering the control cannot drift from the operation that refuses it.
- **A change request is answered by a candidate, and judged before it is believed** (2026-09-17): the approval endpoint takes an `onDecided` hook, and the service uses it — an applied `request_changes` decision records a `RevisionRequestRecord` under `<snapshotDirectory>/revisions/<requestId>/`, naming every section of the manuscript with the body hash it had and the sections the instruction is about. **A candidate is written against the version the request read**: the basis is re-read at write time and a manuscript that moved is refused, as is a request naming a section that is gone and a writer that returns nothing. **The writer is the deployment's own prose channel** (the seam D3/D4 write through), and the channel that wrote a candidate is recorded on it. **The checks read the run, not the text**: a changed section's numbers must be numbers the run declares or measured, its citation labels must be in the reference list, and the candidate must have exactly the manuscript's sections; the review is bound to the candidate's own hash. `@Remote('listRevisions' | 'requestRevision' | 'generateCandidate' | 'reviewCandidate')` exposes the loop. **What is not here**: acceptance. Making a candidate the official manuscript needs the accepting transaction the module design describes as a core operation (version comparison, reference validation, atomic write over the registry, downstream invalidation); until it exists a reviewed candidate cannot become the manuscript.
- **A change request is a decision, and it leaves the gate open** (2026-09-17): `submitApproval` accepts `request_changes` alongside `approved` and `rejected`, carries the instruction the caller states, and answers with the decision the backend recorded plus the run re-projected after it. Core records it in the run's own approval record and `human-approval` event, frozen against the artifact refs that were in front of the person, and the step STAYS `gated` — the person asked for different work, not for the study to stop. **A request that names nothing is refused at both boundaries** (the channel's reader and core), and the refusal leaves the gate where it was. The receipt states the decision the backend recorded rather than a value derived from the step's status, because `gated` is the status of a step that was asked to change AND of one nobody has looked at.
- **A study is findable by a deployment read, not by what the page remembered** (2026-09-17): `@Remote('listRuns')` answers the studies this deployment holds, newest first — the read that makes a study reachable after the tab that started it is gone, because a run id lived in that tab's storage while the snapshots stayed on disk. **A run this process holds is reported from its live state; a run it does not hold is read from its file** and reported `stopped`, carrying the steps that were in flight when the snapshot was taken, so an interrupted study is distinguishable from a finished one. One run appears exactly once even when it is both held and stored, because the live state is what its own readers see. **The order is the id's, not the revision's**: a revision counts what one study committed and cannot order two studies against each other, while ids are UUIDs and sort stably across calls and processes. Each entry carries the execution state, the project revision, `stepsPassed` of the catalogued `stepsTotal`, `submissionReady`, and the two failure facts a reader acts on (`saveFailure`, `executionError`). **A list that could not be read is a refusal**, not an empty list: "this deployment holds no study" and "I could not ask" have different remedies, and one of them is not "your work is gone". **The browser reaches this method only if the Remote assembly bundle carries it** — `dsh-api-remotes/lib/client.js` inlines each package's generated descriptors, so a new `@Remote` method needs a client-face rebuild after the generator rewrites them; a build that bundled first leaves the page calling a method that exists everywhere else, and the page reports it as `listRuns is not a function`.
- **A save that did not land can be retried, and the retry is not a re-run** (2026-09-16): `@Remote('retryRunSave')` writes a run's CURRENT state to its snapshot again, for a run this process holds. It is the remedy a person needs when the deployment's write path failed and recovered: without it the only way to get a run back on disk would be to carry the study out again, which spends its model calls twice and produces different numbers under the same name. It reconciles with the disk rather than trusting a remembered number — the base revision is read from the snapshot as it stands — and it moves the SNAPSHOT's write counter, never the run's `projectRevision` (rewriting the same state commits nothing), so a decision taken before the retry still names a current revision. **A run this process does not hold is refused**: a run read back from its file is already at the state its file records, and there is nothing a second write would carry that the disk does not have. The client offers the retry on the host's own `saveFailure` report and renders the run the retry answers with, so the revision a decision needs is the one the page re-reads.
- **A save that did not land is the run's state, and it refuses both readiness and a decision** (2026-09-16): the failure used to live only in `RunResult.checkpointErrors`, which a RUNNING run has not produced — so the page showed a study advancing and said nothing about the fact that none of it was reaching the disk. It is now `ActiveRun.checkpointError`, reported as the `error` of the run's persistence (beside the `revision` that stopped moving) and CLEARED by the next write that lands. `submissionReady` and the readiness note read that SAME record, through the one accessor the projection renders (`livePersistence`) — a second read could answer the two questions differently and leave a page saying "ready" about a run nobody can save. **An approval is refused on it, before anything is decided** (`research/approval-save-failed`): `submitApproval` reads the run's last durable write beside the other preconditions — run, step, `humanGate`, current status, current attempt, expected revision — because reporting `persisted: false` afterwards was too late. The gate had already moved to `passed` in memory while the snapshot still said `gated`, so a restart asked the person to approve what they had already approved, and the caller was told its decision was not durable with nothing it could do about it. The refusal carries the deployment's own reason, and `RememberedRun` gained `saveState` (with `persist`, both required) so a caller that can write a decision cannot forget to say whether the run it belongs to is on disk. **The remedy, and its bound**: a refusal is never remembered, so the same command is decided once the run's next write lands — a checkpoint, while the run is still being driven. **Once the driver has stopped, nothing in this process writes the run again**, so a run whose LAST write failed stays refused until it is driven again; the refusal states that, and the operation that would re-drive it belongs to the disconnect-recovery work rather than here.

- **A start command is recoverable, or it is not idempotent** (2026-09-16): `StartCommandRecord` is written to `<snapshotDirectory>/commands/<commandId>.json` by write-and-rename, and the in-flight answer is registered synchronously — so two calls arriving together produce ONE run (the map used to be written after the save, and both could miss it), and a retry after a restart is answered from the record instead of starting a second study. **The record lands before the run does**, which is the order that closes the window between them: written afterwards, a process dying between the run's first save and that write left a study with nothing naming its command, and the retry — finding no record — started a SECOND one. Written first, the retry always has something to find, and the only thing the window can cost is a command id that has to be replaced, because a record whose run is missing is reported as such (`persisted: false`, naming the missing run) rather than re-run: a study that was begun may have produced something, and starting another is not a way to find out. That order's price is paid on the failure path — a start that did not happen removes the record it wrote, where it wrote it, so the id stays retryable — and if the removal itself fails the record is left behind, which is the safe direction: the retry refuses instead of duplicating. A command id carrying DIFFERENT research is refused by digest comparison, and an id that cannot name a file is refused rather than sanitised (a sanitised id is a different id, and the next retry would not find it). **A start whose record cannot be written FAILS** — a command nobody can look up is worse than one that did not run. **What is not here**: `startCommands` is not evicted, so a deployment starting many runs grows the map for the life of the process.

- **A cursor names a position in one HISTORY, not only in one run** (2026-09-16): a run restored from a checkpoint keeps the events that checkpoint saved and appends new ones at the indices the lost tail occupied, so a position a reader had consumed can hold different events here — serving the new ones from that position would continue a reader that never saw what replaced what it held. The cursor is now `<runId>#<consumed>#<digest>`, where the digest is a chain over the events below that position (each event's fingerprint folded into the previous digest, folded in a FIXED field order so a restart cannot look like a different history). A cursor whose digest does not match the log it is presented for is refused with a `resync` frame naming it, and the reader re-reads. **The count is the position, not the last index seen**: an envelope now carries `cursor` — the position AFTER the event — beside `eventId`, so a page that reconnects mid-batch is not sent the event it already applied (the old shape set the page's held position to the event's own index, which asked for it again). **Control updates are frames too**: a run's save health and its execution ownership change with no event appended — a checkpoint fails, a driver stops — and the follow now delivers a snapshot frame when either moves, read at the opening frame it describes (a generator initializes after its first `yield`, so a reader that only ever heard about appended events would have been told nothing about a save breaking while a run sat at the human gate). A slow reader is not buffered: an async generator produces a frame only when the consumer asks for the next one, and the subscription is cancelled by its own `AbortSignal`.
- **A run is followed through a stream, from a cursor, instead of polled** (2026-09-16): `@Remote({ mode: 'stream' }) followRun({ runId, cursor? })` yields an opening `snapshot` frame, one `event` frame per appended event, and a closing `snapshot` when nothing is driving the run. **The cursor is the event's index**, scoped to its run as `<runId>#<sequence>`: a run's audit events carry no sequence field and their `ts` is a millisecond that two events can share, so the index is the only strictly monotonic key it has — and the log is only ever pushed to, so an index names the same event for the run's life. **The opening cursor and its snapshot are the same read**, which is what makes "no gap between the snapshot and the subscription" true by construction: the snapshot already contains the effect of every event at or before it, so a reader that reconnects is handed a state that includes what it missed. A cursor from another run, or a position the log never reached, is refused with a `resync` frame naming the reason rather than read as a position in some other history. **The stream is read-only** — version-sensitive commands stay on the authenticated unary path — and **the envelope carries no `detail`**, because the typert generator refuses a bare `unknown` on a wire boundary (it caught this on the first build).
- **A study can be started and read while it runs, and a restart finds it** (2026-09-16): `@Remote('startRun')` creates a run, writes it, answers with its id, and drives it in the background under this service; `@Remote('runSnapshot')` reads the run as it stands. Before this the only entry point was `@Remote('run')`, which answers when the whole study is over — so a person who pressed a button had nothing to look at for minutes, a page reload lost the only handle they had, and the view was built from `RunResult`, a value that does not exist until the run has ended. **`RunResult` is still the drive call's result**; what changed is that nothing needs it to answer "what is this run doing". `runner/project-view.ts` reads the run's OWN records — the step states, the artifact registry and the `step-executed` records — and projects every catalogued step, so a step that has not run reports `pending` with attempt 0 rather than being absent or defaulted to a success. **The snapshot carries `execution`**, which is a fact about THIS PROCESS: `running` means a driver is on the run here and now, and it is never read back from a record written by a process that is gone. A restart's query therefore restores the run from its checkpoints and reports `stopped`, naming the steps that were in flight — honest about what a reader would lose, and never a stale `running`. **A driver that threw is reported at the run level** (`execution: 'failed'` plus `executionError`), because the per-step record says how far the study got and cannot say that whatever was going to continue it is gone. **A retried command reads the answer the first send produced**: `commandId` names the command, so a client that never saw its response sends the same id and is handed the run it already started instead of spending a second study. **A start that cannot record the run refuses** — the id is written to disk before the driver starts, so a deployment with no usable snapshot directory gets an error rather than a success it could not keep. `runPipeline` also gained `checkpointAfterStep`, which it should have had since checkpoints landed: a run started asynchronously was saving only at the end.
- **A study reports how it is going, not only how it went** (2026-09-16): the client's run control starts a run, reads it, and follows it, rendering each snapshot as it arrives; the workbench states the run's id and its execution state beside the readiness badges. **The follow loop is the page's interest in the study, not the study**: the driver is owned by this service, so closing the page does not cancel a run, and a client that comes back reads the same run. **The transport was a fixed client interval and is now the run's own stream** (`followToRest` over `@Remote({ mode: 'stream' }) followRun`, with a cursor, de-duplication and a re-open on a refused cursor — see the entry below, which is where that half is recorded). **What is not yet there**: a client whose read fails leaves the follow loop by throwing, so "the page stopped following" and "the run stopped" are two facts a reader has to tell apart from the message; and `runSnapshot` reads the run's records per call, so a very long run's polls re-project the whole run rather than reading a delta.
- **An approval binds the revision the READER saw, and it used to bind whichever one was current** (2026-09-16): `ApprovalSubmission.expectedProjectRevision` is required, and `submitApproval` refuses a decision naming any revision but the run's — so a page that moved under the reader (a second tab, a step that landed, a recovery) cannot get a decision recorded against a document nobody read. The refusal names both revisions and says to re-read. **The client half**: a page that cannot name a revision does not offer the buttons at all. Together with `approvalStalenessOf` — which catches the same mismatch AFTER the decision — a revision is bound on both sides of the moment.
- **The export manifest names the project revision it read** (2026-09-16): `RunPackageManifest.projectRevision` is read from the run, not derived from the files, so a reader comparing two packages — or matching a package against a screen — can tell whether they are the same state of the study. `generatedAt` says when someone read it, which is not the same fact: two exports a minute apart can carry different manuscripts.
- **A concern the revision left open now blocks readiness** (2026-09-16): `openIssuesOf` reads the `rebuttal` artifact's per-issue outcomes and `submissionReadinessOf` refuses a run that still carries one, naming the issue, its section and the applier's reason. A round records what became of every concern it raised; the ones left `open` were refused because the patch was written against another version, changed nothing, or conflicted with another patch to the same section — each is something a reviewer raised and the paper has not answered, so a run with all gates closed and a person's approval is still not ready. **Before this the list was written and read by nobody**: it did not stop `D4-rebuttal` from advancing and did not reach readiness at all. **What is still missing**: there is no round counter and no budget, so "two rounds of the same failure become a human decision" has nothing to count — `D4` runs one round and a refusal is reported, not retried.
- **Readiness refuses a run whose approval went stale** (2026-09-16): `readinessOfRun` asks core's `approvalStalenessOf` for every step and hands the first answer to `submissionReadinessOf`, which turns it into a refusal naming the revision that moved. An approval covers the document that was in front of the person; a manuscript that left that revision behind — a later step, a recovery from another snapshot, a hand — has not been approved, and a run in that state is not ready. **What this does not cover**: the exported package FILES. Editing `manuscript.md` on disk after the export is outside the run's registry, so nothing here sees it; the manifest's per-file `sha256` is what a reader checks that against.
- **The browser loop closed** (2026-09-16): the end-to-end probe reports **41/41** at `cdf9e69f`. A run driven through the shipped app carried all sixteen steps to `E2-submit`, the operator approved it through the page and the BACKEND recorded the approval (`{"a2":"passed","e2":"gated","steps":16}` then `{"e2":"passed"}`), and the exported package cites 25 real DOIs from the live catalogue with none of them the synthetic anchor. Its manuscript was written by the deployment's configured model route and passed an adversarial read of four checks. **It took five attempts** — four stopped on defects the in-process suite never saw, one on a catalogue outage — and the defects are recorded in `../.agents/notes/implemented/testing/2026-09-16-what-the-browser-found.md`. **The probe runs per delivery, not per commit**: one cycle is a full build of both faces, a profile-install refresh, a booted app, a Chrome instance and up to twenty minutes of a live model.
- **The closed loop runs on the production profile** (2026-09-16): `tests/e2e/closed-loop.spec.ts` asserts the whole chain at once, because every part passing on its own is what a broken loop looks like from the inside. A production run drives all fifteen steps to `E2-submit` on reviewed literature, writes a manuscript whose sections record the evidence they were written from, **stops** at the gate that reads an injected number the run never measured, re-reviews the revised draft with the same checks that reviewed the draft, and reports `profileEligible: true` / `submissionReady: false` until a person approves. A refuted prediction completes the run — `mvp-results.outcome` is `refuted` with `decisive: true`, which are two different facts — because a pipeline that only completes on positive results manufactures them. **What this is not**: an approval. `readinessOfRun` says the material exists and the gates closed; the package is approved by a person at E2, and `evaluation` is never ready at all.
- **A revision is a diff, or it is nothing** (2026-09-16): `runner/issue-patch.ts` holds the Issue → Patch → Verify cycle. An issue names one section and the version it was written against (`basisHash`, computed from the body the author was shown); a patch is a replacement body. It applies only when the basis is still current and the result differs from it, so `revised` is a property of a section whose body CHANGED and is derived from the bodies, never asserted. A patch written against a stale version is refused rather than applied — applying it would silently discard whatever happened in between — and two patches to one section conflict rather than merge. An answer that changes no text is `accepted_explanation`, recorded apart from a patch. `D4-rebuttal` reads `CONCERN`/`SECTION`/`RESPONSE`/`PATCH` lines and writes `issues`, `changes`, `patchedSections` and `openIssues` onto the rebuttal and the revised draft. **Before this** every section was mapped to `{ ...section, revised: record.hasRevisions }`, so one concern marked the whole manuscript revised with no body changed. **The model path is driven, and a malformed reply is refused** (2026-09-16): `tests/d4-model-revision.spec.ts` runs D3 and D4 through a writer that answers each step in that step's own format, so the parser reads the kind of reply a model produces — the browser run's own three-exchange reply is the fixture. `runner/issue-parse.ts` tells three intentions apart: a replacement body, `PATCH: NONE` (the author accepting the concern as an explanation), and a MISSING `PATCH` line. The third used to be the same value as the second, so a reply that simply did not follow the format was recorded as `accepted_explanation` and the step passed. An exchange that omits a label is now reported with its number and the label it lacks, and `assertWellFormed` fails the step on that report rather than closing an issue on nothing. **The parser reads one labeled format and no other**: a reply that answers in prose is refused, not interpreted.
- **A repeated approval command is answered, not re-decided** (2026-09-16): `ApprovalSubmission` carries a `commandId`, and `submitApproval` answers a repeated id with the result the first send produced. A caller that never read the first answer — a timeout, a reload, a second click on a button that looked inert — used to meet `not-pending`, a refusal it cannot tell apart from "my decision never landed". **A different id is a different intent** and meets the state the first command produced, so the ledger answers retries without being a way around the gate. **Refusals are not remembered**: caching one would make a command that failed for a transient reason permanently refused under that id. **The ledger is in memory**: across a restart a retried command meets `not-pending` again — safe, because it cannot decide twice, but not idempotent, and the boundary is stated here rather than given a durable table this layer does not own.
- **A revision is a bounded cycle, not a single round** (2026-09-16): `D4-rebuttal` used to run once, with `roundId` hard-coded to `t19s-rebuttal-1` and nothing to try again when the applier refused a patch. It now asks again — up to `revisionRounds` (deployment configuration, default 2) — telling each round which SECTIONS the previous one left open and giving it the manuscript as it now stands. The artifact carries `rounds`, `revisionRounds` and `stoppedBecause`. **No progress is measured by section, not by issue id**: a round numbers its issues from one, so comparing ids would call two rounds that failed on the same sections progress and spend the budget re-asking. **What it does not do**: a concern still open when the cycle stops does not become a human decision — it blocks readiness and the artifact says why.
- **A required check that did not run blocks the A gate** (2026-09-16): `checkDispositionOf` maps each review to a gate check and `verdictA` aggregates them over the roles the round declares, so a step `judgeRound` alone would have passed is BLOCKED when a required check never reported. **A check that ran and found the material inconclusive is NOT one of those**: an abstention is a finding, `not_evaluated` is silence, and the aggregate blocks only the second. The reachable case is a check whose required input does not exist — `red-stat` and `red-claim` say `evaluated: false` when the run holds no result record, because they verified nothing. **Before this the distinction did not exist**: a check that could not run reported `abstain`, the same value as a check that read the material and found it unsettled, so nothing-was-verified could not be refused.
- **The A gate reviews the manuscript, not the claim material** (2026-09-16): `verdictA` reads `draft` / `revised-draft` when the run has produced one and reviews THAT — `runner/manuscript-review.ts` checks the prose's numbers against the run's measured record, its Method section against the implementation that executed, its float and reference citations against the draft's own rosters, and its conclusion's direction against the sign of the measurement. Before this it called `reviewClaim(runCtx.claimMaterial)` whatever the step had written, so an offline probe could change a number in the draft, delete a Method section and skip the revision, and the A vote did not move. The steps gated on A before any manuscript exists (A2, A3, B1, D2) still review the claim material, and the verdict's evidence says which of the two it read. **The checks find four things and no more**: a number nothing measured, a section nobody wrote, a citation to nothing, and a conclusion its own evidence contradicts. Whether a paper is any good takes a reader, and this repository will not report a rule's output as one.
- **A plan off the wire is resolved to the implementation that measures its quantity** (2026-09-16): `requirePlan` (`runner/study-plan.ts`) returns a plan that always carries `implementationId`, taken from the single supported implementation whose `metric.key` matches the plan's. A plan naming an id has it checked against that metric; a quantity no implementation measures is refused at the boundary. The wire plan — a model proposes a study, a person confirms it — carries no id, and before this `requirePlan` accepted one and `B1-method` threw four steps into the run, leaving the step `in_progress` with no visible error. Every browser run stopped there. `runT19B` now calls `requirePlan` before its first step, so a plan it cannot execute is refused while a caller can still be told why. **One implementation exists**, so a study measuring anything else is refused rather than run.
- **Every section is written from evidence, and one with none is refused** (2026-09-16): `runner/section-evidence.ts` maps a section id to the run data it is written from — the Result section gets the numbers, their unit and the rule version that produced them; Method gets the implementation AND an `execution` entry comparing the method's declared version against the result's; Experiments gets the run accounting; Discussion gets the reviewed sources including the ones a reviewer judged do NOT support the claim. `D3-writing` puts that under `evidence` in the writer's request, and a section whose required evidence is absent is NOT WRITTEN — neither by the model nor from the built-in sentences. The draft records `sectionEvidence` and `refusedSections`, and `readinessOfRun` refuses to call such a run ready. **E1 is what a run actually hits**: `assembleManuscript` already refuses an empty section body (`DSH_MANUSCRIPT_EMPTY_SECTION`), so a refused section stops the run rather than reaching a reader. **The writer was previously given labels, not evidence** — `{field, direction, sectionId, claimRef, figureCount, citable}`, where `citable` is a float roster.
- **The B channel anchors on literature that was retrieved and read** (2026-09-16): `runner/evidence-corpus.ts` holds a small checked-in set of real sources — each with its identifier, the literal passage a reviewer judged, a hash over that passage, and a recorded verdict on whether it supports the claim sentence — and `runner/evidence-anchors.ts` runs the same core `verifyCitation` identity chain over it that the synthetic path runs, publishing `sourceClass: 'literature'`. A production run now drives all fifteen steps to the human gate on a real anchor; before this, the only anchor was `MockCitationResolverAdapter` over `10.0000/synthetic.t19b-anchor`, so no production run could reach a real B pass.
