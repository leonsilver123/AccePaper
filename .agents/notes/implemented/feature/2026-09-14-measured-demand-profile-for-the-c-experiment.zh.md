# Agent Note: C 通道实验的需求改由实测序列推导

Status: implemented

[English](2026-09-14-measured-demand-profile-for-the-c-experiment.md) | 中文

## Problem

C 通道决定一个可证伪预测是否挺过了实验,而实验跑的是写在 `runner/traffic-sim.ts` 里的需求数组:`[[950, 250], [450, 350], [980, 220], …]`。没有任何数据集产生过这些数字,也没有任何计算把它们与某个数据集连起来 —— 因此 C 判定只是关于"某人替它编出来的那个需求"的陈述。仓库此前已经拿到两个开放许可的数据集并记录在 `data/README.md`,但两者的字节都没有进入过任何计算。

这个对比还有第二处缺陷。两条策略跑在同一个固定周期上,只差绿信比分配,因此自适应策略只能靠"分得不一样"取胜 —— 而在本研究自己的剖面上,它选出的分配与基线原本就计划的相差无几。测量是对一个编造输入的真实算术,而它度量的机制很单薄。

## Decision

`runner/demand-profile.ts` 从真实的小时车辆计数序列推导实验需求。`scripts/derive-demand-profile.mjs` 用该推导跑 UCI 的 Metro Interstate Traffic Volume 序列(48 204 行、1 214 个完整日历日、CC BY 4.0),写出 `runner/study-demand.ts`;该模块被提交,使流水线在不带数据集字节的主机与 CI 上仍然确定。

推导过程:按"一天中的小时"对完整日历日求均值,把一天切成 6 个 4 小时控制区间,对整条曲线做一次缩放使最忙区间恰为声明的设计流量,再按声明的常数把每个区间分给两个相位。实测与假设分别记录在剖面上:一天的形状是实测的;把多车道州际计数映射到一个两相位交叉口的那个比例,以及每相位占比,是序列无法陈述的假设。`designTotalVehPerHour()` 由饱和流率、设计周期与设计饱和度算出设计流量,而不是直接命名一个数字。

两条策略现在的差别在于**用哪个需求去做计划**,而不在于算什么。`selectPlan()` 是一条规则 —— 在声明区间内的 Webster 最优周期,加上在声明上下限内与观测需求成比例的分配 —— `runFixedTimePolicy` 在设计区间喂给它一次并保持结果,`runAdaptivePolicy` 每个区间喂给它该区间自己的需求。因此这是两种控制策略之间的比较,降幅归因于自适应性,而不是归因于两个不同算法。

`tests/traffic-sim.spec.ts` 钉住使该归因成立的性质(同一需求下两条策略选出同一个计划)、降幅所来自的机制(空闲区间能跑的周期长度),以及可证伪的方向(完全平稳的剖面必须恰好为零)。`demand-profile.spec.ts` 在数据集存在时从字节重新推导并比对,因此在带该序列的主机上,手改无法不被发现。

在推导出的剖面上的实测结果:固定配时 27.28 s/veh,自适应 24.26 s/veh,降幅 11.09%,而预测承诺的门槛是 5%。

## Admission and ownership

`runner/traffic-sim.ts` 拥有实验:延误模型、计划选择规则、两条策略与判定。`runner/demand-profile.ts` 拥有推导,且是序列文本的纯函数 —— 无时钟、无随机、无模块级状态。`runner/study-demand.ts` 是生成物,携带序列的 SHA-256,因此提交的数字总能追溯到它们所来自的那次测量。`runner/registry.ts` 给 C1、B3、C3 三个产物挂上同一份 `demand` 证据块,使三者不可能描述不同的输入。

无法解析的行被**计数**,绝不默认为零:零会作为一个真实的安静小时进入日均曲线,拉低整个剖面。没有正的逐小时流量、区间数不整除 24、设计流量非正、占比落在 `(0, 1)` 之外,一律抛错,而不是产出一个剖面。

实验仍是解析式 Webster 模型,不是微观仿真。绝对延误值是模型输出,不是现场数据;测量所确立的是同一模型内两条策略之间的差。这限定了主张的范围,并写在产物与本包 README 上。

## Alternatives considered

**运行时读取序列,而不是提交剖面。** 否决:那样流水线的数字将取决于主机是否带数据集,同一条主张在 CI 与开发者机器上会被判出不同结果。提交一个带输入哈希的生成模块,既让运行确定,又让来源可复核。

**从 SUMO krauss 信号记录里推导分相位分配。** 基于证据否决。该数据集描述的是一个四相位、九链接的路口,不是研究所建模的两相位交叉口;而且它的记录步长没有公布 —— 观测位移与记录的 speed 列之比无法把它解出来,因此任何从中读出的周期长度都会建立在一个"被当作测量陈述出来的假设"上。相位结构是真实的,但不可迁移。

**解开数据集的 `map_info` 几何,把车辆归属到进口道。** 否决:这需要执行嵌入在不可信外部文件里的代码,为了一个本研究并不需要的输入,不值得冒这个风险。

**把固定配时基线按整段运行的均值需求设计,而不是按设计区间。** 否决:真实的固定配时实践按设计小时流量设计,而按均值做的计划在高峰不可行。自适应策略要打败的,是从业者真的会装的那套基线。

## Consequences

`SCENARIO` 不再携带 `baselineDelaySeconds`、`variantDelaySeconds`、`reductionRate`。那三个字面量(10.0 / 9.09 / 0.091)没有任何读取方 —— 执行器早已改为实测 —— 因此文件曾在宣示没有任何一次运行产出的数字。`SCENARIO.datasetId` 现在指向那条实测序列,这本来就该是 fallback 引用的东西。

本包 README 的"真实 vs fixture"边界过时了:写的是 5 步真实,注册表里是 8 步。已在 README 更正,并补上"实验需求是实测的、延误模型是解析的"这一新事实。

`runner/registry.ts` 现在约 2 250 行、承担四类职责。拆分仍是已识别的债;本次改动增加了压力而不是缓解它。
