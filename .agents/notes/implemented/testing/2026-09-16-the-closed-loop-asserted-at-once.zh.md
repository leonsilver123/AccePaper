# Agent Note: The closed loop, asserted at once

Status: implemented

[English](2026-09-16-the-closed-loop-asserted-at-once.md) | 中文

## Problem

复核的 R5 要一条验收路径:真实材料 → 被这份材料约束的手稿 → 一个被注入的错误 → 修好它的那次修订 → 一个人对**那个精确的包**的批准。

R1 到 R4 把零件造了出来,每个都有自己的测试。这正是本篇要讲的问题。一条循环的**每一个零件**都可以各自通过,而循环并没有闭合 —— 而上一轮看起来恰恰就是这样:1665 条测试全绿、两个 TypeScript 面干净,而每一次浏览器运行都停在 `B1-method`,因为从线上到达的方案不带实现 id。**逐零件的测试套件看不见零件之间的缝**,因为缝就在没有测试的地方。

## Decision

`tests/e2e/closed-loop.spec.ts` 把整条链当作**一件事**来断言,跑在 production profile 上。四个事实,每一个在本轮开始时都是假的:

1. **一次 production 运行凭存在的证据走到人工门。** 十六步全走,`E2-submit` 是 `gated`,没有 submission 记录。它的 B 门锚在 `reviewed source` 上而不是 `MockCitationResolverAdapter`;它的 draft 记着 `refusedSections: []` 与每一节的证据来源。
2. **注入的错误在读到它的地方被抓到。** 一个包装过的 D3 执行器追加 `The improvement was 12.5%` —— 一个运行从未测过、但看起来完全合理的数字 —— 运行停在 `D3-writing`,`verdicts.A: 'blocked'`。没有修订稿、没有手稿、不就绪:那个数字没有到达任何读者。
3. **修订会被复审。** `D3-writing` 与 `D4-rebuttal` 都通过了 A 门,而判定 evidence 具名手稿;D4 判定的 `targetRefs` 恰好是该 attempt 的提交引用 —— 于是一份报告不可能被读成"批准了另一份 draft"。
4. **就绪不是批准。** `profileEligible: true`、`submissionReady: false`,手稿在,理由具名 `E2-submit` 而不是缺了哪个工件。

这个文件同时钉住了**负面**那一格,而它正是流水线最可能悄悄坏掉的地方:仓库自带研究的测量**否证**了它预测的方向(记录 −38.2 %,主张预测上升),而运行照样完成,`mvp-results.outcome.verdict: 'refuted'` 且 `decisive: true`。这是两件不同的事实 —— 实验跑了并反对这个主张,而不是没能跑 —— 而一条分不清它们的流水线,是一条只在正面结果上完成的流水线。

## Alternatives considered

**把 R1–R4 的逐单元测试当作验收证据。** 拒绝,而这正是这个文件存在的全部理由。逐单元套件全绿的同时,产品跑不完一次运行。复核要一条闭环验收,是因为"每个零件都通过"与"循环闭合"是两个不同的主张,而其中只有一个能在某个零件内部被检查。

**只通过浏览器探针做验收。** 拒绝把它作为唯一形式,虽然探针正是**发现**线上方案那个缺陷的东西。它需要一个实时模型、一个启动的应用、一个 Chrome 实例和二十分钟,所以它不能是每次提交都跑的检查 —— 而跑得很少的检查,其失败会被很晚才发现。现在两者都在:这个文件给每次提交,探针给部署。

**用手搓的判定上下文断言注入的错误,而不是一次被驱动的运行。** 拒绝:R3 的测试已经那么做了,而那是更弱的主张。包装真实执行器意味着注入走的是真实路径 —— 执行器产出工件、驱动器提交它、门读被提交的那个东西 —— 而"运行**停下**"这条断言只有在真实路径上才有意义。

## Consequences

- `packages/research` **1758 passed / 99 files**;`tsc -b tsconfig.host.json` 干净。
- **浏览器探针自线上方案那次修复之后,还没有跑完过一次。** 是它发现了缺陷 —— 三条检查失败、运行停在 `B1-method`,报 `{"a2":"passed","steps":5}` —— 而正是它的证据定位了原因:被记录下来的运行 spec 里 `implementationId: undefined`。之后的三次尝试都停在等待一次运行上,而那次运行现在要带着真实的模型调用跑完十五步,比探针的第一段等待更长。那是关于**探针的耐心与本机模型延迟**的陈述,它**不是**"修复后的构建在浏览器里能跑"的证据。上面那条进程内闭环才是说修复成立的东西;一次独立的浏览器运行仍然欠着。
- **批准失效在别处被断言。** 具名一个步骤已经走过去的 attempt 的决定会被批准通道拒绝(`tests/approval.spec.ts`),而报告那一半 —— 目标不是该 attempt 提交的判定 —— 被 core 的 `submitGateVerdict` 拒绝。这个文件钉的是前两者所依赖的那条绑定,而不是重测它们。
- **被证伪的预测是一次完成的运行。** 这一点本来就是真的,而且没有端到端测试;现在有了 —— 这很重要,因为仓库自带的研究恰恰就是被证伪的那一格。
