# Agent Note: What the browser found that the suite could not

Status: implemented

[English](2026-09-16-what-the-browser-found.md) | 中文

## Problem

本轮结束时,research 各包有 1758 条通过的测试、99 个文件、两个干净的 TypeScript 面、五个全绿的
文档门。而**产品跑不完一次运行**。

这不是巧合,也不是对测试的批评。套件里的每一条测试都在进程内驱动 `runT19B`,方案由 TypeScript
构造;而产品是一个浏览器,通过生成的 wire 协议跟一个启动起来的应用说话,中间还有一个实时模型和
一个活目录。本轮所有缺陷都住在那道缝里,而且没有一个能从测试内部够到。

## 浏览器找到了什么

四个各自独立的缺陷,按出现顺序。每一个都已修复并钉住;前两个是产品缺陷,后两个是我的。

**1. 一个流水线执行不了的方案,在第四步之后才发现。** 线上方案不带 `implementationId` —— 一份
提案知道它在研究什么,不知道这个部署能跑什么代码 —— 而 `requirePlan` 接受了它。`B1-method`
随即抛出,`runStep` 把该步留在 `in_progress`,运行就那样停下,没有任何看得见的错误。每一次浏览器
运行都如此。量到的是 `{"a2":"passed","steps":5}`。

**2. 数字检查把参考文献一节里的标识符当成了测量值。** 运行到 D3 之后,`red-stat` 因为正文引用了
47 个 DOI —— `10.1016/j.trb.2025.103352`、`18051527`、`802.11` —— 判一篇**正确**的手稿为错,并
挡住了那一步。第一版修法(剥离 DOI / URL / arXiv / 方括号)是一张方案表,而它离下一次误拒只有
"多一种编号方案"那么远;立得住的规则更窄也更真:这条检查读的是陈述结果的节,参考文献一节不是。

**2b. A 门另外两条检查也说一篇正确的手稿是错的。** 数字检查修好之后,同一次运行又被挡下,这次
是两条从未见过模型手稿的检查:

- `red-citation` 拿正文里的 `Figure 1` 去比对图表的**标题**而不是编号 **label**,于是文档里每
  一条引用都显得悬空;
- `red-claim` 读的是"第一句提到被测量量的句子",而在真实手稿里那一句通常是**假设** ——
  "the HV-AV-HV platoon shall exceed the all-HV platoon in minimum time-to-collision by at least
  20 %" —— 于是它把对主张的忠实复述判成一处虚假结论。现在它要求**量级**,并排除承诺自己的
  措辞(`at least` / `at most` / `within`,以及将来时的 `shall` / `will`),于是一句陈述
  "lowered it by 38.20 %" 会被读,而一句预测不会。

两条都是**检查对一篇正确的论文判断错误**,而两条对套件都不可见 —— 因为套件审的每一份 fixture,
都出自与检查同一个作者之手。

**3. 改一个 wire 类型要重建两个面。** 新增必填的 `MeasuredMetric.unit` 弄坏了浏览器,而每一个
进程内测试都通过:客户端 bundle 的生成 wire schema 早于那个字段,于是它把值剥掉,主机回
`gateway/input-invalid: typert gateway: research/run: wire field "request" failed boundary
validation`。那个标签页渲染的是它的空状态,没有运行被创建 —— 读起来像"运行从没开始",而不像
schema 不匹配。身份检查抓不到它:它拿安装副本与工作区的 `lib/` 比,而两者是**一起**过期的。

**4. 一次故障说不出自己是什么。** `A1-landscape` 失败时说"the catalogue is UNAVAILABLE",没有
理由。`LiteratureSearchOutcome` 从接缝写下那天起就带着 `detail`,而 `buildArtifact` 把它丢了,
于是 HTTP 403、限流、DNS 失败、被拒的 venue 过滤,在最后一步完全相同 —— 而同一个请求形状从应用
进程外重放**每次都成功**。这让唯一重要的问题 —— 是环境还是我的改动 —— 变得无法回答。

## Decision

浏览器探针不是"更慢的套件",它是唯一能看见这一类缺陷的东西。套件的 1758 条测试说**零件**能工作。
探针说**产品**能工作,而这一轮这两个答案差了四次。

代价是真实的,值得写下来:一次探针循环 = 两个面的完整构建 + 一次 profile 安装刷新 + 一个启动的
应用 + 一个 Chrome 实例 + 最多二十分钟的实时模型驱动十六步。这就是探针按**交付**跑而不是按
**提交**跑的原因,也是 `tests/e2e/closed-loop.spec.ts` 那条闭环与它并列存在的原因。

## Alternatives considered

**让浏览器探针每次提交都跑,而不是每次交付跑一次。** 以代价为由拒绝,而那个代价是量出来的、
不是假设的:一次循环 = 两个面的完整构建 + 一次 profile 安装刷新 + 一个启动的应用 + 一个 Chrome
实例 + 最多二十分钟的实时模型驱动十六步。这么贵的检查会跑得很少,而跑得很少的检查,其失败会被
很晚才发现 —— 这次正是如此,而那仍然好过完全不跑它。

**认为进程内套件已经足够,就用它收尾。** 拒绝:在那四个缺陷的全过程中它一直是绿的。套件与探针
回答的是不同的问题,而这一轮就是"两者可以连续四次给出不同答案"的证据。

**把数字检查的标识符黑名单加宽,而不是豁免参考文献一节。** 在第二次尝试之后拒绝。每加一种方案
(DOI、URL、arXiv、方括号索引),下一个真实字符串就落空 —— 先是 `18051527`,然后是 `802.11` ——
因为一张参考文献表可以含有它的来源所用的任何编号方案。更窄的规则不做枚举;它说明这条检查读
**哪些节**。

**让 A 门的检查"容忍模型写的手稿",放松到某一次真实运行通过为止。** 拒绝,而这正是这样一轮里
最有诱惑力的失败模式。那两处检查缺陷,都是靠把规则改得**更窄**来修的 —— 比对编号而不是标题、
要求量级、排除承诺自己的措辞 —— 而不是靠删掉一条检查或放宽一个容差。一条被放宽到"某一份特定
文档能通过"的检查,已经不再是一条检查。

## Consequences

- 四个缺陷全部修复,每一条都带一个**用浏览器真实产出**而不是"造出来为了失败"的形状写成的测试:
  线上方案的修复有一条被驱动的、穿过 B1 的运行;数字检查的修复用真实字符串
  (`doi:10.1016/j.trb.2025.103352`、`18051527`、`802.11p`)钉住,并另有一条证明"标识符旁边的
  测量值照样被拒";孪生修复是一个字段;目录故障的理由从适配器经工具一路走到该步的拒绝里。
- **A1 那次故障本身是环境性的,且没有解释清楚。** 适配器在应用进程里报 `unavailable`,而同一台
  主机上一个普通 Node 进程发出完全相同的请求答 200 —— 之后有一次探针运行 A1 通过并取回了记录。
  同一个构建上,两次失败、一次成功。本仓库自己的计划文档记过 OpenAlex 限过这台机器,那仍是最
  可能的解释,但**没有确立**。
- **那种故障下 A1 的行为是正确的、没有改**:故障让该步失败,而不是产出一个空目录 —— 因为由零条
  记录派生的目录是编出来的。
- **浏览器那条循环仍未被观察到走到 `E2-submit`。** 浏览器运行跑得最远的一次到了 D3,而每一次
  停下的原因要么是一个现已修复的缺陷,要么是一次故障。说"闭环闭合"的是进程内那条闭环;浏览器
  确认的是它**只有浏览器能确认**的那些部分,而这个区分正是本篇的要点。
