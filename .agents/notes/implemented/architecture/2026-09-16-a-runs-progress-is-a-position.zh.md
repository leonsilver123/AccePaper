# Agent Note: A run's progress is a position, not a poll

Status: implemented

[English](2026-09-16-a-runs-progress-is-a-position.md) | 中文

## 问题

页面只能用那个 unary 入口允许的方式持有一次进行中的研究:每 1500 毫秒重读整份投影。这回答了"这次运行在 做什么" —— 那正是上一轮才让它成为可能的问题 —— 但它回答不了"发生过什么",而且它没有可续传的位置。掉线的 页面只能重新取一份快照,并指望中间发生的事都不重要;回来的读者也无法判断屏幕是否漏掉了一步。

计划的 §7.2 写明了它要的形状:快照与 cursor 指向**同一个序列点**,订阅从该 cursor 之后接续,cursor 无法 服务时显式给出重新同步信号,且快照与订阅之间没有缺口。

## 决定

**运行通过一个 stream Remote 被跟随,寻址用的 cursor 是它的事件下标。**

- `@Remote({ mode: 'stream' }) followRun({ runId, cursor? })` 产出:一帧 `snapshot`,随后每个新追加的事件 一帧 `event`,并在没有东西再驱动这次运行时产出一帧收尾 `snapshot`。
- cursor 是 `<runId>#<sequence>`,sequence 是该事件在 `run.events` 里的**下标**。运行的审计事件没有序号字段, 而 `ts` 是 `Date.now()` —— 同一毫秒内追加的两条会共用它 —— 所以下标是这次运行唯一严格单调的键。事件数组 只 push,没有任何地方裁剪、重排或压缩它,这才是"一个下标终生命名同一个事件"的依据。
- cursor 带着它所属的运行,所以拿别的运行的 cursor 来会被**拒绝**(`resync`),而不是被读成这次运行历史里的 一个位置 —— 这就是计划里的跨运行反例。
- 到不了的位置同样得到 `resync`。日志从不裁剪,所以本部署产出过的 cursor 自己不会变得不可服务;将来引入裁剪的 构建欠这一帧第二个理由,类型注释里写着这一点。

## 为什么"没有缺口"由快照帧本身成立

开场帧的 cursor 就是它那份快照被读出时的位置 —— 两者在同一步同步读取里得到 —— 而日志只会变长。所以那份快照 已经包含了位于该 cursor 及之前的每一个事件的效果:重连的读者拿到的是一个**已经包含**它所错过内容的状态,其后 的帧恰好是此后追加的事件。"快照"与"订阅"之间不存在可以丢事件的区间,因为它们是同一次读取。

**页面渲染服务的投影,而不是自己的投影。** 每一批事件之后都跟着一帧该批次所到位置的状态快照,所以客户端永远 不需要把事件重放进第二份可能与服务不一致的投影 —— 本仓库把这条规则写作"缓存与 UI 回声从同一权威来源派生"。 事件在客户端的作用是**顺序**:页面知道自己持有哪个位置,并拒绝应用一帧接不上它的帧。

## 考虑过的其他方案

**继续轮询,把事件当作变化信号。** 这就是客户端此前的做法。它失败在无法满足的要求上:信号只说"有东西变了", 不说读者在哪里,所以漏掉一个信号的页面无法判断自己是否漏过 —— 而计划要一个位置,正是为了让这个问题有答案。

**把事件重放进一个客户端投影。** 页面会把信封折叠进自己的视图模型,快照只是起点。它失败在于服务已经拥有那份 投影:客户端里的第二个实现是一份会漂移的副本,而失效方式是静默的 —— 屏幕与主机的**事件**一致、与它的**状态** 不一致。

**用 `RemoteSnapshotStream`(基线 + 替换)代替 cursor。** 它是本仓库里更便宜的机制,workspace controller 在用, 也能给出"屏幕是当前的"且完全不需要 cursor。它失败在计划写下的验收上:没有位置,就没有东西可以在读者的窗口不是 这次运行历史时被拒绝,"没有缺口"也就无法作为一个性质被陈述,只能被指望。另一个候选是 `RemoteJournalStream`, 若将来需要分页或经页方法补缺,它仍是本仓库的维护路径;一次运行的日志很小,一次开场加其后尾巴就服务完了,所以 那套补缺机制在这里暂时无事可做。

## 后果

- **最后一帧说明流为何结束。** 运行的执行状态是在**结束它的那一批之后**才变化的,所以那一批旁边的快照仍可能写着 `running` —— 而流到此结束,跟随者就会被留在一个"没有执行器却显示执行中"的状态上。因此本进程驱动过的运行会多发 一帧收尾快照;本进程从未驱动的运行不需要它,因为它的开场快照本就在该位置上读出、且已经写着 `stopped`。
- **这条流是只读的。** §7.2 把版本敏感的命令放在经过认证的 unary 通道上,所以页面能开的流不是一条写路径;计划里 "无身份写操作"那条反例在这里没有可以失败的面。
- **信封上没有 `detail`。** 第一次构建被 typert 生成器拒绝:"Remote boundary contains unconstrained unknown data"。生成器是对的 —— 裸 `unknown` 不该出现在线上边界 —— 而订阅者需要从事件里得到的是"它是哪个事件、位于 哪里"。需要具体载荷的消费者应当得到一个有类型的字段。
- **宿主仍在 250 毫秒的节拍上观察自己的日志。** core 不发布任何东西:`appendAuditEvent` 写进一个数组,journal 的通知缝是一个空回调。所以这条流和页面一样地观察日志,但它是从一个**位置**出发而不是从零出发 —— 投递因此是 有序且可续传的,而轮询从来不是。
- **投影现在报告的是该步骤当前的那次尝试。** 被取代的尝试的记录可能在新尝试之后追加(超时与取消是从"被启动的那次" 发出的,不会复查步骤是否已经前进),而只按步骤键取最后一条会让它覆盖新尝试的结果。改为按 `(stepId, attemptId)` 键,已经前进的步骤在新尝试产出结果之前不报执行结果。
