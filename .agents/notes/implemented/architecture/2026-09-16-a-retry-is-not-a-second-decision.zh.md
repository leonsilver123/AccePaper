# Agent Note: 重试不是第二次决定

Status: implemented

[English](2026-09-16-a-retry-is-not-a-second-decision.md) | 中文

## Problem

审批端点裁决一道人工门。它的守卫是基于状态的,而且都是好守卫:不是 `gated` 的步骤被拒,不是当前 attempt 的被拒,而一个 `approvalEventId` 每次运行只能被消费一次(`DSH_APPROVAL_REPLAY`)。

它们做不到的是:扛住一个**从没读到答案**的调用方。读者按下批准,调用超时,然后 —— 合情合理地 —— 再按一次。后端用 `not-pending` 拒绝第二次发送,因为**第一次**已经裁决了那道门。而调用方分不清这句 拒绝与「我的决定根本没落地」:两者看起来都是"门还在等"。

检查单点名了这件事:「网络超时导致重复批准或重复研究 | 幂等命令、结果查询、同一任务恢复」。

## Decision

`ApprovalSubmission` 增加 `commandId` —— **命令**的身份,不是决定的身份 —— 而 `submitApproval` 对 重复的 id 回答**第一次发送产生的结果**。

- 台账在**任何裁决发生之前**查,所以一次重试碰不到通道,也不会因为第一次发送产生的状态而被拒;
- 只记住**成功**。缓存一次拒绝,会让因为暂时性原因失败的命令 —— 通道坏了、这个进程不持有这个运行 —— 在那个 id 下被永久拒绝;
- **不同的** id 是不同的意图,它撞上的是第一条命令产生的状态。台账回答重试,它不是绕过门的办法;
- 这个 id 在 wire 上**必填**。没有身份的命令无法被安全地重试,而给它一个默认值会让每一次重试都变成 一次新的决定。

客户端为每个意图生成一个,并在意图不变时**复用**:失败后再按批准是同一条命令,改成驳回是新的。

## Alternatives considered

**让客户端重发同一个 `approvalEventId`。** 拒绝:那个 id 是主机对一次决定的记录、也是重放守卫的键。 自己挑它的调用方可能撞上一条它从未做出的决定,而一次性规则存在的意义恰恰是调用方不能指名别人的事件。

**任何第二次发送都返回已记录的状态,不要命令 id。** 拒绝:没有调用方说明,一次重试与一次真正的第二次 尝试无法区分。从步骤状态推导答案,也意味着端点永不拒绝重复 —— 而"回滚后新 attempt"这条守卫的诚实, 正依赖于 attempt 被指名。

**把台账做成持久的。** 这一层拒绝:那意味着在一个并不拥有运行存储持久化的包里放一张表,而诚实的边界 比那窄。跨重启之后重试的命令会再次撞上 `not-pending` —— 安全(它无法裁决两次),但不幂等 —— README 如实这么写,而不是暗示一个这一层并不提供的保证。

**忽略不认识的 `commandId`,照常裁决。** 拒绝:那正是被修的这段行为,只是多了几个字段。

## Consequences

- `tests/approval.spec.ts` 钉住:重复的命令返回**第一次**的结果、且该步上只有**一条**批准记录;不同的 id 撞上 `not-pending`(台账不是旁路);以及**拒绝不被记住** —— 一条打错运行的命令,在打到对的运行上 之后仍然能裁决一次。
- `tests/approval-panel.dom.spec.ts` 钉住客户端那一半:一次传输失败之后的重试带**同一个** `commandId`, 而改投相反的一票带一个新的。
- **这不做的事**:从另一个客户端、或者刷新之后,按 id 查询一条命令的结果。那是 U03 的「命令结果查询」 那一半,它需要持久的命令记录。
