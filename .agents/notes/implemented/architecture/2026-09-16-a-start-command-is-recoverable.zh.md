# Agent Note: A start command is recoverable, or it is not idempotent

Status: implemented

[English](2026-09-16-a-start-command-is-recoverable.md) | 中文

## 问题

`startRun` 的幂等性此前是一个 `Map<string, ResearchRunStart>`,而且是在运行保存**之后**才写入的。两个后果, 都与幂等键存在的意义相反:

- **同时到达的两次调用都会错过它。** 映射是在一个 `await` 之后写入的,所以第二次调用可能在自己的查找上跑过去, 而第一次还在保存,于是两边都创建了运行。
- **重启后根本无法回答重试。** 映射随进程消失,于是响应丢失的调用方 —— 正是这个键存在的那个场景 —— 没有任何 办法被告知它的命令产生了哪次运行,剩下唯一看起来安全的答案就是再来一次研究。

还有一处静默的缺口:同一个 id 携带**不同**研究时,会被用第一次的运行回答,调用方可能拿到一项它没有要求的 研究,而且无从察觉。

## 决定

**命令的答案被记录在它所命名的运行旁边,而"正在进行中"的答案在任何 `await` 之前就完成登记。**

- `StartCommandRecord`(`{commandId, runId, paramsDigest, startedAt}`)以"写临时文件再改名"的方式写进 `<snapshotDirectory>/commands/<commandId>.json`,**先于它所命名的那次运行的保存**。记录写不出来的启动会 **失败**:一条无法被找回的命令比没跑过更糟,因为调用方会拿着一个谁也查不到的 id。
- **这两次写入的先后就是它们之间的那个窗口。** 反过来写时,进程死在"运行的首次保存"之后、"记录"之前,会留下一 项没有任何东西命名的研究,而重试因为找不到记录,会再起第二项。先写记录,重试就总能找到东西,窗口最坏的代价 只是换一个命令 id:记录在而运行不在时会被如实报出(`persisted: false` 并指出缺失的运行),**绝不重跑** —— 已经开始的 研究可能已经产出了东西。
- **没有发生的启动会把它的记录取回**,而且是从它**写下的那个路径**取回,而不是重新解析一次目录 —— 快照根是部署 侧实时读取的事实,在这两次写入之间被挪动的根会把删除送到别处。若这次删除失败,记录会留下,那是安全的方向: 重试被拒绝,而不是重复。
- `startRun` **同步**登记一个 promise —— `startCommandOnce` 会跑到它的第一个 `await`,而这段同步块不可能被 别的调用插入 —— 所以第二次到达会等待第一次的答案,而不是创建一次运行。失败的启动会删除该条目,因为什么都没 记录,id 又自由了。
- **命令要求什么的摘要随命令一起走。** 重试比较相等;同一个 id 携带不同研究会被拒绝,并说明原因。跨重启时摘要 来自记录本身。
- **记录还在、运行没了,不是一次成功。** 回执给 `persisted: false` 并指出缺失的那次运行,因为"你的命令被认识" 与"你的研究找得到"是两条事实。
- **命令 id 必须能命名一个文件**(`[A-Za-z0-9_-]{1,128}`):它会成为一个路径片段,因此**拒绝而不是净化** —— 净化后的 id 是另一个 id,下一次重试就找不到它了。

## 考虑过的其他方案

**保留映射,加一把锁。** 在"查找并保存"外面加互斥,能关掉并发窗口且不需要任何持久记录。它输在更重要的那一半: 重启依然回答不了重试;而锁对"这个 id 是否被用于另一项研究"一个字也说不出。

**把命令记录进运行自己的快照。** 记录会住在运行的目录里而不是自己的目录,看上去更整齐 —— 直到查找为止:查找 是**按命令 id** 的,而运行目录是按运行 id 命名的。找一条命令将变成列出所有运行并逐个读取。

**用第一次的运行回答改过的请求,并把它写进文档。** 这正是代码此前的行为。它失败在调用方分不清"我的重试"和 "我的第二项研究" —— 摘要比较是唯一能分清的东西,而拒绝会说明它看到的是哪一种。

**净化不可用的命令 id。** 剥掉那些字符会让调用带着一个调用方从未发送过的 id 继续,于是它的重试(发送原始 id)会创建第二项研究。拒绝是唯一能让 id 只意味着一个东西的答案。

## 后果

- 快照目录现在在运行目录旁多了一棵 `commands/`。没有配置快照目录的部署什么都不记,而它的启动本来就会失败 (`persisted` 不可能为真),所以这项保证没有静默丢失。
- 读到一条**不可读**的记录会**抛错**,而不是返回"没有这条命令":记录缺席意味着这条命令从未发到这里,而不可读 意味着这个部署无法被交代 —— 把后者当前者,就是重试变成第二项研究的方式。
- `startCommands` 仍会在进程存活期间增长。启动很多运行的部署需要按时间淘汰它;这里还没有做,而持久记录正是 将来加入淘汰时使其安全的东西。
