# Agent Note: A run is readable while it is running

Status: implemented

[English](2026-09-16-a-run-is-readable-while-it-runs.md) | 中文

## 问题

研究界面只有一个入口 `@Remote('run')`,而它要等整项研究结束才返回。它下游的一切都继承了这个性质:
浏览器的视图模型由 `RunResult` 构建 —— 那是驱动调用在结束时才返回的值 —— 于是"这次运行在做什么"
这个问题,对一次正在做这件事的运行根本问不出口。按下按钮的人盯着一块空白页面等八到十五分钟;一次刷新
就丢掉了手里唯一的把手;而中途执行失败的步骤会永远显示成 `in_progress`,因为引擎会保留失败尝试以便回滚,
那个失败只存在于还没回来的驱动结果里。

也不能"早一点"用 `RunResult` 构建投影。`RunResult` 的定义就是结束:它的 `steps` 是驱动累积下来的结果,
驱动还没走到的步骤根本没有结果可报。伪造一个 —— 空的 `steps`、合成一个 `StepOutcome`、用类型断言绕过
缺失字段 —— 等于把一句没有任何运行说过的话写进产物。

检查点计划直接要求了这件事面向用户的那一半:按运行之后先弹出方案确认,确认后**立刻**拿到 runId 并看到
运行状态,而不是等整条流水线跑完。

## 决定

**运行自己的记录是它投影的来源,驱动调用的返回值只是驱动调用的结果。**

`runner/project-view.ts` 读取运行存储里的步骤状态、工件登记表与 `step-executed` 记录,并投影出**每一个**
目录内步骤:

- 驱动没走到的步骤报 `pending` 且 attempt 为 0 —— 是报出来,不是省略,也不是默认进一个含义不同的桶;
- 步骤的执行结果取自它**最后一条** `step-executed` 记录,因为一个步骤可以执行不止一次(回滚会把它重新
  打开),而读者问的是它最后怎么了;
- 执行失败与闸门裁决分开传递(`executeStatus` / `executeError`),因为那是两件不同的事的两条不同事实。

**`@Remote('startRun')` 创建一次运行、把它持久化,并在研究结束之前就返回它的 id。** 顺序就是保证:id 在
驱动启动**之前**写入磁盘,所以快照目录写不进去的部署拿到的是错误,而不是一个它守不住的"成功" —— 调用方
也因此可以安全重试,因为什么都没开始。驱动随后在服务下运行(`void driveRun(...).then(...)`,拒绝处理记录
`execution: 'failed'` 与驱动自己的消息),所以关掉页面不会取消研究,也没有悬空的 promise。

**`@Remote('runSnapshot')` 返回的 `execution` 是关于本进程的事实。** `running` 表示此刻这里有执行器在
驱动它;它绝不会从一个已经消失的进程写下的记录里读回来。查询本进程不持有的运行时,会从检查点恢复它并报
`stopped`,同时列出当时在飞行中的步骤 —— 这就是诚实的"可恢复或已中断",也是这个字段不被持久化的原因:
重启后的进程没有执行器,存下来的 `running` 会是一句谎话。

**`commandId` 命名的是命令,不是请求。** 没读到响应的客户端 —— 超时、刷新 —— 重发同一个 id,拿到的是它
已经启动的那次运行,而不是再花掉一项研究。不同的 id 就是不同的研究。

**客户端是跟随,而不是等待。** `startRun` → `runSnapshot` → 渲染 → 重复到没有东西在驱动它为止;每读到一份
快照就交给工作台,工作台在就绪徽章旁标出运行 id 与执行状态。

## 这不是事件通道

传输是客户端固定间隔的轮询,所以没有 cursor、没有去重、没有定序规则、没有补缺。早先计划里的"首帧快照带一个
可用于事件接续的 cursor"描述的是一条本次交付没有构建的通道。

**那条通道的机件在这里已经存在,本条不是在说它不存在。** `@Remote({ mode: 'stream' })` 是被支持的 Remote
形态,客户端有 `RemoteJournal`("snapshot-first opening, ordered live delivery, pagination, and repair over a
reconnecting Remote stream",打开帧带 cursor 与 page),`session-controller` 的 `follow` 已经在用它。把运行的进度
接到这条通道上属于接线而不是建造,也是补上本次未做验收的路径。

本次交付保证的是:第一份快照在第一步完成**之前**就可读,且每一份快照都是对运行自身记录的一次一致读取,而不是
读者可能漏掉的增量。

## 考虑过的其他方案

**让驱动增量地发布一个 `RunResult`,据其构建投影。** 这要求驱动每步之后发出一个部分结果。它失败在于
`RunResult` 的含义是"驱动累积下来的结果",而部分结果是一个注定会被推翻的值:拿着它的读者分不清"还没走到的
步骤"和"缺失的步骤",而它要携带的工件登记表与裁决本来就记在存储里,于是部分结果成了同一真相的第二份副本,
可以和第一份漂移。

**保留唯一入口,在它旁边加一条进度事件。** 运行仍由 `run` 调用创建,另有一条通道报告进度。它失败在于:
创建运行恰恰就是必须尽早返回的那一步 —— 调用方需要先拿到 id 才能问关于这次运行的任何问题,而一个返回得晚的
入口无法靠旁边加一条进度通道补救。

**立刻返回 runId,但把运行状态放在服务自己持有的缓存里,不落盘。** 这让 id 在一个进程内有意义、跨重启无意义
—— 刷新会遇上一个"没有这次运行"的服务,而诚实答案会变成"它没了",尽管它的检查点就在磁盘上。它失败在本仓库
明确要求的那一点上:重启后必须能定位原运行。

**在恢复的执行器还没接上时,把恢复出来的运行报成 `running`。** 它失败在于这个字段存在的意义就是回答"还有东西
在处理它吗":在重启与恢复之间,答案是"没有",而被告知相反的读者会去等待,而不是去行动。

## 后果

- `runPipeline` 在同一次改动里补上了 `checkpointAfterStep`。这个字段自检查点落地起就一直缺失,于是经新路径
  启动的运行会在结束前什么都不写 —— 重启也就什么都找不到。两个入口现在只在"什么时候返回"上不同。
- `persistRun` 改为接收 run id,而不是 `RunResult`。它此前只从中读 `run.runId`,而为了拿一个 id 而要求一个
  驱动结果,正是把调用方推向伪造一个的原因 —— 那恰恰是一次运行中的批准为了持久化自己的决定所不得不做的事。
- 经 `startRun` 跑完的运行,通过与同步路径相同的 `recordRun` 导出产物包,所以两条路径产出相同的工件。
- **"这次运行在盘上第几版"由一条规则推导,因为两份副本赔掉了一个决定。** 这是浏览器探针找到的:快照报的是完成时那次写入的 revision,而批准的落盘基于**最后一次检查点**的,于是 E2 的批准生效之后被拒
  (`the persisted snapshot is at revision 18 but this write is based on revision 17`) —— 决定留在内存里,没上盘。现在
  `savedRevisionOf` 是"这次运行在第几版"的唯一答案,快照与每个写入方都读它。进程内测试到不了批准自己的那次写入
  (需要一次停在人工门的运行);它钉的是:报出来的 revision 就是盘上的,且以它为基础的写入被接受。
- **状态由进程内测试作证,线上由浏览器探针作证。** `tests/start-run.spec.ts` 用一个在研究释放它之前不回答的
  文献适配器,把一次真实运行按在真实步骤内部,并在那里读投影 —— 没有 sleep,而一个等待研究的 `startRun` 会挂住
  而不是通过。重启场景在同一个快照根上启动第二个服务,读取第一个服务留下的运行。浏览器探针
  (`verify-browser-b.mjs`,打在出货的 `web` profile 上、1120 端口、真实浏览器与真实模型)报 **44/44**,
  其中两条正是这个决定的读数:页面在运行尚未结束时就说明有东西在驱动它,而后端同时确认它还没有任何步骤通过 ——
  第一步结束之前就可见;页面与后端对运行 id 的说法一致。
- **刷新之后恢复运行,只有 DOM 级证据。** `verify-browser-b.mjs` 不检查它,因为经 CDP 重载页面会把调试端点一起
  带走:实测两次,`127.0.0.1:9334` 不再监听,之后的每次读取都挂住,第二次尝试更是让探针没有输出摘要就结束了。
  一个探针会死在其中的检查无法作证,所以它是缺席而不是绿的 —— DOM 用例断言了运行 id 会回来、以及无可恢复时页面
  会这么说;实施记录里逐项写明哪一条有什么证据。
- **探针必须被教会新语义。** 它此前等的是一个快照**文件**出现,再从文件里读运行 —— 在快照只在结束时写一次的时候
  这是对的。现在运行的 id 在第一步之前就已落盘,于是那个等待立刻返回,把一次空运行读成了已结束的运行;等待现在
  落在运行自己的执行状态上,读的是页面轮询的同一个方法。
