# Agent Note: 决定需要这次运行在盘上,而且是在决定做出之前就被拒绝

Status: implemented

[English](2026-09-16-a-decision-needs-the-run-on-disk.md) | 中文

## 问题

`E2-submit` 是本部署从 `gated` 走到 `passed` 的唯一通路,而推动它的那个决定:要么是持久化的,要么什么都不是 —— 只活在服务进程里的决定会被重启忘掉,恢复出来的运行又显示闸门 `gated`,请人批准一件他已经批准过的事。

而一次保存正在失败的运行,照样被裁决了。`submitApproval` 先应用决定、再写它;写失败时,它在一个内存里早已持有 `status: passed` 的运行旁边回答 `persisted: false`。[失败的检查点就是运行的状态](2026-09-16-a-failed-checkpoint-is-the-runs-state.zh.md) 让这次失败变得可见 —— 运行把它作为持久化记录的 `error` 报出,并拒绝就绪 —— 同时刻意没有阻断审批,并记下"要阻断它应当放在审批自己的前置条件里"。

把它留在那里,代价不是一个报错的报告,而是它造成的状态:闸门在一个注定会被遗忘的进程里是 `passed`,快照仍说 `gated`,而调用者被告知自己的决定不持久,却无从补救。

## 决定

**`submitApproval` 读取这次运行最后一次落盘的写入,并在它报出失败时拒绝。**

- 这项检查与其他前置条件 —— 运行、步骤、`humanGate`、当前状态、当前 attempt、期望版本 —— 并列,因为那是唯一还能让决定不发生的位置。决定之后的拒绝,是对已经发生的事的汇报。
- 新的错误码是 `research/approval-save-failed`,消息里带着部署自己的原因,所以操作者读到的正是页面正在渲染的那个原因。
- 读的是投影渲染的那条事实(`ResearchRunSnapshot.runPersistence`),经由同一个访问器(`livePersistence`)。因此 `submissionReady`、就绪说明与这次拒绝,不可能对"运行是否在盘上"给出不同答案。
- `RememberedRun` 新增 `saveState`,同时 `persist` 变为必填。一个能写决定的调用者,无法忘记说明"它所属的运行是否在盘上";不保留持久化记录的部署回答 `null` —— 那是关于部署的事实,不是一次失败。
- **恢复靠运行自己的下一次写入。** 拒绝永远不会被记住(账本只缓存答案),所以运行恢复可写之后,同一条命令 id 就会被裁决。运行仍在被驱动期间,下一个落盘的检查点会清除这次失败。驱动一旦停止,本进程内就没有任何东西再写这次运行,所以**最后一次**写入失败的运行会一直被拒,直到它被重新驱动 —— 拒绝里说明了这一点,而负责重新驱动的那个操作属于断线恢复那一项工作,不是这一项。

## 考虑过的替代方案

**只在运行自己的收尾写入失败时拒绝,其余情况仍报 `persisted: false`。** 这是对缺陷最窄的读法,而它把一条事实劈成两半:一个在被驱动期间检查点一直在失败的运行仍会被裁决、被应用,然后才被告知不持久 —— 正是同一个失败,只是推迟了一个进程的寿命。页面已经在告诉读者这样一次运行不就绪;审批必须说同样的话。

**用"决定前先写一次"来证明可持久。** 守卫可以调用运行的写入器,把写入成功当作证据,这也能治好陈旧的失败记录。代价是每次恢复成功的审批多写一次;它把一次写入放到模块明文记载的"决定之后再持久化"之前;而且它只证明了部署刚才写得下去 —— 决定仍然要在其后写入,那次写入仍然可能失败。读取运行自己的记录,是更弱但被诚实陈述的断言:这次运行现在在盘上,所以关于它的决定可以做出。

**拒绝,并依赖已有的 `persisted: false` 报告。** 那正是已发布的行为,也正是它造成了上面的状态。一个在闸门已经移动之后才到达的报告,无法把那一步移回去。

**让客户端拒绝 —— 页面本来就显示"未就绪"。** 页面是那条事实的渲染,不是它的执行。`submitApproval` 可以被任何进程内调用者、也可以经由已认证通道到达,而只有读者自己的屏幕在执行的规则不是后端的规则。

## 后果

- 闸门再也不可能在一个"快照仍说 `gated`"的进程里因为写入失败而被移到 `passed`。剩下的失败模式是反方向的,也是安全的那一种:运行被拒绝,直到它可被写入。
- 这次拒绝是前置条件,不是门闩。`tests/approval.spec.ts` 钉住"事实清除后同一条命令 id 被裁决";`tests/start-run.spec.ts` 用真实服务分别在不可写目录(被拒、闸门未动)与"运行工作期间修好的损坏快照"(失败在运行中清除,随后决定被记录并持久化)上驱动。
- `snapshotOf` 的就绪参数现在是持久化记录的 `error`,而不再是检查点钩子自己的字段,于是 `submissionReady` 与这次拒绝读同一条记录。这堵上了此前允许的一处分歧:一次已停止、收尾写入失败的运行会报"就绪",而针对它的审批却会被拒。
- 审批的写入器在登记项上从可选变为必填,顺带删掉了把"没有写入器"与"写入器返回 null"当作通往同一答案的两条路径的那个分支。
- **本次没有做的**:让一次已停止的运行重新可写。一次带着失败收尾写入而停止的运行,在本进程里无法被裁决,因为这里没有任何东西会再写它;操作者会被告知的正是这一点。从快照重新驱动一次运行属于断线与恢复那一项工作,在它存在之前,这类运行在浏览器里的补救手段还不存在。
