# Agent Note: The run maintains one document on disk

Status: implemented

English | [中文](2026-09-19-the-run-maintains-one-document-on-disk.zh.md)

## Problem

Nothing in the pipeline touched disk until export. The document was a value in the artifact registry, and the files a person actually wants — the `.docx` a journal takes, the `.tex` an author edits, the figures it embeds — were written once, at the end, into a package nobody was expected to change. Two consequences followed that no test could see.

The first is that a person who wanted to fix a sentence had no file to fix. The registry is the pipeline's own store; the only way to reach it is through the run. `D4-rebuttal` and the manuscript-revision flow both produce replacement prose, and both require the run to be driven: a correction that takes a person thirty seconds in an editor costs a revision request, a generated candidate, a review and an acceptance, and a reviewer has to have been configured for any of it to be possible.

The second is the one that made this worth doing: **there was no way to hand a file back at all**. A pipeline that writes a document and cannot read one has no answer to "I fixed the typo in the methods section" except to ask a model to reproduce prose a person has already written. And a pipeline that DID have one — reading whatever bytes happened to be in a directory and calling them the manuscript — would adopt text no gate has ever seen, under a version number that says it did.

## Decision

- **A deployment setting, `manuscriptDirectory`, resolved like the three directories beside it.** `<root>/<runId>/` holds `manuscript.md`, `manuscript.docx`, `manuscript.tex`, `manuscript.pdf` (only when the compiler's own probe advertises pdf), `figures/<label>.svg`, `assets/<label>.png`, `tables/<label>.{md,csv}`, `refs-pdf/<citeKey>.pdf`, and `document-manifest.json`. It is a DEPLOYMENT setting and not a request parameter for the reason `packageDirectory` is: `runPipeline` is a Remote method, so a request-supplied path would let a browser choose where the host writes files — and the import reads its file from here rather than from a path a client named. **Configured with no `document` compiler, the load is REFUSED with the reason**: a directory whose whole purpose is to hold a document a person edits has nothing to put in it without a toolchain, and the alternative is discovering that at the last step of the first run.
- **The registry stays the authority; the directory is a projection of it.** `planManuscriptDirectory` builds every file from `getRunSnapshot(store, runId).registry` and never from an executor's return value, so the directory cannot describe anything a commit refused. The Markdown, the figures, the rasters and the tables come from the `manuscript` artifact — the one document the run maintains — and the compiled deliverables from `typeset`, because only a compile produces a `.docx`.
- **The projection runs in `drive.ts`, immediately after a step commits successfully.** That is the single place the driver observes a commit: `runStep` either committed or returned a non-success status, and every other caller would be guessing which. It sits BEFORE the gate, because the gate does not decide whether the work exists — a blocked or failed step's output IS committed, and the person editing the file has to see the document the run actually holds.
- **A projection failure does not fail the step, and is recorded twice.** The step has already committed, so throwing away real work in order to complain that a copy of it did not land is the trade `checkpointAfterStep` already refuses. It is appended to the run's own audit log as `manuscript-projected` (core's `recordManuscriptProjectionFailure`, read by the panel through `ResearchRunSnapshot.manuscriptDirectory` and by `checkFinalPackage`) and carried on the step outcome as `projectionError`. **Only failures are recorded**: a projection that landed is on disk, which is the record, and an event per successful projection would put sixteen copies of a file list into the log for no reader.
- **`document-manifest.json` carries `manuscriptRef` (version + contentHash), `documentHash` (the digest of `manuscript.md` as it landed), `renderedFrom` (the typeset form the compiled files came from) and `files` in the same shape the package manifest uses.** The last of these is not tidiness: it makes drift detection the existing `checkPackagedFiles` comparison rather than a second one written here. **Two drift facts are reported separately**, because the remedies differ — `edited` is a file on disk that is not the bytes the manifest recorded (re-project), and `runMoved` is the run holding a version the directory does not project (re-render) — and `describeManuscriptDirectoryDrift` names which applies.
- **The write discipline is one implementation.** `staged-directory.ts` is `writePackageFiles` and `publish` extracted: staged, verified against its own manifest, then swapped in, with the previous directory put back on a failed swap. Two directories carried the same discipline twice, and the second copy was reachable only through the package export — so the assertions about it moved to the helper rather than being deleted. It also refuses a plan that lists one path twice, which is a real defect the extraction exposed: two files at one path is a directory that cannot be what its manifest says, whichever landed last.
- **The round trip is an explicit, gated operation.** `publishArtifactVersion` is the third way `acceptance.ts` argues for: publishing a new version of an artifact a step already wrote is neither a commit (there is no attempt to write through) nor a plain registry write (no guards, no producer, no record). Its own module, its own refusals, its own audit kind `artifact-republished`. The import refuses a manifest entry the run does not have, a file this run never projected, a file that is byte-for-byte what was projected, a format the deployment's compiler cannot read back, and a document version the run has left behind. **What it publishes is a new version**, so a sentence that changed loses the judgement bound to it — the mechanism working, not a case to smooth over.
- **What each format loses is recorded, and the difference between formats is the point.** `.tex` holds its text and its mathematics verbatim; a `.docx` holds comments, cross-reference fields and embedded media that no Markdown rendering keeps, and `PandocCompiler.read` reports the ones it can see — a Word comment is detected by the `word/comments.xml` part the OOXML package really contains, so the loss is reported when the file has one rather than claimed for every `.docx`. The losses travel on the receipt, in the audit detail and in the assembly's own record of what it matched.
- **Sections are matched by heading and never by position.** A person who reorders two sections has reordered them, and matching by index would read the second section's prose into the first section's judgement. A heading that matches nothing is REPORTED rather than appended: a section this pipeline never wrote has no argument-plan obligation, no citation bindings and no place in the outline.
- **`materializeManuscript` re-renders the typeset form, and does not re-run E1's gates.** The obligations E1 checks were discharged where the document was assembled and their verdicts are recorded against that step; re-running them here would be a second adjudication nothing records. What a hand edit costs is caught where it should be: an approval names the artifact versions it was taken on, so the acceptance or import that moved the document leaves the approval stale and the run cannot be exported as final until a person approves the version that now exists.

## Alternatives considered

- **Have the driver write files in place instead of staging them.** Rejected: a half-written directory is indistinguishable from a finished one, and the person editing the file is exactly the reader who cannot tell — the manifest from the previous projection would sit beside files from the failed one.
- **Record every projection, successes included.** Rejected: sixteen copies of a file list per run, cloned into the log, for a fact the files on disk already state. The absence of a failure means "no projection failed"; a deployment that configures no directory has no entries at all, which is a different fact and is carried by the configuration.
- **Let the import take a filesystem path.** Rejected: the same reason `manuscriptDirectory` is a deployment setting. The request names a FORMAT, and the path is resolved here.
- **Re-run E1's checks inside `materializeManuscript`.** Rejected: those verdicts are recorded against the step that made them, and a second adjudication at a repair would report a gate result nothing in the run's history backs. The approval is the mechanism that makes a hand edit cost something.
- **Parse the `.tex` and the `.docx` in this package.** Rejected: one is TeX and the other is a ZIP of OOXML. The compile seam already says a deployment's toolchain renders a document; reading one back is the other direction of the same seam, so `DocumentCompiler.read` is optional there and a deployment that cannot read a format refuses the import with the format named.
- **Adopt a heading the document has no section for.** Rejected: it would publish text no gate has seen, under a section the argument plan does not oblige and the citation bindings do not cover.

## Consequences

- A deployment that configures `manuscriptDirectory` gets a real document on disk from the first writing step onward, and a person can edit it. `@Remote('importManuscript')` and `@Remote('materializeManuscript')` are the two operations a page reaches; both are also driven in `tests/manuscript-round-trip.spec.ts`, which runs the real pipeline and the real service rather than hand-building either.
- `Core` gained two audit kinds (`artifact-republished`, `manuscript-projected`) and two modules: `engine/publication.ts` (the operation `acceptance.ts` is a special case of) and `engine/manuscript-projection.ts` (the failure record). `appendAuditEvent` is still not exported — each new kind has one narrow writer, which is what the core entry's header requires.
- `AuditEventKind` is mirrored in `run-persistence.ts`'s load boundary, and both members are there; a run persisted by this build loads in it.
- `ResearchRunSnapshot` gained `manuscriptDirectory` and `StepOutcome` gained `projectionError`, so `runner-registry.spec.ts`'s shape tripwire was updated — the question it asks ("does the view need this?") is answered yes for the first and no for the second, and the second is why the driver's own result carries it.
- The `describe` in this note's sibling, `2026-09-19-one-document-one-slug.md`, still holds: there is one `manuscript` slug, and an import is one more publisher of a new version of it.
- **Not done here**: `dsh-research-web`'s panel does not render `manuscriptDirectory` yet, so the field is on the wire and unread by the shipped tab; the working directory's `manuscript.md` is rendered by `renderDocumentMarkdown` from the document model, which is not byte-identical to E1's assembled Markdown, so the two files that describe one paper are two renderings of it rather than one file written twice.
