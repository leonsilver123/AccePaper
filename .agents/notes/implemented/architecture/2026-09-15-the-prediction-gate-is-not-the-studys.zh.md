# Agent Note:判决门不是研究的一部分 —— 被测量的量是参数

Status: implemented

[English](2026-09-15-the-prediction-gate-is-not-the-studys.md) | 中文

## 问题

`runner/platoon-sim.ts` 里装着两件互不相干的东西。一件是跟车仿真 —— 智能驾驶员模型、装反应延迟的环形缓冲、碰撞时间。另一件是"一条主张到底能不能被判决"的纪律:它的散文有没有点出它声明的那个量、它写下的锚与方向词跟它自己声明的承诺对不对得上、一个否定会不会让这句话的语气变得读不出来。那个文件一千五百行里大约六百行是第二件,而它没有一行是关于交通的。

代价是在流水线不再只研究一个题目之后才出现的。`evaluatePrediction` 读模块级的常量拿指标键、读模块级的表拿主张必须用到的措辞、读模块级的标签拼证据串,而且它自己去跑车队比较。别的领域的研究要够到这套纪律,就得先 import 一个跟车模型 —— 于是"研究是什么由部署配置决定"这件事靠配置根本到不了,得先做这个拆分。

## 决定

**纪律搬到 `runner/prediction-gate.ts`,被测量的量变成它的参数。**

- `MeasuredMetric` 带着主张声明的键、给人看的标签、值越大是否越好、以及主张必须真的用到的那些措辞。研究里那四个并排的常量收成一个由它构造的 `MEASURED_METRIC` 对象。
- `PredictionMeasurement` 取代研究的 `PlatoonComparison`,成为门所判决的东西,而且是一个**封闭的二选一**:要么是一个可比的结果(相对改进量,加上研究自己给两条臂起的名字),要么是"没有可比的东西"的理由。第二个分支里**根本没有** `relativeImprovementPct` 这个字段,所以"没得比"没法被表示成"没有改进" —— 那正是 C 通道那条 fail-closed 的弃审要挡住的塌缩。
- `PredictionGateInput.measure` 是一个**回调**,不是一个值。门只调它一次,而且在每一道主张级检查都过了之后 —— 这样就保住了本来就在、而且已经被审计过的那条次序:先跑比较会让一次撞车的测量把三道措辞缺陷全盖住。
- "不可比"的那句话是**研究**写的,不是门写的。门不知道什么叫碰撞、也不知道两条臂叫什么名字,而替一次自己没做过的测量编一句话,正是这个模块其余部分存在的意义所在。
- 调用方(`registry.ts` 的 C1 执行器、`verdict.ts` 的 C 闸门)传 `measure: () => measureStudy(study)`;红队评审读同一批辅助函数,并用 `phrasingsFor(material.metricKey, MEASURED_METRIC)` 解析出措辞。

## 考虑过的其他方案

**把 `evaluatePrediction` 留在原处,在研究里加一层薄的位置参数适配。** 按仓库的预发布立场否决:那就是一个兼容垫片,而它保住的那四个位置参数正是新输入改成对象的理由 —— `(predictionText, study, metricKey, commitment)` 末尾两个可选参数,调用方只能靠数数分辨。

**把测量当值传进来,而不是当回调。** 否决,而且这个是会**静默**出错的:一个被提前算出来的测量跑在主张级检查**之前**,于是一次什么都没测出来的研究会把矛头指向自己,而不是指向主张本身的缺陷。这条次序是有文档、也被审计过的;值保不住它。

**保留那张按指标键索引的封闭 `METRIC_PHRASES` 表。** 作为表否决,作为规则保留:`phrasingsFor(declaredKey, metric)` 只在主张声明的就是这个研究的指标键时返回它的措辞,于是绑在别的量上的主张仍然什么都拿不到 —— 这正是那张封闭表原有的性质。把它做成函数而不是记录,才是让指标能当参数的前提。

**方向词照旧拿改进量的符号来判。** 在新 spec 用例里那个合成指标跑起来之后否决:见下面那条后果。旧公式是出货研究自己的约定,却写得像是唯一的约定。

## 后果

**浮出来一个真缺陷,而且它是一个 `higher-is-better` 假定。** `inClaimDirection` 原先按 `direction === 'increase' ? improvementPct : -improvementPct` 算。这只有在"值越大越好"时才对:在一个"越小越好"的量上,一条说该量 "shall lower" 的主张被判成要的是反方向,于是一个其实满足它的测量被报成反驳了它。门现在读 `MeasuredMetric.direction`。车队研究的行为不变 —— 它的方向是 `higher-is-better`,两种读法在那里一致 —— 这正是找出这个缺陷的用例必须换一个指标的原因。

**这套参数化是在门自己的接口上被证明的,不是端到端被证明的。** 第二个指标是 `tests/prediction-gate.spec.ts` 里一个合成的延迟量。那个用例走的是一条主张、一次测量和一条不可比的理由穿过同一条代码路径,但这棵树里没有第二份研究,所以"别的领域的研究够得到这套纪律"靠的是接口,不是一次出货的流水线运行。

**纪律有了自己的 spec 文件。** 原先 `tests/platoon-sim.spec.ts` 同时钉住两半;43 个用例按主题拆进了仿真那个文件和 `tests/prediction-gate.spec.ts`,于是一次对门的改动不再读起来像是对模型的改动。门的 spec 多了四个针对参数化路径的用例,其中一个是上面那个方向缺陷。

**每一处引用都改了,没有做再导出。** `MEASURED_METRIC_KEY` / `_LABEL` / `_DIRECTION` / `_PHRASES` 都不在了;`registry.ts` 里那十处、`verdict.ts` 里那两处、评审器、resume 读取器以及四个 spec 文件改读 `MEASURED_METRIC` 的字段。树里没有任何地方 import 一个已经不存在的名字。
