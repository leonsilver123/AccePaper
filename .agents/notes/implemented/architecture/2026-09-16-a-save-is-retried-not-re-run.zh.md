# Agent Note: 失败的保存是重试,不是重跑

Status: implemented

[English](2026-09-16-a-save-is-retried-not-re-run.md) | 中文

## 问题

一次运行对快照的写入失败之后,它就不在盘上:重启会丢掉它,而且 —— 自从[决定需要这次运行在盘上](2026-09-16-a-decision-needs-the-run-on-disk.zh.md)之后 —— 它到达的那道人工门也无法被裁决。拒绝会说出部署自己的原因,并由运行的下一次写入自行清除,这覆盖了**仍在被驱动**的运行;它覆盖不了浏览器实际会遇到的那种情形:运行**已经停止**(E2 是人工门,所以驱动已经返回),最后一次写入失败,而进程里再没有任何东西会写它。

系统当时提供的唯一出路是**把研究再驱动一遍**。这在构造上就是错的补救:这次运行已经花掉了它的模型调用,而第二次执行会在同一名字下产出不同的数字 —— 那篇论文就不再是被测量的那篇。

## 决定

**运行的当前状态可以被再写一遍,而那次写入是它自己的命令。**

- `@Remote('retryRunSave')` 把本进程为某次运行**持有的**状态写进它的快照,并回答写入的结果以及写入之后重新投影的运行。
- **它与磁盘对账**:基准版本从磁盘当下的状态读出,所以被别的写入者移动过的文件不会被盲目覆盖。每一次尝试也走与检查点相同的串行写入器,因此重试不可能与检查点交错。
- **它推进快照的写入计数,绝不推进运行的 `projectRevision`。** 这是两个不同的数字 —— 一个数的是对文件的写入,另一个数的是研究提交了什么 —— 而把同一份状态再写一遍没有提交任何东西。因此重试之前做出的决定仍然命名着一个当前版本,它被约束的绑定与之前完全一样。页面从重试回答的那份投影里重新读到版本。
- **本进程不持有的运行会被拒绝。** 从文件读回来的运行已经处在它文件所记录的状态;再写一遍没有磁盘上还没有的内容,而重新执行它不是保存。拒绝里说明了调用者要的是哪一种。
- **持久化记录只有一个来源。** 重试通过与其他写入者相同的 `noteSave` 规则报出结果,因此 `livePersistence`、`submissionReady` 与审批的前置条件看到的都是刚刚落盘的那次写入,而不是它刚从其中恢复的那次失败。
- 工作台在**后端自己报出** `saveFailure` 时提供这个重试,并渲染重试回答的那份运行。不能重试的部署**不显示**这个控件,而不是显示一个按不动的按钮。

## 考虑过的替代方案

**保存失败时把研究重跑一遍。** 这是从"不在盘上"到"在盘上"最短的一条路,而它在产品存在的理由上输了:稿件、图表与实测数字会描述第二次执行,而批准了第一次的读者批准的东西已经不存在了。它还让每一次磁盘故障的代价乘以一项研究的代价。

**让客户端把它读到的最后一份快照写回去。** 页面持有的是投影,不是运行的状态:工件、闸门裁断与审计日志都在 store 里,而一个把自己视图写回去的页面是在发明一份记录。写入应当发生在状态所在的地方。

**写入失败时自动重试。** 重试循环会掩盖一个写不下去的部署,而人最需要看到的那条失败 —— 磁盘满了、目录没了 —— 会被报成"研究有点慢"。重试是显式的,并且在被使用之前页面一直陈述那条失败。

**把重试自己的版本号存下来供调用者比较。** 快照的计数已经在 `runPersistence.revision` 里,投影也带着它。为同一个数字再开一个字段,就是一份可能和第一份打架的副本。

## 后果

- 从"部署的写入路径坏了又好了"到"闸门可以被裁决"之间的路径现在是一次保存重试,研究绝不会被做两遍。
- 客户端获得了它第一个既不是启动也不是审批的写命令,而且它是在**后端报出的事实**上提供的,而不是页面自己对数字的解读。
- **本次没有做的**:它无法恢复一份状态已经不在的写入 —— 重启后的记录本身就是磁盘的内容,而一个在写入失败之后死去的进程也没有更新的东西可以提供。那种情形属于断线恢复那一项工作,不是这一项。
