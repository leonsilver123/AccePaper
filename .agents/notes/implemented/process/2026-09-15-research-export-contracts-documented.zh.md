# Agent Note:研究包为导出面写下契约

Status: implemented

[English](2026-09-15-research-export-contracts-documented.md) | 中文

## 问题

两道文档门禁在研究包上一直是红的,而 `pnpm run test:docs` 都看不到它们。

实测:`verify-export-jsdoc` 列出 **280** 条缺失的 `@param`/`@returns`(各类违规共 411 条),分布在 `dsh-research-{tools,core,team,cordis}`;`gen-config-catalog --check` 列出 **9** 个没有 JSDoc 散文的 config 字段,全在 `dsh-research-cordis`。第一道门禁不在 `run-gates.ts` 的 `quick` 集合里,所以 `test:docs` 从不运行它;两道都在完整的 `doc-sync`/CI 路径上。

后果不是外观问题。本仓库的前提是 **AI 生成的科学主张不可信**,而研究层正是这些主张的产出地。一个导出函数旁边没有 `@param`,它就没有陈述任何契约:读者 —— 人或 agent —— 无法知道某个参数是做什么的,复核调用点是否表达了签名所允许的语义的人同样无从判断。

## 决定

**按签名要求为每个导出补上它需要的标签**,逐包推进,一个包只有在两道门禁都通过时才算做完。

仓库为这项工作定下的批次规则是有约束力的:**某个导出无法用一句清晰的话描述时,优先质疑导出面,而不是写废话 JSDoc**。注释陈述的是代码**实际具有**的契约,不是复述代码:一个参数要满足什么条件这次调用才成立、返回值携带什么、以及调用方必须处理哪一种失败。

先做的是 `dsh-research-cordis`:52 条标签与 9 个 config 字段已完成,该包在两道门禁下都干净。

**第一个包就查出了一处门禁说不出名字的缺陷。** config 门禁报为"无文档"的那个字段 `Config.requireResearchTools`,它的散文**是存在的** —— 只是被搁浅在三个声明之上的一个孤立 JSDoc 块里,那是该接口更早一版的修订留下的位置。一个什么都没在文档化的块比没有块更糟:它读起来像文档,而它所描述的字段却被报成缺失。那段散文被移到了它所描述的字段上,既满足门禁,也把这个包带进了生成的目录。

## 考虑过的其他方案

**把研究包从 `verify-export-jsdoc` 豁免掉。** 否决:这道门禁存在的意义就是让导出面陈述自己的契约,而研究层恰恰是要求读者去信任其产出的那一层。在这里豁免,正好就是本仓库前提所排除的安排 —— 最难核查的主张,配最少被陈述的契约。

**写复述参数名的 `@param`。** 否决。那会让 CI 变绿,同时把当时的 API 面永久固化成一堆装饰 —— 这正是批次规则点名的失败形态。凡是真的写不出诚实标签的地方,该改的是那个导出本身。

**只补模块散文,标签留到以后。** 不可行:门禁要的就是标签,拆开做只会让两道门禁红得更久,而且没有部分完成这一说。

**让孤立的 JSDoc 块留在原地,只在字段上加一小段标签块。** 否决:那样会有一个字段被两段文档描述,而搁浅的那段还在描述一个已经不存在的声明。

## 后果

**生成的 config 目录多了两个包。** `docs/config-catalog.md` 现在带 `@deepseek-ai/dsh-research-cordis` 与 `@deepseek-ai/dsh-research-team` 两节,以及末尾两个清单里的四条,因为一个包只有在它的 config 有文档之后才会出现在那里。中文对侧是**手工**维护的 —— 文件自己的头部就是这么写的 —— 所以那四条清单项与两个新小节被镜像进 `docs/config-catalog.zh.md`,并用 `verify-translation-pairing --write` 重记了配对。

**这道门禁查的是包的**入口**够得着什么,不是包里的每个文件。** `dsh-research-core` 没有导出 `./src/*` 子路径,所以 `verify-export-jsdoc` 通过构建产物 `lib/types/index.d.ts` 与 `lib/types/host-prod.d.ts` 解析它的导出面。`GATE_ERROR_PREFIX`、`appendAuditEvent`、`_applyHumanApproval` 这三者从两个入口都够不到,门禁**从来没有报过**它们,它们也不在那 280 条里。它们仍被补齐了,为的是与旁边的同类保持一致。所以"门禁绿"的含义是"消费者能 import 的每一个名字都陈述了契约" —— 这正是门禁的主张;它**不等于**"每个文件里的每个导出名"。

**一处既有注释被证明是假的,而它所在字段的文档把这件事实说了出来。** `RoadmapNode.kind` 被描述为"可选的自由布局提示",但没有任何渲染器或校验器读它 —— 分层布局只按边放置节点。这个标签由调用方写入,原样进入产物。如果只在接口层如实描述、却把那个描述着"无人实现的效果"的字段注释留在原地,更正的正下方一行仍然躺着那句假话,所以字段注释被改写为陈述事实。

**文档不等于完成。** 通过 `verify-export-jsdoc` 与 `gen-config-catalog --check`,说明每个导出如今都陈述了契约;它不说明那个契约是**对的**。这一批的证据就是这两道门禁加上没有回归的测试套件,本文里的任何内容都不把某个包在完成度阶梯上往上移一级。
