# Agent Note: 拒绝要被说出来,空语料不是一张景观图

Status: implemented

[English](2026-09-18-a-refusal-is-not-a-no-match.md) | 中文

## 问题

一次运行停在 `D3-writing`,而产品说不出为什么。阶段标记写着 受阻,运行的「下一步」选择器里根本没有「被拒绝」这个状态,于是它把运行报成仍在进行;而真正的原因 —— 论文大纲声明了 `references` 这一节,起草步骤把它留成了空 —— 躺在一份没有任何页面显示的闸门判决里。复盘这个原因,用上了这次运行自己的快照、拿同一个主题字符串打一次真实目录(当天 1639 条命中,前 25 条全都带 DOI),以及读四个文件。记录本身回答不了这个问题,因为它需要分开保存的两个事实以同一个值到达:*目录答了、什么也没匹配到* 和 *目录答了、但适配器的过滤把所有匹配都丢掉了*,都长成 `outcome: ok, hitCount: 0, hits: []`。

复盘过程中读检索通路,又发现同一类塌缩还有四处。目录持有但没有 DOI 的记录被 OpenAlex 适配器丢弃,于是 *这个适配器无法用外部标识命名它* 传到管线里变成了 *不存在这样的文献* —— 而共享的引文契约在 2026-09-18 已经放宽到 `isbn`、`standard` 与 `unknown`,只是那条放宽只落在 Zotero 通道上。一个 `200` 但正文不是结果信封的响应 —— 代理改写、限流提示、schema 变动 —— 被读成真实的「无匹配」,而这个适配器自己的类文档承诺过绝不把故障报成无匹配。landscape 产物丢掉了工具产物上的 `truncated`。而 A1 这一步对「没有记录就没有景观图,所以这一步直接失败」这条写在它自己注释里的教条,只对故障生效;于是一次答了却什么都没匹配到的实时语料通过了 A1,并在五步之后以「写作被挡下、原因是参考文献缺失」的形态浮出水面。Zotero 通道的主题过滤另有一处缺陷:它要求主题里每个超过三个字符的词都以原始子串形式出现在标题或摘要里,所以主题 `Robustness of platoons to mixed-traffic disturbances` 匹配不上一篇题为 "Robust platoon control in mixed traffic flow" 的论文,而放着这篇论文的书库被读成空语料。

## 决定

- **主题词可以匹配以它开头的标题词。** `matchesTopic` 现在接受 `haystack.includes(word) || tokens.some(token => token.length >= 4 && word.startsWith(token))`,既保留了刻意为之的「主题内容词全都要命中」,也保留了子串那一半 —— 正是它让主题词 `take-over` 能命中把这两个词写成一个词 `takeover` 的标题。这条规则只会增加命中,从不减少。它仍然是一个关键词过滤器,并且如实这样说:没有词干还原,方向是单向的(`analysis` 找不到 `analyses`),四个字符的下限也允许 `plan` 被读成提到了 `platoons`。
- **没有 DOI 的文献是命中,不是伤亡。** `toHit` 只在记录既无 id 又无标题时才跳过。没有 DOI 的文献以 `ref: { kind: 'unknown', id: <OpenAlex work id>, title, authors }` 输出,那是来源自己的登记表为它铸造的身份 —— 这套顺序与理由,Zotero 适配器里的 `refOf` 早已为收藏条目陈述过。
- **不是结果信封的 `200` 就是故障。** `search()` 要求正文是一个带 `results` 数组与 `meta` 对象的对象,否则解析为 `unavailable`,并在详情里说明到达的是什么(`arrivedAs` 会按键名报出代理的错误对象,或报出数组、标量)。`{ meta: { count: 0 }, results: [] }` 仍然是 `ok` 且零命中 —— 这条区分正是本次改动存在的理由。
- **landscape 产物带上那个封顶前的标志。** `a1Executor` 把工具产物的 `truncated` 记进 `landscape-map`,于是运行的记录能分开「答了、零匹配」与「答了、但被过滤器清空了」。
- **匹配不到任何东西的实时语料让 A1 失败。** 在既有的 `unavailable` 拒绝之后,`a1Executor` 在 `liveCorpus && artifact.hits.length === 0` 时抛错。错误信息点名主题,并说明这不是故障 —— 因为补救方式不同:故障是网络,而这是主题或这个部署点名的语料。

## 考虑过的其他做法

- **让空的实时语料像原来那样走到 `D3-writing` 再停下。** 不采纳:那正是这次事故无法定位的原因。挡住运行的那条拒绝说的是参考文献,而那是后果;原因 —— 这个主题在这个部署点名的语料里什么都没匹配到 —— 不在任何产物里,运行的记录也无法把它与「被过滤成空」区分开。一个全部产出就是一张景观图的步骤,不能在一条记录都没带的情况下通过,这一点该步骤自己的注释对故障早已写明。
- **把「不是结果信封的 200」报成零命中的 `ok`,让适配器的过滤器背锅。** 不采纳:这种正文里没有任何东西说明目录持有什么,所以 `ok` 断言了响应并不携带的事实,而管线据此写出一份参考文献为空的稿件。该适配器的类文档对每一条其他失败路径早已承诺相反的做法。
- **在 OpenAlex 适配器里继续要求 DOI,把放宽后的契约当成 Zotero 专用。** 不采纳:`LiteratureRefKind` 这个联合类型由两条通道共用,两者会对同一个问题给出不同答案,而 `unknown` 这个新增种类会在通往开放目录的那条通道上不可达 —— 那恰恰是书、标准与没有 DOI 的报告最可能出现的地方。
- **把目录封顶前的 `total` 也加进工具产物。** 不采纳:`truncated` 就是由那个 total 推导出来的,所以那条「零匹配还是被过滤清空」的区分它已经带着了;加入原始计数要改动冻结的工具产物、`buildArtifact` 的两个分支以及该工具自己的产物断言,却换不到多一个比特的含义。这里记为刻意不加,而不是疏漏。
- **把主题过滤的全要命中放宽成命中任一。** 不采纳:那条 AND 是刻意为之且有文档的 —— 对一个写成句子的主题,命中任一等于返回整个书库 —— 而缺陷在原始子串测试,不在这个合取。

## 后果

- **空的实时语料现在让运行停在 A1,而那条过去用来端到端演练 D3 拒绝的场景,通过驱动已经到不了。** 拒绝含空章节稿件的机制仍然可达 —— 一次带记录答复的语料仍可能留下某一节起草步骤填不上 —— 而这条规则在 `manuscript-review.spec.ts` 里保有直接的单元覆盖;过去经驱动端到端跑它的那个用例,现在换成了 A1 的用例。这是「更早失败」的代价,写在这里而不是被吸收掉。
- **`truncated` 的好坏取决于各通道 `total` 的含义。** OpenAlex 通道报的是目录封顶前的匹配数;Zotero 通道报的是它自己主题过滤之后的匹配数,所以一个被过滤器清空的书库仍然报 `total: 0, truncated: false`。产物获得的这条区分,在一条通道上是精确的,在另一条上要弱一些。
- **一次拒绝现在会让运行失败在产品必须渲染的位置上。** A1 失败是一个带执行错误、没有产物的步骤,而这是阶段视图与运行列表早已会显示的状态;报告它的面板,就是报告其他所有步骤的那一个。
- **没有任何闸门、阈值或证据模式被移动。** 每一处改动要么是如实报出管线过去报成另一种状态的状态,要么是取回目录持有而适配器丢弃的记录。改动前能通过的运行,改动后仍然通过,而检索取回的是更多而不是更少。
