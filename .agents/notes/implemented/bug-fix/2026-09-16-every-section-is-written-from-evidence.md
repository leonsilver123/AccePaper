# Agent Note: Every section is written from evidence, and one with none is refused

Status: implemented

English | [中文](2026-09-16-every-section-is-written-from-evidence.zh.md)

## Problem

`D3-writing` handed the model this context:

```ts
{ field, direction, sectionId, claimRef, figureCount, citable }
```

`citable` is a roster of float labels — "Figure 1", "Table 1" — not the data behind them. So the request carried five fields, and none of them was evidence. The run held the method spec, the measured result, the figure plan and the literature records, and not one of them reached the writer.

A faithful model was therefore asked to write a Results section it had never been shown the results of. The only thing between that and an invented number was the model's own restraint, and a model that declines to write is a model that has failed the instruction rather than one the pipeline has protected.

The other half of the same gap is what the run did when it had nothing. `bodyTextFor` generates deterministic sentences from the run's own numbers, and it says it is a fixture: `proseSource: 'fixture'` and a note. That is honest about the sentence and not about the document. A manuscript with a Methods section generated by a fallback reads exactly like a paper, and a reader cannot tell which sections were written from the run and which were filled in.

## Decision

`runner/section-evidence.ts` maps a section id to the run data that section is written from, and to the evidence it cannot be written without. `D3-writing` puts the first under `evidence` in the writer's request and refuses to write a section whose second is not satisfied.

The evidence is specific, because a generic blob would let the writer pick. The Results section receives the numbers with their unit and the rule version that produced them. The Method section receives the implementation AND an `execution` entry comparing the method's declared version against the result's — two artifacts in one run naming different versions is a manuscript whose Method describes code that did not produce its numbers, and that comparison needs both halves, so a method spec naming no version leaves the entry absent and the section refused rather than compared against nothing. The Experiments section receives the run accounting (`runs: 1`, `repeated: false`, `deterministic: true`, `fieldData: false`), which is what a reader needs to judge the numbers and what no section was stating. The Discussion receives the reviewed sources including the ones a reviewer judged `does_not_support` — a counter-source that never reaches the writer is the same defect as one that never reaches the gate.

A section whose required evidence is missing is not written at all. Not by the model, and not by `bodyTextFor` either: the body is empty, the draft records the section under `refusedSections` and the missing names under `sectionEvidence`, and the hole is visible.

**E1 turns out to be what a run actually hits.** `assembleManuscript` already refused an empty section body (`DSH_MANUSCRIPT_EMPTY_SECTION`) — a guard older than this change, which nothing had ever produced a section for. So a refused section propagates: D3 refuses it, E1 refuses to format a manuscript containing it, the run stops with a named reason, and no package is exported. `readinessOfRun` gained the same check as a second line rather than as the mechanism.

## Alternatives considered

**Give the writer the whole run and let it select.** Rejected. The request is the only place the pipeline decides what a section may assert, and a context that contains everything is one where nothing is enforced: a model that quotes the abstract-only source from the Keynote section is not detectable afterwards.

**Keep `bodyTextFor` as the fallback for a section with no evidence, and mark it.** Rejected, and this is the decision the change is really about. The marking exists — the artifact says `proseSource: 'fixture'` — and a marked fixture body still reads as a finished paper. The pipeline's premise is that a plausible-looking claim is the hazard, and a plausible-looking section is the same hazard one level down.

**Fail the D3 step when any section lacks evidence.** Rejected: it discards the sections that could be written, and the run then reports nothing about which section was unevidenced. Recording the refusal and carrying on lets E1 name the hole and lets a person fix the missing evidence.

**Require every section to list everything it could use.** Rejected: a section that refuses itself over a missing nicety is a pipeline nobody runs, and a pipeline that is not run enforces nothing. Each entry names only the evidence without which the section would have to assert something the run does not hold.

**Put the evidence in the instruction as prose rather than in the context.** Rejected for the reason the float roster was already in both: a value the model has to recover from a sentence is one it can get wrong, and the context is what a test can assert on.

## Consequences

- `packages/research` is at **1715 passed / 96 files**; `tsc -b tsconfig.host.json` is clean.
- **`tests/section-evidence.spec.ts` (14 tests) falsifies the refusal end to end**: a retrieval that succeeds and finds nothing leaves an empty `references` section, and the test drives that run through D3 and E1 and asserts the whole chain — `refusedSections: ['references']`, an empty body, `DSH_MANUSCRIPT_EMPTY_SECTION` on the E1 outcome, no manuscript artifact, and a readiness answer of not-ready. An empty retrieval is the one reachable way to starve a section, and it is a real state rather than a contrived one.
- `D3-writing` now declares `method-spec` as an input. The dependency-closure spec found the read before any test asserted it — the second time that spec has caught a real undeclared read.
- **The writer's context is now assertable.** The old context had nothing in it a test could check against the run; the new one can be compared, section by section, against the artifacts it came from.
- **The model path is not exercised end to end here.** The refusals and the supply are, and the request's contents are not: a driven run in this suite has no writer, so `D3` takes the fixture path. The request's `evidence` field is built by the same function in both paths, which is the argument that the two cannot diverge — an argument, not a test.
- **`sectionEvidence` names the supplied evidence KEYS, not the values.** The draft records `supplied: ['result', 'figures']`, not the numbers. A reader who wants to compare a sentence against the number it quotes still has to follow `resultRef` to the record.
