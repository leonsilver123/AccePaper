# Agent Note: One set of sources answers both citation questions, and a publication keeps the producer link it replaced

Status: implemented

English | [中文](2026-09-20-one-source-set-and-a-publication-that-keeps-its-producer.zh.md)

## Problem

Two defects, both found by the framework review of `2a8ab4d1`, both of the same class: a check whose input is empty in a way the check reads as satisfied.

**The gate that decides a claim is externally anchored and the roster the writer may cite from were two different sets.** `verdictB` built its anchor from `assessmentsFor(claimRef)` — the compiled evidence corpus — and `d3Executor` built the writer's roster from `judgementsFor(claimRef, ctx.sources)`, which reads the same corpus and then looks each assessment's source up **in the run's configured source map**. `sourcesForMode` keyed a registered source by `registration.identity` (`zotero:<type>:<library>:<itemKey>`, never a DOI) and `judgementsFor` looked it up by `assessment.sourceDoi`. The two sets agree only while `ctx.sources` holds the corpus's own three DOIs, which is true exactly when `sourceRegistryMode` is `'curated'` — and `dsh-research-cordis` defaults to `'zotero'` whenever a `sourceLibrary` is named. Measured: with a registration naming the DOI of a reviewed corpus source, `buildEvidenceAnchors` returned `anchoring=true, provenance=literature` while `judgementsFor` returned **0** judgements. So a deployment that names a library passed every anchoring gate on the compiled corpus, wrote a manuscript that cites nothing, and could export it as the package a journal receives: a paper with no literature, with the sign flipped on the defect the citation layer exists to prevent. Nothing downstream could see it — `checkManuscriptCitations` runs neither of its two loops when the body cites nothing and the reference list is empty, two empty sets are equal, and no condition in `FinalPackageCheckCode` asked whether the paper cites anything.

**A published slug could never satisfy a step input again.** `isInputSatisfied` requires a registry entry's `producerStepId` to name a step in `run.steps` whose status is `passed` and whose `attempt_id` equals the entry's `producerAttemptId`. `publishArtifactVersion` wrote `producerStepId: request.producer` and `producerAttemptId: 0`, and `acceptManuscriptCandidate` wrote `ACCEPTANCE_PRODUCER` and `0`. No step is named `manuscript-import`, `materialize-manuscript` or `human-acceptance`, and `0` is never a live attempt id, so after an import, an acceptance or a repair, `canStart('D4-rebuttal')` and `canStart('E1-format')` were false for the rest of the run. `rollback` did not help — `invalidateArtifactsFor` only touches entries whose producer and attempt match the rolled-back step — so the one recovery was rolling back to `D3-writing` and re-committing it, which overwrites the person's edit. Worse, the diagnostic written to name this cause could not: `startabilityOf` filtered `stepDef.inputs` by `resolveStepInput(...) === undefined`, and a published value resolves, so the missing list was empty and the operator was told the step "looks startable to the driver" — the misleading message `startabilityOf` was written to remove.

## Decision

**A registered source is cited and judged under the DOI it states.** `citationIdOf` (new, in `runner/citation-bindings.ts`) returns `registration.ref.id` when the ref is a DOI and `registration.identity` otherwise; `sourceRecordOf` uses it for `SourceRecord.id`. Every other end of the chain already keys on the DOI — `judgementsFor` resolves an assessment by `assessment.sourceDoi`, `citeKeyOf` mints the writer's marker from the id, `bibliographyOf` resolves a citation by it — so one key makes the two questions one set of sources, and `combined` becomes one set rather than two. The registry's own identity is not lost: it is the key of the source's `EvidenceBinding.sourceIdentity`, which is what the deployment's attachment reader resolves, and the spec asserts it survives. A registration whose ref is not a DOI keeps its identity, because nothing else in the run keys on an ISBN or an arXiv id.

**A run whose claim holds reviewed evidence and whose registry yields no citable source is refused at `prepareRun`.** `citableSourceRefusal(claimRef, sources)` states the condition and `drive.ts` throws it before creating the run — where the person who configured the registry still is, rather than at D3 where the writer is handed an empty list. THE CONDITION IS NARROWER THAN "THE ROSTER IS EMPTY", deliberately: a claim with no reviewed assessment at all is a claim the corpus says nothing about, the B channel reports that itself (under the production profile it abstains and the run holds), and refusing it here would refuse every study this repository ships that is not the compiled one — the second study `second-study-run.spec.ts` drives to the human gate. What is refused is the state where the anchoring gate would pass ON the corpus and the writer could cite none of it.

**A manuscript that cites nothing while the run held sources is refused at the final package, and reported by the quality baseline.** `FinalPackageCheckCode` gains `manuscript-cites-sources`, which reads a new fact `ManuscriptFacts.citations` = `{ made, held }`. `made` counts the distinct markers the manuscript's sections carry; `held` is the larger of the cite keys the run's own `proseRequests` offered its writer and `assessmentsFor(claimRef).length`, the reviewed evidence the corpus holds for this claim. This is the one condition that reads a citation COUNT rather than a citation's target, and it is what catches the outcome whatever its cause — including a run whose roster never reached the writer, which is the state no set comparison can see. `paper-quality.ts`'s `no-literature-position` gets the same fact as `PaperQualityInput.sourcesHeld`: it used to need `referenceCount > 0`, which is the half the defect removes, so it read "no bibliography" as "has nothing to cite" and stayed silent about exactly the defect.

**A publication inherits the replaced entry's `producerStepId` and `producerAttemptId`, and records the publisher in a new `publishedBy`.** The dependency the pipeline scheduled on is the step that produced the value this one replaces, and it is still the same artifact under the same slug; the inherited pair is what `canStart` reads, so a slug a person edited is still an input the steps after it can start on. Inheriting is not a claim that a step wrote this text: `publishedBy` says who published it on the registry entry a reader is looking at, `ArtifactRecordMeta.publishedBy` carries it through `getRunSnapshot`, `ResearchArtifactMetaView.publishedBy` carries it to the panel, and the publication's own audit record (`artifact-republished`, `manuscript-accepted`) names the publisher, the basis, and the version and hash it replaced. `acceptManuscriptCandidate` records `ACCEPTANCE_PRODUCER` the same way, and the snapshot reader keeps its two allowances for records an earlier build wrote.

**`startabilityOf` asks `isInputSatisfied`'s question.** Core gains `unsatisfiedInputs(store, runId, stepId)`, the same predicate `canStart` decides with, answered per input with one of four reasons — `absent`, `invalidated`, `producer-not-passed`, `stale-attempt` — and the driver renders the reason rather than a claim that everything looks in order. A step's explanation and the engine's decision cannot disagree now, because they are the same function.

## Measured

- **The keying divergence, before and after.** With `sourceRegistryMode: 'zotero'` and a registration whose `ref` is the DOI of a reviewed corpus source: before, `judgementsFor` returned **0** judgements while `buildEvidenceAnchors` returned `anchoring=true, provenance=literature`; after, `judgementsFor` returns the corpus's judgement under the cite key `cite-10.1109/tits.2026.3727135`, with the corpus's own `support`, `judgedBy` and passage. `tests/registered-sources.spec.ts` asserts both directions, and reverting `citationIdOf` to `registration.identity` fails five cases in that file and one in `citation-bindings.spec.ts`.
- **The publication link, before and after.** `tests/publication.spec.ts` drives a run whose D3 has passed and whose `manuscript` is published over by `manuscript-import`. Before, the published entry named `manuscript-import` with attempt `0`, `canStart('D4-rebuttal')` was false and `unsatisfiedInputs` reported `producer-not-passed`; after, the entry names `D3-writing` at its own attempt, `publishedBy` is `manuscript-import`, and both `D4-rebuttal` and `E1-format` are startable with no unsatisfied input. Reverting the inheritance fails all three cases in that describe.
- **The no-citation refusal, before and after.** `tests/package-export.spec.ts` drives a real 16-step run and publishes over `manuscript` the same document with every `[@cite-…]` marker removed. The package's `manuscript-cites-sources` check fails and the manifest state is `draft`; with the check's condition forced true, the case fails. The same file's real run, whose manuscript cites, passes it — the condition distinguishes a paper that cites nothing from one that cites.
- **The driver's message, before and after.** `tests/e2e/recovery-t19b.spec.ts` holds `A1-landscape` with a gate abstention (so its artifact is committed and its producer is `gated`, not `passed`) and drives `A2-claim`. Before, the driver said the step "looks startable to the driver"; after, it says `'landscape-map' was produced by 'A1-landscape', which is 'gated' rather than 'passed'`.

## Alternatives considered

- **Have `verdictB` take `ctx.sources` so both questions read the same map.** Refused as the weaker half: the registration is the unreachable end, and a `verdictB` that read the run's library would still find no judgement for the corpus's assessments — the run would then have no anchor either, which turns a citation defect into a B-gate abstention and hides the misconfiguration one step later instead of naming it.
- **Key the registered source by both the identity and the DOI.** Refused: two keys for one work is two reference entries for one DOI, which `checkCitationKeys` would refuse as `citation-duplicate-key` only after they had been minted. The map is keyed by the one name the rest of the chain resolves.
- **Refuse `prepareRun` whenever the claim yields no citable source, as the review states it.** Refused as over-broad and measured: `LATENCY_PLAN` — the second study this repository ships so that a run can be conducted as something other than the platoon study — yields 0 assessments and 0 judgements, so that reading refuses it at run start and `second-study-run.spec.ts` with it. A claim with no reviewed assessment is not a misconfigured registry; it is a claim the B channel reports on by itself. The condition implemented is the divergence the review measured: reviewed evidence exists and cannot be cited.
- **Put the no-citation refusal in `checkManuscriptCitations` as the review words it ("no citation marker in the body and `reviewedKeys` is non-empty").** Refused because it is vacuous where it is needed: `reviewedKeys` at that call site is `revised.citations` — the BINDINGS — and in the empty-roster outcome the bindings are empty too, so the guard fires exactly when the defect is absent. A manuscript whose bindings are non-empty and whose body has no markers already refuses at E1 through `citation-entry-uncited`. The refusal needs the roster, and the roster is `ctx.sources`, which that function is not given; adding a required field would have meant editing the call site inside `runner/registry.ts`, which another change held while this one was written.
- **Give the published entry a producer step id of the step the slug "belongs" to.** Refused: which step a slug belongs to is not knowable from the slug, and a table mapping slugs to steps would be a second copy of the pipeline's graph. The replaced entry is the authority on where the value came from, and inheriting it is exact.
- **Drop `producerAttemptId` from `isInputSatisfied`'s comparison so a publication satisfies it with attempt 0.** Refused: that comparison is what stops a superseded attempt's artifact from satisfying a re-run step, and weakening it would make a stale artifact readable after a rollback.
- **Make `publishedBy` required on `ArtifactRecord`.** Refused: a committed artifact has no publisher, so `undefined` is a fact rather than an omission, and a required field would refuse every snapshot an earlier build wrote.

## Consequences

- **One source set now answers the anchor question and the citation question**, which is what the review asked for; the cost is that a library registration whose DOI is one of the corpus's DOIs is the checked-in record, not the library's copy of it — the existing "a registration never overwrites a curated record" rule, applied to the key the two now share.
- **`publishedBy` is optional and read tolerantly.** `parseRegistry` keeps its allowances for a `producerStepId` that is not a step, because the format is read across builds and dropping them would make studies an earlier build wrote unreadable; `RUN_SNAPSHOT_SCHEMA_VERSION` is unchanged, since the addition is readable in both directions and the reader refuses nothing it accepted before.
- **A rollback of the step a publication inherited now invalidates the published version**, where before it did not touch it. That is the other side of the same link: the entry says which step's work this artifact is, and withdrawing that step withdraws it. The alternative was the state this note fixes, where no step could start at all and the only recovery discarded the edit.
- **What is not here**: nothing decides whether the citations a paper makes are the right ones. `manuscript-cites-sources` reads a count, and a paper that cites one source while holding twenty passes it — the per-source obligations are `owedCiteKeys` at D3 and `citation-*` at E1, and this condition exists because those cannot see the empty case.
- **What is not here**: a run refused at `prepareRun` for an uncitable registry is not recoverable by resuming it — the refusal is at run creation, and the remedy is the deployment's configuration. A run already under way when its registry changes is not re-checked, because the sources are a deployment capability and not a frozen field of the run; the package condition is what still stands over such a run.
- **What is not here**: `dsh-research-web`'s panel names the new condition and nothing else about it changed; no client-side control offers to fix a manuscript that cites nothing, because the fix is a rewrite the writer would have to make.

## Testing

- `registered-sources.spec.ts`: the library registration carries the corpus's judgement under the corpus DOI; an empty library carries none; `prepareRun` refuses the registry that cannot supply it and starts the one that can.
- `publication.spec.ts`: a publication inherits the producer link, records `publishedBy`, keeps `D4-rebuttal` and `E1-format` startable with no unsatisfied input, and inherits through a second publication.
- `final-package.spec.ts` and `paper-quality.spec.ts`: the refusal fires when the run held sources, does not fire when it held none, and reports as `defect-found` where the bibliography rule used to be `not-applicable`.
- `package-export.spec.ts`: the real run's package refuses a manuscript whose markers were removed, and the run before the removal passes.
- `e2e/recovery-t19b.spec.ts`: a held step's committed artifact produces a message naming the producer's status rather than one claiming the step looks startable.
- Each of the above was run with the fix reverted and fails without it; `vitest run packages/research` is 168 files and 2611 tests with no failures, and both `tsc -b` faces exit 0.
